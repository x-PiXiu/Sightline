# 02 · 服务端业务逻辑设计——账号登录 · 对战记录 · 模式选择

> **定位**：三大企业功能（简易版）的**业务规则与协议设计**——账号登录、对战记录、模式选择。
> 依赖 [01-服务端存储与脚本基础设施设计](01-服务端存储与脚本基础设施设计.md) 的存储地基（MySQL/Redis/Mongo + 存储线程池 + Lua 配置）。
>
> **设计总纲**：每类数据进对的库；用例只产出事实与编排意图；持久化细节全部在 Repository 实现内。
> **排期**：D2~D5（依赖文档一 D1 存储地基）；客户端蓝图 D6。

---

## 一、现状差距

| 能力 | 现状 | 差距 |
|---|---|---|
| 登录 | C2S_Login 只带 name，PlayerId 自增分配，断线即身份消失 | 无账号/凭证/持久化/重连身份 |
| 对局 | 三杀判胜 → 5s 重开，对局数据即抛 | 无 MatchRecord、无落库、无查询 |
| 房间 | 单房间单模式，胜利条件"三杀"写死，无列表/创建/选择 | 无 ModeConfig、无 Lobby |

**协议改法总则**：延续"加尾不改头"；C2S_Login 特殊处理见 3.1（旧格式 = 游客登录，天然兼容）。
**消息号续编**：现有最大 16（S2C_ItemTaken），新消息从 17 起。

| MsgId | 消息 | 方向 | 载荷 |
|---|---|---|---|
| 17 | C2S_Register | C→S | `[2B accountLen][account][32B passHash]` |

| 19 | S2C_MatchEnd | S→C | `[8B matchId][8B winnerAccountId][2B durationSec][2B count] × count{[8B accountId][2B kills][2B deaths]}` |

| 22 | C2S_ListRooms | C→S | 空 |
| 23 | S2C_RoomList | S→C | `[2B count] × count{[4B roomId][1B mode][1B curPlayers][1B maxPlayers]}` |
| 24 | C2S_CreateRoom | C→S | `[1B mode]` |
| 25 | S2C_JoinAck | S→C | `[4B roomId][1B ok][1B mode]` |

**两端纪律**：UE 侧 `EMsg` 与服务器 `MsgId` 同值枚举，改动两端同步、以本表钉死。

## 三、账号登录

### 3.1 领域模型

```
Account {
  accountId : uint64      // 全局唯一（MySQL 自增）
  account   : string      // 登录名（UNIQUE）
  passHash  : string      // SHA-256(密码+固定盐)——简易版约定
  nickname  : string
}
PlayerStats { accountId, wins, losses, kills, deaths }   // 战绩汇总（登录摘要直读）
```

### 3.2 服务与端口

```
AccountService（Auth 模块）
  ├─ register(account, passHash) → errCode        // 唯一性检查 → INSERT
  ├─ login(account, passHash) → {Account, token}  // 验哈希 → Redis SET token+TTL / SADD online
  └─ 依赖端口 IAccountRepository { load, save }

IAccountRepository（ports）
  ├─ 内存 fake（单测）
  └─ MySqlAccountRepository（adapters，prepared statement）
```

### 3.3 登录时序（存储线程复合任务）

```
epoll 线程: C2S_Login 收包（解析判别：账号格式 / 旧 name 格式→游客）
   ▼ 投递复合任务
存储线程:
   ① MySQL prepared: SELECT 账号 → 验 passHash
   ② 通过 → Redis: SET token:{accountId} EX 86400 + SADD online
   ▼ queueInLoop 回投
epoll 线程:
   分配 playerId、Session 绑定 conn ↔ {playerId, accountId, token}
   S2C_LoginAck(playerId, isGuest, accountId, nickname, 战绩, token) → 进入大厅
```

**密码安全（简易版约定）**：客户端 `SHA-256(密码+固定盐)` 后传输，服务端只存哈希——不传明文、不存明文。企业差距（TLS + bcrypt/argon2 + token 鉴权 + 防爆破限流）照实写进文档作为谈资。

**游客兼容**：旧格式 name-only 登录 = 游客（accountId=0，不入库、无战绩）。行为与现网一致，零破坏。

## 四、对战记录

### 4.1 领域模型与采集点

```
MatchRecord {
  matchId    : uint64       // MySQL 自增
  mode       : uint8
  winnerId   : uint64      // 胜者 accountId（游客=0）
  durationSec: uint16
  players    : [{accountId, kills, deaths}]   // Room 内现成的 kills/deaths
}
```

**采集点**：`RoomService` 三杀判胜处（唯一出口）——判胜即组装 MatchRecord，经 `IMatchRepository::save` 落库：

```
save 内部（存储线程）：
  ① MySQL 事务：INSERT match_record + UPDATE player_stats（胜者 wins+1/败者 losses+1，
                双方 kills/deaths 累加）
  ② Mongo  ：battle_logs 插入对局文档（事件流+结算快照，幂等重写）
  ③ Redis  ：ZINCRBY lb:kills（排行榜）
  顺序：先 MySQL 后 Mongo；失败策略 = Mongo 重试队列（不参与判定，允许延迟）
```

### 4.2 下发与查询

- `S2C_MatchEnd`（MsgId 19）：判胜后广播全员——客户端结算面板直接消费；
- `C2S_QueryRecord`（MsgId 20）→ `S2C_RecordList`（MsgId 21）：主菜单战绩页，`IMatchRepository::queryByAccount` 出最近 N 条。

## 五、模式选择

### 5.1 ModeConfig 参数化（Room 从写死变配置）

```
ModeConfig {
  mode       : uint8        // 1=Deathmatch 2=FlagCapture(预留)
  winKills   : uint8        // 0 = 不用击杀判胜
  winFlags   : uint8        // 0 = 不用夺旗判胜（夺旗 W4~W5 落点）
  maxPlayers : uint8
}
```

- `Room` 构造接受 ModeConfig；判胜检查策略化：`DM: kills >= winKills`；夺旗(预留)：`flags >= winFlags`；
- **win_kills 等默认值从 config.lua 读**（热更：reload 后新开局生效，进行中对局不受影响）；
- Lobby 维护 `roomId → Room(ModeConfig)`，房间列表协议从它出。

### 5.2 LobbyService

```
listRooms() → RoomList                      // 遍历活跃房间快照
createRoom(mode) → roomId                   // ModeConfig 从 config.lua 的 modes 表读
joinRoom(playerId, roomId) → ok/err         // 满员拒绝；简易版"匹配"= 满员自动开局
```

### 5.3 与夺旗（W4~W5）的衔接

模式框架就位后，夺旗 = ①新增 mode=2 的 ModeConfig ②domain 新增 Flag 规则子模块 ③Lua 里新增 modes[2] 配置——房间/落库/协议/客户端选择界面全部复用。

## 八、企业对照表

| 能力 | 企业做法 | 简易版 | 面试可讲 |
|---|---|---|---|
| 账号 | 独立账号服务/OAuth/token 鉴权/Redis 会话/防爆破限流 | 进程内 AccountService + MySQL + SHA-256+盐 | 密码为何不存明文；会话为何绑账号不绑连接 |
| 匹配/模式 | matchmaking 集群 + 房间服 | 进程内 LobbyService + ModeConfig | 为什么胜利条件要参数化（夺旗复用） |
| 战绩 | 战斗服→MQ→数据服务分库→Redis 排行榜 | 端口内 MySQL + Mongo 双写 + 独立写线程 | 写库为何不能阻塞网络线程；双写顺序与失败策略 |

## 九、风险与注意

1. **C2S_Login 语义变化**：旧客户端 name-only = 游客登录（兼容声明写入协议文档）；SessionService 既有测试随改造更新；
2. **写库阻塞**：全部存储操作走存储线程（文档一 StorageIO），epoll 线程零阻塞 IO——铁律；
3. **协议两端同步**：新消息号 17~25 两端枚举同步，以本文第二节为契约；
4. **游客战绩**：游客（accountId=0）的 kills/deaths 不落库（player_stats 主键为 accountId）——预期行为，文档明示；
5. **mongocxx 集成风险**：三驱动之最；受阻降级 = 对局文档暂缓（MySQL 汇总照常），见文档一降级矩阵。
