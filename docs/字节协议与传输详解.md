# Sightline 字节协议与传输详解

> 本文回答：**信息是怎么变成字节、字节怎么穿过 TCP、到达后又怎么变回信息的**。
> 所有字节序列都是 `scripts/demo_interact.py` 跑出来的**真实抓包**，非示意。
> 配套代码：`include/adapters/protocol_codec.h`（编解码）、`buffer.h`（缓冲）、`tcp_connection.h`（读写路径）。

## 一、一帧长什么样：逐字节解剖

Sightline 的线缆格式（wire format）：

```
┌──────────────┬──────────────┬────────────────────────┐
│ 2 字节 长度   │ 2 字节 消息ID │ N 字节 载荷(payload)    │
│ (payload长度) │ (这是什么消息) │ (这条消息的具体内容)     │
└──────────────┴──────────────┴────────────────────────┘
```

Demo 里 Alice 登录的真实字节：

```
07 00 01 00 05 00 41 6c 69 63 65
└┬┘   └┬┘   └──────┬──────────┘
 │     │            └─ payload: 05 00 41 6c 69 63 65
 │     │                 = [2B 字符串长度=5]["Alice" 的 ASCII]
 │     └─ msgid = 0x0001 = C2S_Login
 └─ len = 0x0007 = 7（payload 的字节数）
```

服务器回的 LoginAck：

```
04 00 02 00 01 00 00 00
└┬┘   └┬┘   └────────┬
 │     │              └─ payload: 01 00 00 00 = playerId=1
 │     └─ msgid = 2 = S2C_LoginAck
 └─ len = 4
```

**为什么需要"长度前缀"？** 因为 TCP 是**字节流**不是消息流——它只保证字节顺序，不保证"你 send 一次我 recv 一次"。两次 `send` 可能合并到达（粘包），一次可能被拆成两半（半包）。**长度前缀就是接收方在无边界的流里给每条消息"画边框"的唯一依据**。没有它，收到 `41 6c 69` 你无法知道 Alice 是不是完整的。这就是传说中的"自定义长度前缀 + 消息 ID"二进制协议，行业里最常见的手写格式。

**为什么 2 字节长度够用？** 65535 字节上限，游戏内单条消息（位置、开火、聊天）绰绰有余。若有大消息（地图快照），加一条分片消息或把长度升 4 字节即可。

## 二、字节序：为什么是 `07 00` 不是 `00 07`

数值 7 用两个字节表示是 `00 07`（大端/网络序）或 `07 00`（小端）。Sightline 全协议统一**小端**，原因很简单：

- x86、x86-64、主流 ARM 手机全都是小端机器；
- 两端（C++ 服务器 / UE 客户端）都是小端时，`memcpy(&val, bytes, 2)` 直接完成编解码，零转换成本；
- 网络字节序（大端）是互联网早期异构机器时代的惯例，对局域网自定义协议不是必需。

一个值得记的面试细节：**跨端严谨做法**是显式按字节拼（先发低字节还是高字节写进协议文档），而不是依赖"反正都是小端"。`ProtocolCodec::Writer` 就是这么做的——`u16(7)` 产出 `[0x07, 0x00]`，与机器字节序无关；解码侧的 `rd16` 目前用 memcpy（依赖两端同为小端），协议文档里已声明这个契约。

## 三、各种数据怎么变成字节

### 3.1 定长整数：直接按小端铺开

| 类型 | 字节 | 例 |
|------|------|-----|
| uint16 | 2 | `01 00` = 1 |
| uint32 | 4 | `02 00 00 00` = 2（playerId） |
| uint64 | 8 | `7b ac 52 91 91 01 00 00` = 1724720000123（Ping 时间戳） |

### 3.2 浮点数：IEEE 754，先到 uint32 再铺字节

float 不做任何特殊处理，**它的 32 个 bit 就是一个 uint32**：

```
Bob 的 y=10.0f 在 Move 帧里是  00 00 20 41
  = uint32 0x41200000
  = IEEE754: 符号0 / 指数 10000010(=130-127=3) / 尾数 0100...
  = 1.25 × 2³ = 10.0 ✓
```

`ProtocolCodec::Writer::f32` 的实现就两行：`memcpy(&bits, &v, 4); u32(bits);`。客户端同理还原。demo 里 respawn 位置的 `00 00 90 41` = 18.0f，正是出生点半径。

### 3.3 字符串：长度前缀 + UTF-8

```
05 00 41 6c 69 63 65
└─2B─┘└──── 5B ASCII ────┘
```

先告诉你多长，再给字节。为什么不给结束符 `\0`？定长前缀允许串里出现任意字符（包括 0），且读取时一次分配。

### 3.4 结构化数据：字段顺序即协议

协议就是"**第几个字节是什么**"的契约。以 Hit 事件为例（demo 第 4 枪）：

```
11 00 08 00 | 01 00 00 00 | 02 00 00 00 | 19 00 00 00 | 00 00 00 00 | 01
 len=17  id=8   shooter=1    victim=2     dmg=25(0x19)  victimHp=0    dead=1
```

17 = 4+4+4+4+1，每个字段的偏移都是写死的。**改字段顺序 = 破坏性协议变更**，两端必须同步（这也是未来换 protobuf 的动机：schema 文件即契约，自动生成两端代码）。

## 四、全消息字节布局表（与 UE 客户端的共同契约）

| MsgId | 方向 | 消息 | payload 布局 | demo 实测 |
|-------|------|------|--------------|-----------|
| 1 | C→S | Login | `[2B 名字长度][UTF-8 名字]` | `07 00 01 00 05 00 41 6c...` |
| 2 | S→C | LoginAck | `[4B playerId]` | `04 00 02 00 01 00 00 00` |
| 3 | C→S | JoinRoom | 空（身份由会话推导） | `00 00 03 00` |
| 4 | S→C | RoomStart | `[4B 人数]{每人 [4B playerId]}` | `0c 00 04 00 02 00...01 00...` |
| 5 | C→S | Move | `[3×4B pos][4B yaw]`（**不含 playerId**） | `0c 00 05 00 00 00 00 00...` |
| 6 | S→C | MoveEvt | `[4B pid][3×4B pos][4B yaw]` | `14 00 06 00 02 00 00 00 00 00 20 41...` |
| 7 | C→S | Fire | `[3×4B 起点][3×4B 方向]` | `18 00 07 00 ...80 3f...`（`80 3f`=1.0f） |
| 8 | S→C | Hit | `[4B shooter][4B victim][4B dmg][4B victimHp][1B dead]` | 见 3.4 |
| 9 | S→C | GameOver | `[4B winner]` | `04 00 09 00 01 00 00 00` |
| 10 | C→S | Ping | `[8B 客户端时间戳]` | `08 00 0a 00 7b ac 52...` |
| 11 | S→C | Pong | `[8B 原样回传时间戳]` | 同上，一字不差 |
| 12 | S→C | Kick | `[1B 原因]`（1=心跳超时） | — |
| 13 | S→C | PlayerLeft | `[4B pid]` | `04 00 0d 00 02 00 00 00` |
| 14 | S→C | Respawn | `[4B pid][3×4B pos][4B hp]` | `14 00 0e 00 ... 64 00 00 00`（hp=100） |

**注意 C→S Move 不含 playerId**：服务器从连接会话推导身份（`SessionService::playerIdOf`），客户端无法伪造"别人在移动"。这是服务器权威在协议层的第一道体现。

**Ping/Pong 的设计**：服务器原样回传客户端时间戳，客户端用 `now - 回传值` 得到 RTT。服务器不需要理解时间戳的含义——**最省的 RTT 方案**。

## 五、为什么用二进制而不用 JSON

用 demo 的 Move 上报算账（FPS 客户端 10Hz 每玩家）：

| | 二进制帧 | 等价 JSON |
|---|---|---|
| 内容 | `0c 00 05 00` + 4×float | `{"x":0,"y":0,"z":0,"yaw":0.5}` |
| 字节数 | **16** | ~40（含引号逗号，数字更长时更多） |
| 每玩家每秒 | 160 B | 400+ B |
| 解析成本 | `memcpy` × 4 | 词法分析 + 建树 + 字符串转 float |
| 注入风险 | 无（定长字段） | 字段缺失/类型错需防御 |

差距看起来不致命？再乘上：**8 人房间 × 10Hz × 转发**、**万人 CCU 的转发服务器**、以及移动端流量资费——二进制是实时游戏的默认选择。JSON/Protobuf-JSON 适合登录、公告、配置这类低频非关键路径。

## 六、字节怎么穿过 TCP：粘包/半包与 Buffer

发送端 `send` 三次，接收端可能收到任意切割：

```
发送: [帧A 11B][帧B 20B][帧C 12B]
线路: ──A──B前半─┃断点┃─B后半──C──     (TCP 只保证字节序，不保证边界)
```

接收侧的解法在 `adapters/buffer.h` + `ProtocolCodec::tryExtract`：

```
Buffer（累积缓冲）                    tryExtract 的拆帧状态机
┌─────────────────────────┐
│ 已读 │  待解析字节        │    1. readable < 4？→ 等下次（半包头）
│      │                  │    2. 读出 len；readable < 4+len？→ 等（半包体）
└──────┴──────────────────┘    3. 够了 → 切出一帧，retrieve(消费)
                                4. 循环，处理"一次到达多帧"（粘包）
```

游戏服务器面试的高频题"**怎么处理粘包/半包**"，答案就是这两行：**长度前缀定边界 + 累积缓冲攒数据**。Sightline 的实现是 `GameServer::onMessage` 里的 `while (auto pkt = tryExtract(buf))`——一个循环同时消化粘包与半包。

## 七、读路径：ET + readv 排干

`TcpConnection::handleRead`（连接 fd 是边缘触发模式）：

```cpp
while (true) {
    ssize_t n = input_buffer_.readFd(fd, saved_errno);
    if (n > 0) continue;                    // 继续读：ET 只通知一次，必须读到 EAGAIN
    if (n == 0) { handleClose(); return; }  // 对端关闭
    if (EAGAIN/EWOULDBLOCK) break;          // 排干完毕 ← ET 的"读完了"信号
    ...
}
if (readableBytes() > 0) message_cb_(...);   // 整批交给分发器
```

`Buffer::readFd` 内部用 `readv` 一次系统调用读两块（Buffer 剩余空间 + 64KB 栈上临时区），减少 syscall 次数；读超了再 append 进 Buffer。

**ET vs LT 的核心区别**：LT（水平触发）只要还有数据没读，epoll 每次都提醒你；ET（边缘触发）只在"从无到有"那一刻提醒一次——**所以 ET 必须一次读完**，否则剩余数据永远不会再来提醒（直到新数据到达）。读 ET 省 wakeup 次数，代价是必须排干，Sightline 的读事件用 ET、写事件用 LT 的混合模式，理由见《架构设计文档》。

## 八、写路径：直写 → 输出缓冲 → EPOLLOUT

`TcpConnection::sendInLoop` 的三级火箭：

```
send(字节)
  ├─ 输出缓冲为空？→ 直接 write() 进内核发送缓冲   ← 99% 的情况在这里结束
  ├─ 内核缓冲满(EAGAIN) / 有剩余？→ 追加进 output_buffer_ + enableWriting()
  │                                          （关注可写事件，等待内核腾出空间）
  └─ EPOLLOUT 到来 → handleWrite() 排干 output_buffer_
                      └─ 发完 → disableWriting()   ← 不发数据时绝不关注可写
```

最后一步是 LT 写事件的关键纪律：**LT 下"可写"几乎恒真，不关掉就会空转唤醒**。demo 日志里偶见的 `sendInLoop write error` 就是客户端已关闭还尝试写（EPIPE），随后走正常的连接清理链路。

## 九、协议演进：改字段怎么办

二进制定长协议的软肋是**版本兼容**。实践中的三级方案：

1. **加尾不改头**：新字段只许追加在 payload 尾部，老代码按 len 截断忽略（demo 协议天然支持——len 决定解析边界）；
2. **版本号消息**：登录时协商协议版本，分流新旧解析；
3. **换 protobuf**：`.proto` 文件即契约，字段编号 + tag 允许前后兼容，两端代码自动生成——这是 Sightline W6 计划的动机。届时**只替换 ProtocolCodec 一个文件**，这正是"翻译收口在适配层"的架构红利。

## 十一、前后端契约面清单（协同设计边界登记表）

> 凡是"改一头必须改另一头"的东西都在这张表上。**登记规则：任何对契约面的改动 = 两端同步修改 + 各自仓库提交说明，只改一端即事故。**
> 服务器实现：`include/adapters/protocol_codec.h`；客户端实现：UE 工程 `Source/FPS_Game/SightlineProto.h`；契约正文以本文第四节消息表为准。

| 契约项 | 内容 | 服务器落点 | 客户端落点 | 状态 |
|---|---|---|---|---|
| 消息表 | msgid 分配、字段布局、字节序、长度前缀 | `protocol_codec.h` MsgId+encode/decode | `SightlineProto.h` EMsg+Enc/Decode | ✅ 冻结(1~14) |
| 坐标系映射 | 服务器 y-up ↔ UE Z-up，互换收口在两端 codec | 广播原值 | EncMove/Decode 内换轴 | ✅ 已做 |
| 身份语义 | C→S 不带 playerId（会话推导防伪造）；pid 生命周期 | `SessionService` | 蓝图不自报身份 | ✅ 已实现 |
| 心跳参数配套 | Ping 间隔 2s < 超时 8s；Kick reason 码 | `SessionService::Config` | Ping 定时器 + Kick(12) 处理 | ✅ 已配套 |
| 同步频率与插值 | 10Hz 上报 ↔ VInterpTo 速度是一对参数 | RoomService 转发 | RemotePawn 插值 | ✅ 当前档配套 |
| 背压与限流 | 高水位踢人/令牌桶 ↔ 客户端上报自律(10Hz) | TcpConnection+装配侧 | 遵守上报频率 | ✅ 服务器侧已有 |
| 协议版本演进 | "加尾不改头"（len 决定边界，老端忽略新尾部） | codec 天然支持 | `tryExtract` 同理 | ✅ 规则已定 |

**待协同设计事件**（未来仅有的三个允许动这张表的时机，每一个都需两端一起改）：

1. **W5 断线重连**：重连 token / 宽限期时长 / 恢复范围（血量·位置·房间）——服务器 `SessionService` 语义改造（detachPlayer+宽限定时器，见架构文档第五节落点推演），客户端重连 UI 与状态恢复；加 2 个消息号。
2. **W6 KCP 可靠性分级**：哪些消息可靠（登录/开火/Hit）哪些可丢（移动快照）——服务器换 adapters 传输实现，客户端 Subsystem 换 KCP 端点；帧格式不变，可靠语义变。
3. **W6 protobuf**：`.proto` 成为单一事实源，替代两端手写编解码；消息号保留，两端代码改为生成。

**预测校正（W6+，若做）**：协议需加输入序列号/客户端时间戳字段——归入"同步频率与插值"契约项的扩展，同样两端同步。
