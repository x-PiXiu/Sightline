# 案例 12 · 血条显示架构——轮询与事件驱动的分层抉择

> **标签**：UMG 架构 · 边沿/电平语义 · MVVM · C++与蓝图分工
> **一句话**：血条该轮询还是事件驱动？——正确答案是分层组合：
> **数值用轮询保准确，反馈用事件保及时**；HUD 复杂化后演进到 MVVM 数据绑定。

---

## 一、问题背景（Situation）

项目 HUD（血条 + 弹药数字 + 武器名）在换装迁移（BP_Player → BP_LyPlayer）后出现
数据链断裂：WBP_HUD 的数据绑定 `Cast to BP_Player` 对新 Pawn 失败 → HUD 拿不到
任何数据。Cast 修复为 `SightlineCharacter` 后，**数值显示自动恢复**（轮询绑定生效）。

由此引出本案例的架构问题：**血条显示业界到底用每帧轮询还是事件通知？为什么？**
以及本项目的组合方案如何定位。

## 二、机制分析（为什么不是简单二选一）

### 2.1 本质：边沿语义 vs 电平语义

UI 更新需求分两类，适配的机制天然不同：

| 语义 | 定义 | FPS 例子 | 天然适配 |
|---|---|---|---|
| **边沿（edge）** | 某瞬间"发生了一件事" | 受击红闪、"+50"飘字、受击音、方向伤害指示器、镜头微抖、命中标记 | **事件**——有明确起因、时刻和上下文数据 |
| **电平（level）** | "当前值是多少"的持续事实 | 血条百分比、血量数字、弹药计数 | **轮询/数据绑定**——任何时刻读都成立 |

**关键洞察**：血量"值"是电平，但**每次血量变化是边沿**（受击/治疗都是离散事件）。
受击红闪这类反馈是纯边沿语义——轮询做边沿检测需要自己保存上一帧值做对比，
**等于重新发明事件系统**，还拿不到事件上下文（谁打的、哪个方向、多少伤害——
红闪颜色和方向指示器恰恰依赖这些）。

### 2.2 FPS 为什么尤其偏向事件驱动：一对多扇出

一次受击在 FPS 里天然驱动**一整串反馈**：

```
一次 DamageEvent（服务器判定 + 广播）
  ├─ 受击者：血条扣减、屏幕红闪、受击音、方向伤害指示器、镜头微抖、手柄震动
  ├─ 攻击者：命中标记、伤害数字、命中音
  └─ 致死时：击杀播报、观战切换……
```

**一个事件、六个以上消费者**——观察者模式的教科书场景。轮询方案下每个消费者
都要自己逐帧 diff"我的数据变了吗"：六份重复的边沿检测代码，还拿不到事件的
上下文字段（打你的人的方位、伤害类型）。事件广播一次、全员各取所需。

### 2.3 但轮询也有真实的生存空间（三个理由）

| 理由 | 说明 |
|---|---|
| **零生命周期管理** | 事件绑定要管解绑：widget 销毁时解绑了吗？pawn 重生后重绑了吗？**悬空委托是 UI 系统 bug 的头号来源**。轮询无状态，免疫此类 bug |
| **连续变化量天然适配** | 冲刺体力、载具速度表、倒计时——每帧都在变，事件会退化成"每帧发事件"，与轮询等价还多一层转发 |
| **原型成本** | 一个绑定函数 5 分钟搭好；事件推送需要设计"谁创建 HUD、谁持有引用、如何订阅" |

### 2.4 一个容易踩的 UE 特有限制（本项目实际遇到）

`BlueprintImplementableEvent`（如 GameState 组件的 `BP_OnHealed`）**只能由声明类
自己的蓝图子类实现**——USightlineGameStateComponent 没有 BP 子类，所以
BP_LyPlayer（Character 蓝图）**无法直接实现该组件的治疗事件**。

解法 = **C++ 桥**：角色 C++ 在治疗路径调用自己声明的角色级事件
（`ASightlineCharacter::BP_OnHealed(NewHp)`，提交 `5544aff`），
BP_LyPlayer 作为 Character 的子类即可实现它。**组件事件 → C++ 桥 → 角色事件 →
蓝图表现**，三层转发，各层类型安全。

## 三、实现梯度（从原型到 Lyra 级）

| 层级 | 做法 | 适用 | 代表 |
|---|---|---|---|
| **原型** | UMG 函数绑定每帧轮询（`GetOwningPlayerPawn → Cast → GetHP`） | 快速验证、简单 HUD | 本项目现状（Cast 修复后） |
| **进阶** | C++ 委托（`OnHealthChanged` 多播）→ HUD 函数推送；特效挂角色级 BP 钩子 | 中型项目、功能完整的 HUD | 本项目（BP_OnHealed 桥已加，随需接线） |
| **生产/3A** | **MVVM**（UE 5.1+ 官方 ViewModel 插件）：ViewModel 持有字段 + 字段变化通知，View 声明式绑定；或 GAS 的 `AttributeSet` 变化委托 | 复杂 HUD、多控件、团队协作 | **Lyra**（血量存 GAS AttributeSet，UI 订阅属性变化委托驱动 ViewModel） |

**Lyra 的具体答案**（与本项目最相关）：血量存在 **GAS AttributeSet**，角色订阅
属性变化委托（事件），变化时更新 **HUD ViewModel** 的字段（带字段通知），
血条 widget 绑定 ViewModel 字段——**事件只负责把新值推进 ViewModel（一次），
视图随数据声明式更新（多次）**。这就是"轮询 vs 事件"争论的工业化调和：
**事件推进数据缓存，视图声明式消费缓存**。

## 四、决策规则（可复用）

```
这个 UI 需求，数据是边沿还是电平？
├─ 边沿（发生了某件事：受击/治疗/拾取/击杀）
│    → 事件驱动（效果直接挂事件；多消费者用委托扇出）
├─ 电平（当前值是多少：血条百分比/数字/进度）
│    ├─ 值少且稳定 → 轮询绑定（简单可靠）
│    └─ HUD 复杂/多控件 → MVVM ViewModel（事件推进缓存，View 声明式绑定）
└─ 混合（血量：值+边沿都有）
     → 事件更新"值缓存"，边沿触发"特效"——缓存供轮询/绑定读
```

## 五、本项目落地的组合架构

```
WBP_HUD（显示层）
├─ 血条 Percent      ←── 方法 B：轮询绑定（GetOwningPlayerPawn
├─ 血量文本 "75/100"  ←─     → Cast to SightlineCharacter → GetHP ÷ 100）
│                       （受击/治疗/重生全覆盖，下一帧自动反映）
│
BP_LyPlayer（表现层）
├─ BP_OnHitReceived ──→ 红闪特效/受击音            ← 只做效果
├─ BP_OnHealed ──────→ 绿闪/"+50"飘字/治疗音       ← 只做效果
└─ BP_OnRespawned ───→ 重生特效
```

**分工铁律**：轮询管"值"，事件管"效果"——**事件节点里不再 Set Percent/文本**
（避免双写互相覆盖）。特效实现收口在 WBP_HUD 暴露的函数（如
`PulseHealthBar(FLinearColor)`），角色蓝图只调用。

**成本诚实账**：1~2 个轮询绑定的每帧成本是微秒级（对比一次 GC 卡顿数十毫秒），
"隐形税"在当前规模可忽略；绑定数量长大后再全面转推送/MVVM——演进路径清晰，
不需要提前设计。

## 七、追问演练

**Q：为什么不干脆全部事件推送，彻底消灭轮询的每帧税？**
A：推送要求 HUD 能订阅所有数据源事件——需要管理订阅生命周期（widget 销毁
解绑、pawn 重生重绑），悬空委托是 UI bug 的头号来源。1~2 个绑定的每帧轮询
成本微秒级，"隐形税"论在绑定数量少时是伪命题；绑定膨胀后（十几个、链路含
Actor 查找）再全面转推送/MVVM——演进按需，不过早设计。

**Q：血量的"低血量心跳效果"（低于 30% 屏幕泛红 + 心跳音）用哪种？**
A：**状态机语义**——跨过阈值是一个边沿（进入低血量状态），状态持续期间是
电平（保持泛红）。实现：事件跨阈值时触发进入/退出（对比新旧值跨没跨 30%），
状态持续期间的效果由状态自身驱动。纯轮询做需要逐帧对比，纯事件做需要
"每帧报告当前区间"——正确解是**边沿触发状态切换 + 状态驱动表现**。

**Q：受伤红闪和血条更新，哪个必须事件？**
A：血条（电平）轮询可替代；**红闪（边沿）必须事件**——它需要"受击这一刻"
的触发，轮询只能对比上一帧值模拟，且拿不到伤害方向等上下文。方向伤害
指示器同理：没有事件的方向数据就做不出来。

**Q：Lyra 是轮询还是事件？**
A：都用了——GAS AttributeSet 变化委托（事件）推进 **UI ViewModel** 字段，
View 声明式绑定 ViewModel（带字段通知的 MVVM 模式）。事件负责"变化通知"，
ViewModel 负责"数据缓存"，View 只声明绑定——三层各司其职，这正是本项目
"轮询管值、事件管效果"组合在大型项目里的成熟形态。

## 八、30 秒速答卡

> "血条显示业界主流是**事件驱动的分层架构**，但不是简单二选一：血量的'值'是
> 电平语义——血条百分比用数据绑定读缓存；'变化'是边沿语义——受击红闪、飘字、
> 方向指示这些效果必须事件驱动，因为它们需要事件的上下文（谁打的、多少伤害、
> 什么方向），而且一次伤害要扇出六七个反馈，观察者模式天然匹配。纯每帧轮询
> 只适合原型——它表达不了边沿效果，绑定多了还有每帧的隐形税。UE 5.1+ 的
> 标准答案是 MVVM：事件推进 ViewModel 字段、View 声明式绑定——Lyra 就是
> 这么做的。我项目当前是'数值轮询 + 事件特效'的混合，HUD 复杂化后按这个
> 梯度演进。"
