# 案例 05 · 武器蓝图连锁报错——类设计评估与变更扩散半径

> **标签**：类设计评估 · 依赖方向 · 变更扩散半径 · 迪米特法则
> **一句话**：一个蓝图编译失败，武器和 HUD 全线跟着炸——用这次真实事故
> 提炼出"六问检查法"，把设计好坏变成可测量的指标。

---

## 一、现象（Situation）

`BP_Player` 编译失败后，`BP_Weapon_VIRTUS`、`WBP_HUD` 等一批不相干蓝图
**集体编译报错**。这些蓝图各自逻辑完好，却全线下线。

## 二、机制（为什么一坏全坏）

```
BP_Player 编译失败（病灶）
      ↓
UE 规则：不能 Cast 到编译失败的类
      ↓
所有含「Cast to BP_Player」节点的蓝图 → 集体失败（症状遍地）
```

受害者自身无错——**病在一处，症状遍地**。这正说明依赖形态出了问题。

## 三、六问检查法（评估框架）

把设计原则翻译成六个可回答、可观察的问题：

| # | 检查问题 | 对应原则 | 观察细节 |
|---|---|---|---|
| 1 | 有几种变化理由？ | SRP | 一句话描述职责，数"当…时要改它"的数量 |
| 2 | 知道别人哪些内部细节？ | 迪米特 | 引用的是公开接口还是别人的成员/子组件 |
| 3 | 依赖的是稳定还是易变对象？ | DIP | C++/抽象（稳定）vs 蓝图/具体（易变） |
| 4 | 改它会让谁跟着改？ | OCP | 变更扩散半径（fan-out） |
| 5 | 状态谁能写？ | 单一真源 | 状态变量写入口数量 |
| 6 | 能脱离环境测试吗？ | 可测试性 | 构造参数数、是否需要引擎/网络 |

外加两个关系形态检查：**继承还是组合**（is-a 还是 has-a）、
**fan-in/fan-out**（高入度高出度=上帝类；高入度低出度=稳定基石）。

> **核心直觉**：好设计 = **变更局部化**——任何变更的影响被限制在少数类内部。

## 四、实例体检：旧武器蓝图逐条不合格

旧链：`BP_Weapon_VIRTUS --Cast--> BP_Player --Get--> ArmsMesh --播--> 旧骨架动画`

| # | 检查 | 结果 |
|---|---|---|
| 1 | 变化理由 | 换枪要改、角色模型改要改、换弹表现改要改——≥3 种 ❌ |
| 2 | 知道别人细节 | 知道角色有 ArmsMesh 组件、知道插槽名、知道骨架动画——**对角色 internals 如数家珍** ❌ 迪米特 |
| 3 | 依赖稳定性 | 依赖蓝图类 + 组件级内部细节——**全部是最易变层** ❌ DIP |
| 4 | 变更扩散 | **实测**：BP_Player 坏 → 武器/HUD 全炸；删 ArmsMesh → 播动画链断裂 ❌ |
| 5 | 状态 | 弹药 HUD 靠轮询绑定每帧拉取，无事件源 ⚠️ |
| 6 | 可测试性 | 换弹表现必须 PIE + 双客户端才能验证 ❌ |

**fan-out 清点**：旧武器出度 = BP_Player + ArmsMesh + 旧骨架动画 = **3 个易变依赖**。

## 五、新设计与对比

```
旧：武器 --Cast--> BP_Player --Get--> ArmsMesh --播--> 旧骨架动画
新：武器(只依赖 C++ 基类 + Definition DA)
    角色侧经 GetCurrentWeapon → GetArmReloadMontage 自己来取
```

| # | 新设计 | 判定 |
|---|---|---|
| 1 | 变化理由只剩"武器行为规则变了"才动 C++ | ✅ |
| 2 | 武器对角色的全部认知 = 基类指针 + 四个公开事件，**不知道 ArmsMesh 存在过** | ✅ |
| 3 | 依赖 C++ 基类（编译期冻结）+ DA（纯数据），全是稳定方向 | ✅ |
| 4 | 换角色模型：武器零改动；加新枪：复制 DA + 空蓝图 | ✅ |
| 5 | 弹药唯一写入口 = C++ ConsumeAmmo/AddReserveAmmo | ✅ |
| 6 | 冷却/弹药/换弹规则全在 C++，可纯单测 | ✅ |

**fan-out 对比**：旧 = 3 个易变依赖；新 = **0 个蓝图依赖**。

## 六、实操：三个快速体检动作（UE 特定）

1. **引用查看器**（右键资产）：数入度/出度；出度里出现蓝图类 = 红灯；
2. **Ctrl+F 搜 Cast**：每处 Cast 到蓝图子类都是一条隐形依赖线
   （本次全线报错就是它们集体引爆）；
3. **假想删除测试**："删掉/重命名这个成员，几处报错？"——报错数 = 变更扩散半径。
   旧设计的答案"3 个系统全炸"；新设计"0"。

## 七、追问演练

**Q：四个蓝图事件的最终归宿是什么？**
A：两个（ShotImpact 贴画、AmmoChanged HUD）与具体武器无关，**在 BP_Weapon_Base
实现一次、子类永久继承**；两个（ReloadStarted/FireEffects）的资产化部分由 C++ 从
Definition 自动播放，蓝图钩子降级为可选的额外表现口——**蓝图事件需求被压到趋近于零**。

**Q：为什么 C++ 基类就"稳定"？蓝图类就不稳定？**
A：稳定与否看**变化频率和变化原因**。C++ 类编译进模块，只要游戏逻辑在它就是那个
契约；蓝图子类会被删除、重构、改名（BP_Player→BP_LyPlayer 就是活例）。DIP 的
"依赖抽象"在 UE 的落地就是"依赖 C++ 基类/接口，不依赖蓝图子类"。

**Q：怎么区分"该拆"和"过度设计"？**
A：变化理由是真的发生过还是想象的。我们为此定过纪律（路线图反 YAGNI 条款）：
"第二实现什么时候出现？排期里有才做"。比如 BP 基类抽象——第一把枪时直继 C++
是对的，复制第二把枪时的真实痛点出现，才提炼 Base（三次法则的 UE 版）。

## 八、30 秒速答卡

> "判断类设计我用六问：职责单一吗、知道别人多少内部细节、依赖稳定还是易变、
> 改它扩散多远、状态写入口唯一吗、能单测吗。我们有个真实事故：玩家蓝图一编译
> 失败，武器和 HUD 全线跟着炸——因为武器 Cast 到玩家蓝图还直接操作它的手臂组件。
> 重构后武器只依赖 C++ 基类和一个数据资产，四事件在基类写一次子类继承。
> 前后对比的量化指标是变更扩散半径：旧设计删一个组件三个系统全炸，新设计是零。
> **好设计的分水岭，就是变更来了爆炸半径是一个类还是半个工程。**"
