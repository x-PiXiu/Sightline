# 案例 10 · 命中表现从蓝图迁入 C++——"结果为无"报错与职责归位

> **标签**：蓝图接线脆弱性 · 职责归位 · C++/蓝图分工判断标准
> **一句话**：`尝试读取属性 ImpactFXConfig 时结果为无` 每枪刷屏——排查发现子类蓝图
> 把该属性**显式覆盖成了 None**（冻结了父类继承），最终以"职责归位 + 继承机制修正"
> 双层修复，并确立了 C++/蓝图/DA 三方的分工标准。

---

## 一、现象（Situation）

PIE 中每开一枪刷一条蓝图运行时错误：

```
LogScript: Warning: 尝试读取SightlineWeapon中的(real)属性ImpactFXConfig时，结果为无
    Function /Game/Code/Weapon/Base/BP_Weapon_Base_C:ExecuteUbergraph_BP_Weapon_Base
    节点：分支  图表：EventGraph  蓝图：BP_Weapon_Base
PIE: Error: 蓝图运行时错误：...
```

同时贴画/音效/碎屑全部失效。

## 二、机制分析（Action · 证据 → 结论）

### 2.1 报错本身的解读（三层信息）

```
读取对象：SightlineWeapon（武器实例）
读取属性：ImpactFXConfig（贴画配置 DA 引用）
读取结果：无（None）
执行位置：BP_Weapon_Base 的 EventGraph，一个 Branch（分支）节点
```

结论 ①：**BP_Weapon_Base 里有完整的 ShotImpact 实现**且每枪都在执行
（错误每枪刷一次 = 链在跑，卡在配置读取这一步）✓ —— D3.3 的复制移植是成功的。
结论 ②：**配置引用为空** → 分支失败 → 贴画/音效/碎屑全灭。

### 2.2 实锤根因：子类显式 None 覆盖冻结了继承

**蓝图属性默认值的真实继承机制（delta 序列化）**：

```
子类 CDO 构造 = 复制父类 CDO（继承全部默认值）
              + 叠加子类资产里序列化的"差异项"
```

- 子类**从未存储**某属性的差异 → 跟随父类（父类改了自动跟）✅
- 子类**显式存储了覆盖**（哪怕值是 None）→ 冻结，**不回退父类** ❌

本次事故：`BP_Weapon_Rifle` 的类默认值里，`ImpactFXConfig` 被显式序列化为
**None**（排查期间误触保存）——父类 BP_Weapon_Base 后来设置的 DA 无法穿透
这条显式覆盖，运行时实例读到 None → 分支失败 → 三件套全灭。

**为什么 UE 这样设计**：如果"子类为 None 就回退父类"，你将永远无法表达
"这个子类故意没有 X"——清空父类提供的值会成为不可能的操作。显式 None 是
合法覆盖，UE 必须尊重。代价是它**静默失效、不报编译错**，只能靠运行时日志发现。

**诊断实锤手段**（C++ 临时日志，定位后移除）：

```cpp
UE_LOG(Warning, TEXT("[诊断] %s | 父类=%s | ImpactFXConfig=%s"),
    *GetName(), *GetClass()->GetSuperClass()->GetName(),
    ImpactFXConfig ? *ImpactFXConfig->GetPathName() : TEXT("None"));
```

输出 `父类=BP_Weapon_Base_C | ImpactFXConfig=None` → 一行日志同时证明
**继承链正确**（排除父类问题）与**覆盖存在**（锁定子类属性层）。

修复：BP_Weapon_Rifle 类默认值 → Impact FX Config 手动重选 DA → 编译保存 →
诊断行显示 DA 路径 → 贴画恢复。

## 三、职责归位：命中三件套移入 C++

### 3.1 决策依据（什么逻辑该在蓝图、什么该在 C++）

本项目的表现分层原则（案例 02/06 已建立）：

| 表现类型 | 归属 | 例子 |
|---|---|---|
| **规则驱动**（查表/配置 → 自动播） | **C++** | 枪声/枪口火焰/弹壳池/命中三件套——`FireShot` 里按配置自动执行，蓝图零参与 |
| **资产化差异**（每把枪/每个表面长什么样） | **DA/资产槽** | `DA_SightlineImpactFX`（表面→表现包）、`DA_Weapon_Rifle`（武器定义） |
| **子类专属附加**（个别武器的独特花样） | **蓝图钩子**（BP_OnFireEffects 等） | 曳光弹、特殊烟——按需实现 |

命中三件套 = "按表面查表 → 弹孔/音效/碎屑"——**纯查表规则**，完全符合
"规则驱动 → C++"的归属。原来放蓝图（读 ImpactFXConfig 再三件套）是教程式
写法，其接线脆弱性（悬空引用/复制断链/迁移丢失）已在本次事故中充分暴露。

### 3.2 C++ 实现（FireShot 内，替换 BP 链）

```cpp
if (W->LineTraceSingleByChannel(Impact, Origin, Origin + Dir * 100000.f, ECC_Visibility, Params))
{
    const EPhysicalSurface SurfaceType = UPhysicalMaterial::DetermineSurfaceType(Impact.PhysMaterial.Get());

    // 命中三件套（C++ 数据驱动：查 ImpactFXConfig 按表面分流）
    if (ImpactFXConfig)
    {
        FSightlineImpactFX FX;
        if (ImpactFXConfig->TryGetImpactFX(SurfaceType, FX))
        {
            if (FX.DecalMaterial)   // 池弹壳
                Pool->SpawnDecal(FX.DecalMaterial, Impact.ImpactPoint, Impact.ImpactNormal, FX.DecalSize);
            if (FX.ImpactSound)     // 落地音
                UGameplayStatics::PlaySoundAtLocation(this, FX.ImpactSound, Impact.ImpactPoint);
            if (FX.ImpactSystem)    // 碎屑特效
                UNiagaraFunctionLibrary::SpawnSystemAtLocation(this, FX.ImpactSystem, Impact.ImpactPoint);
        }
    }
    BP_OnShotImpact(Impact, SurfaceType);   // 钩子降级：仅子类专属附加表现
}
```

**注意字段判空**：DA 某字段留空（如 Enemy 行不贴弹孔）时跳过该项——三件套
各自独立判空，互不阻塞。

### 3.3 附带修复

- **合并版文件缺失 include**：`NiagaraFunctionLibrary.h`（另一台机器的文件合并时被清理）——
  补上后 `SpawnSystemAtLocation` 才能编译。

## 四、结果（Result）

- 蓝图运行时错误清零（BP_Weapon_Base 的 ShotImpact 链整段删除后无代码可错）；
- 命中三件套在 C++ 自动执行：开枪打墙 = 弹孔+音效+碎屑，**蓝图零接线**；
- 每把新武器继承即得（C++ 基类行为），加枪成本进一步下降；
- 子类显式覆盖已修正（重选 DA 后诊断行显示 DA 路径）——**同类陷阱的通用防御**：
  配置类属性在子类蓝图里"要么显式填值、要么确认无覆盖标记"，处于
  "显示 None 但以为在继承"的中间态最危险（静默失效、不报编译错）。

## 五、追问演练

**Q：为什么蓝图属性会"结果为无"？子类不是继承父类默认值吗？**
A：蓝图默认值继承是"子类存储与父类的差异"——没动过的属性跟随父类；一旦在
子类手动改过（哪怕改回空），属性被标记为显式覆盖并冻结。BP_Weapon_Rifle 的
链路里某个 SightlineWeapon 引用为空（Target 悬空或覆盖为 None），读取即得 None。

**Q：为什么不修 BP 接线而要移 C++？**
A：接线修复治标——下一次复制/迁移/重构还会断。移 C++ 治本：这条链是
"查表→分发表现"的规则逻辑，不依赖任何蓝图状态，C++ 实现后**蓝图零接线、
零断链风险**，且每把新武器继承即得。判断标准：逻辑是否依赖具体武器/蓝图
状态——依赖则留蓝图，不依赖则下沉 C++。

**Q：EditDefaultsOnly 的属性，运行时实例能读到值吗？**
A：能。EditDefaultsOnly 只限制"编辑位置"（只能改类默认值，不能改实例），
实例生成时属性值从 CDO 拷贝，运行时读取正常。日志能证明：BeginPlay 预热
读同一个属性命中了 4 个特效系统——配置链路本身是通的。

**Q：三件套里哪个留在蓝图了？**
A：都没有。`BP_OnShotImpact` 钩子保留声明但降级为可选——只有子类专属的
附加表现（如击杀特写）才需要实现它，标准三件套永远由 C++ 自动执行。
