# 案例 03 · 道具系统——服务端权威的网络对象生灭

> **标签**：服务端权威 · 协议设计 · 惰性计算 · NetID/TypeID 解耦
> **一句话**：地图上出现血包/弹药箱、走过自动拾取、15 秒重生——
> 全程只加 2 条下行消息、0 个定时器、0 条上行消息。

---

## 一、需求与核心权衡（Situation → 决策）

需求：地图刷血包/弹药箱，走近自动拾取，效果生效，一段时间后重生。

**第一个决策：走过自动拾取 vs 按键拾取。**

拾取没有"用户意图"要表达（不是"我要开枪"这种主动动作，是走过去被动触发），
所以判定可以直接挂在**位置上报**上——每次 `applyMove` 顺带做距离检查，
**省掉 C2S_Pickup 消息、省掉输入绑定、省掉请求-验证往返**。服务端权威还天然成立：
位置本身就是服务器采纳的。

**第二个决策：重生怎么驱动——惰性检查，不用定时器。**

道具冷却到点需要重置。独立定时器要管理生命周期（房间销毁要清理），
而拾取检查本来就搭在 applyMove 上——**重生检查也搭同一班车**：
每次有人 move 就扫一遍 `taken && now-taken_at > cooldown`。
代价是"房间里没人移动就不重生"——但没人移动就意味着没人在玩，重生给谁看？
**零空闲开销换一个无害的延迟，是赚的。**

## 二、协议设计（契约面 +2 条，加尾不改头）

| MsgId | 方向 | 布局 | 说明 |
|---|---|---|---|
| 15 | S→C | `[4B netId][1B typeId][12B pos]` | 道具出现（开局布点/冷却重生共用） |
| 16 | S→C | `[4B netId][4B pid][1B typeId][4B pickerNewHp]` | 被拾取（含拾取者新血量） |

关键设计——**NetID / TypeID 解耦**：

- `netId`：房间内自增（重开一局重新从 1 计），客户端据此建立场景 Actor 镜像表；
- `typeId`：1=血包 2=弹药箱（两端枚举数值契约），**道具长什么样完全由客户端
  DataAsset 决定**——服务器换皮零改动，服务器只发"出现了一个 1 号"。

血包的服务器效果：`hp = min(max_hp, hp+50)`，新血量随 ItemTaken 下发——
**治疗是服务器权威的**。弹药箱：服务器只标记冷却，弹药是客户端本地演出
（协议不管弹药——设计取舍，不是疏漏，注明即可）。

## 三、服务端实现要点（domain 纯净 + 惰性）

```cpp
// domain/room.h —— 规则全部在实体层，可纯单测
std::optional<PickupResult> tryPickup(PlayerId pid, const Vec3& pos, double now_ms) {
    if (state_ != Playing) return nullopt;          // 开局前不可拾取
    Player* p = findPlayer(pid);
    if (!p || !p->alive) return nullopt;            // 死人不可拾取
    for (auto& item : items_) {
        if (item.taken) continue;                   // 冷却中
        水平距离² > r² → continue;                   // 只看水平距离（道具贴地）
        item.taken = true; item.taken_at_ms = now_ms;
        if (血包) p->hp = min(max_hp, p->hp + heal); // 封顶回血
        return PickupResult{...};
    }
    return nullopt;
}
```

时间由 application 层传入（`steady_clock` 毫秒），**domain 不持有时钟**——
保持实体层零依赖、可纯单测（4/4 绿）。

RoomService 编排：开局/重开统一走 `startRoundFor`（布点 + RoomStart + 逐个
ItemSpawn 广播）；`handleMove` 里顺带 tick 重生广播 + 拾取广播。

## 四、客户端实现要点（镜像 + 表现）

- `Items: TMap<NetId, AItemActor*>` 与服务器镜像；同 NetId 重复 Spawn 先清旧的（防御）；
- `BP_OnRoomStart` 清空镜像（新一局服务器重发，防残留防重复）；
- **血包拾取**：`GameState->SetHp(pickerNewHp)`——服务器权威值回填（HUD 走既有
  BP_OnHealed 链）；**弹药箱**：`Weapon->AddReserveAmmo(DA.AmmoAmount)`——本地加备弹；
- 道具外观零蓝图子类：`USightlineWeaponDefinition` 同款思路，
  `DA_SightlineItemConfig` 按 TypeId 查 `{Mesh, 特效, 音效, 自转速, SpawnZOffset}`；
- 表现细节：道具生成/销毁由 C++ Handle 驱动，蓝图钩子只画拾取特效——
  且 **ItemTaken 钩子触发时 Actor 尚未销毁**（故意把 Destroy 放钩子后），
  蓝图可直接读它的位置播特效。

## 五、结果与验证

- 服务端单测 4/4 绿（布点数/NetID 自增/满血封顶/半径边界/死人不可拾/Waiting 不可拾/
  冷却重生时序）+ 依赖三红线干净；
- 双开联调：双方道具位置一致、拾取**双端同时消失**（权威性的直接体现）、
  15 秒同 NetId 重现、重开一局无残留。

## 六、追问演练

**Q：走过自动拾取会不会被外挂刷？**
A：拾取判定在服务器（applyMove 内的距离检查），刷的边界=移动合法性的边界。
本项目 MVP 不做移动速度校验（applyMove 注释里写明它是反外挂校验的自然进化位）——
这是已知边界，不是漏洞。

**Q：为什么血包服务器权威、弹药却本地加？**
A：血包影响战斗平衡（对局胜负），必须权威；弹药是手感演出，当前协议没有弹药
同步，加权威的成本（协议+校验+同步）远大于收益。**权威性是按影响面分配的**，
不是"全部权威"的教条。

**Q：惰性重生的"没人动就不重生"算 bug 吗？**
A：算设计行为：重生是给"正在玩的人"看的，没人在动=没人在玩，重生无观众。
且惰性检查省掉了每房间的常驻定时器和它的生命周期管理。

**Q：为什么 born 点半径从 18 改 1800？**
A：历史遗留——18 在 UE 厘米世界是 18cm，重生点挤在地图原点附近。改成 1800（18 米）
并在单测里加了区间断言（`sp.x ∈ (1700,1900)`）——**用测试锁住修复**，防回归。

## 七、30 秒速答卡

> "道具系统我做了三个省法：**省一条上行消息**——拾取没有用户意图，判定搭位置
> 上报的车（10Hz 同频），走过就捡；**省一批定时器**——重生用惰性检查，也搭同一班车，
> 零空闲开销；**省一层耦合**——NetID 管身份、TypeID 管外观，客户端查 DataAsset
> 决定长什么样，服务器换皮零改动。血包回血服务器权威（新血量随消息下发），
> 弹药本地加（非权威，设计取舍）。单测覆盖拾取规则全分支，双端拾取消失时机一致。"
