# 15 · 客户端整洁架构审查与表现层整改手册

> **定位**：以整洁架构(Dependency Rule)为镜头，对客户端**代码 / 动画 / 特效 / 贴图**做的一次架构审查。
> 每个问题按固定模板记录：**问题 → 为什么会出现 → 什么业务场景暴露 → 如何优化 → 优化思想 → 如何验证有效**。
>
> **与其它文档的关系**：
> 14 号 = 武器动画实施记录 + 已踩坑清单(骨架/插槽/Clamp Axis 等"已发生已修"的坑)；
> **本篇 = 架构层的病根分析 + 未整改问题的工单**。坑是症状，本篇是病因。
>
> **验证基准**：所有"验证有效"均以 PIE 双开为基准环境(A 端本地玩家 / B 端傀儡)。

## 一、审查框架：客户端的四环模型

整洁架构唯一规则：**依赖只能由外向内**。映射到本客户端：

```
┌────────────────────────────────────────────────────────┐
│ L4 框架与资产(最外环·最易变·替换成本应最低)              │
│   BP 图 / AnimBP / Niagara / SoundBase / 蒙太奇          │
│   MM_Rifle_* / SK_Rifle / CS_WalkBob / 材质与贴图        │
├────────────────────────────────────────────────────────┤
│ L3 适配层                                               │
│   ✓ Definition DA(数据注入)  ✓ Proto 编解码              │
│   ✓ RemotePawn 插值(网络快照→表现状态)                    │
│   ✓ GetAimPitchDeg(协议同源取值)                          │
├────────────────────────────────────────────────────────┤
│ L2 用例层(游戏行为)                                     │
│   EquipWeapon / StartFire / FireShot / Reload            │
│   ReportMove / HandleMove / 弹药与冷却规则                 │
├────────────────────────────────────────────────────────┤
│ L1 语义内核(最内环·最稳定)                               │
│   PlayerId / HP / Ammo / Flags(开火/蹲/跳) / AimPitch     │
│   客户端的本质:服务器权威状态的"呈现语义"                  │
└────────────────────────────────────────────────────────┘
```

**判据一句话：换一把枪 / 换一套动画 / 换一种特效，允许动的只有 L2 的 DA 填充和 L4 的资产；碰了 L1/L3 就是违规。**

**已做对的(点名保留，防止整改时误伤)**：
- `BP_On*` 钩子体系 = 教科书式的依赖倒置端口(内环声明事实，外环决定表现)；
- Definition 收口武器数据，C++ 零资产路径；
- `GetAimPitchDeg()` 协议同源(本地与傀儡俯仰天然一致)；
- 对象池 + 装备期预编译纪律。

## 二、代码侧问题

### P1 FireShot 职责混合——用例内核直调四种表现框架

- **问题**:`ASightlineWeapon::FireShot` 一个函数内同时完成内环职责(弹药判定/冷却时间戳/命中权威/抛壳)与外环职责(枪身蒙太奇 `Montage_Play`、`PlaySoundAtLocation` 音效、弹壳池取用+物理激活、Niagara 火焰触发、`BP_OnShotFired` 钩子)。
- **为什么会出现**：迭代历史造成——早期单武器单场景，"开枪" = "一声枪响一个火光"，写在最顺手的地方；后续蒙太奇/弹壳池/钩子逐期叠加，每次都加在同一个函数，从未按职责切分。这是典型的**增量演进未回构**。
- **业务暴露场景**：①给武器新增表现(曳光弹、枪口烟、后坐相机震屏)必须改内核函数，改坏命中判定就是线上事故；②表现出 bug(如弹壳不弹)的调试要在规则代码里翻；③想做"观战模式隐藏部分表现"或"性能分级关特效"时，发现表现与规则焊死，无从开关。
- **如何优化**:`FireShot` 只产出**事实对象**(如 `FShotFiredEvent{ 弹道, 后坐强度, 命中结果, 时间戳 }`)，通过事件/委托广播；表现编排整体迁入订阅方(BP_Weapon_Rifle 或独立 WeaponPresentation 组件)。渐进式：不必一次迁完，每次新增表现时**只准加在订阅侧**，存量随功能顺手搬家。
- **优化思想**：**单一职责 + 依赖倒置**。用例层产出语义事实(内环)，表现订阅事实自行编排(外环)——即把已经建好的 `BP_On*` 口岸走完，让"走私"变"报关"。
- **验证有效**：①`FireShot` 函数体内不再出现 `UGameplayStatics`/`Montage_Play`/Niagara API；②PIE 双开回归：开火的表现(枪身蒙太奇/音效/弹壳/火焰/手臂后坐)与重构前逐项一致；③临时屏蔽表现订阅端，命中与弹药规则仍正常(可单独测试规则层)。
- **增补（2026-09-16 二次审查）**：①**傀儡枪口火焰缺失**是本项事实事件化后的第一批订阅者——当前傀儡开火仅有枪身抖动(PlayAnimation)，无 muzzle flash，对局中"看不见敌人开枪"是可感知的表现缺口（协议 bit0 数据现成）；②落地前先清查工程内既有 AnimNotify 资产（`Code/AnimNotify`、`Effects/AnimationNotifies` 目录已存在）——Notify 化是"推广既有"而非"从零引入"。

### P2 协议位魔数散落三个文件

- **问题**:`0x01/0x02/0x04` 以裸十六进制出现在 `SightlineSessionComponent.cpp`(ReportMove 打包)、`SightlineRemotePawn.cpp`(SetTarget 解码)、`SightlineRemotePawnManager.cpp`(透传)，无命名常量。
- **为什么会出现**：Phase 1 快速贯通时"先跑通"，位定义只存在于 11 号文档；三处使用点各自写死，之后文档与代码还发生过位分配漂移(原设计 bit0=蹲，实际 bit0=开火)。
- **业务暴露场景**：①新增第四个同步位(换弹中/武器类型)时，三处+文档需要人肉同步，漏一处就是"本地有状态傀儡没有"类 bug；②新同事按文档位定义读代码，读出相反语义。
- **如何优化**：C++ 定义唯一真源 `enum class EMoveFlag : uint8 { Firing=1, Crouching=2, Jumping=4 };`(放协议头文件)，三处全部引用；文档标注"位定义以该枚举为准"。
- **优化思想**：**单一事实来源(Single Source of Truth)**。文档描述现实，代码定义现实，两者不能各自演化。
- **验证有效**：①全局搜索 `0x01` 等裸魔数清零；②新增一个同步位的改动只落在枚举 + 打包 + 解码三个必要点，文档零改动。

### P3 武器参数双源(类默认值 vs Definition)

- **问题**：MagSize/FireCooldown/CasingPoolSize 等字段在类默认值和 Definition DA 各存一份，靠 BeginPlay 回填("Definition 优先、类默认兜底")。同一字段两处可改。
- **为什么会出现**：Definition 是 P8 期才引入的数据收口，引入前的老参数留在了类默认值；回填模式是为了兼容而非设计终态。
- **业务暴露场景**：排查"弹匣为什么是 20"时要同时看两处、推理回填顺序；策划只改了 DA 没生效(类里被别处覆写)或反之——典型的"改了没反应"工单。
- **如何优化**：类默认值只保留**结构安全值**(非零防除零、防负数)，语义值全部由 Definition 给出并在文档注明；长期方向是 P8 预留的"规则字段(DamagePerShot/RPM)迁入服务端契约"。
- **优化思想**：**配置单一来源**。兜底值的存在应该是"防崩溃"，不是"第二配置位"。
- **验证有效**：①任取一个武器参数，仅修改 DA 即可改变行为(无需碰 C++/BP)；②故意清空 DA 字段时行为退化为安全值而非崩溃或脏值。
- **增补（2026-09-16）：字段对照表（整改时逐项核对，防漏改）**：

| 字段 | 类默认值 | Definition 真源 | 状态 |
|---|---|---|---|
| Mesh / AnimClass / FireSound / ReloadSound / 四蒙太奇 / MuzzleOffset / CasingOffset / MeshRotationOffset | — | ✓ 已收口 | ✅ |
| MagSize / FireCooldown / ReserveAmmoMax / ReloadTime / bAutoReloadOnEmpty | 有(当前真源) | ✗ 待迁 | P8 预留注释已标 |
| CasingPoolSize | 10 | ✗ 待迁 | P4 |
| MaxActiveCasings | 20(constexpr) | ✗ 待迁 | P4 |
| ImpactFXConfig | 类属性(无默认) | ✗ 待迁 | P10 |

### P4 调优参数进内核(constexpr)

- **问题**：弹壳活跃上限 `MaxActiveCasings = 20` 为 `static constexpr`(SightlineWeapon.h:200)；贴画池渐隐(20s/3s)、环数(64)写死在子系统。
- **为什么会出现**：写池子时数值是"当时拍脑袋的合理值"，没预期到会成为调优对象。
- **业务暴露场景**：性能调优(同屏弹壳过多掉帧)或观感调优(弹壳留太久满地都是)时，改一个数字要重编译整个工程。
- **如何优化**：全部迁为 `EditDefaultsOnly` UPROPERTY 或 Definition 字段；贴画池参数进子系统 Class Defaults。
- **优化思想**：**调优参数与逻辑分离**——代码表达"存在一个上限"，数值表达"上限是多少"，后者属于数据。
- **验证有效**：PIE 中在 Details 面板改数值即生效(重启关卡)，全程零编译。

## 三、动画侧问题

### P5 角色 ABP 武器锁定——"用什么枪 link 什么动画"未实现(最大结构项)

- **问题**：ABP_Player_Manny 的 AnimGraph 烘焙了 MM_Rifle 全族资产：BS_Rifle_Locomotion_2D、BS_Rifle_Crouch、跳跃三段(MM_Rifle_Jump_Start/Fall_Loop/Fall_Land)、瞄准层(MM_Rifle_Idle_Hipfire + AO_MM_Rifle_Idle_Hipfire)。结构图(L3)直接引用具体资产(L4)。
- **为什么会出现**：Phase 1 的目标是"最小可用"——当时只有一把步枪，直接把序列拖进图里是**当时的最优解**；此后每期(蹲/跳/瞄准层)都在同一张图上增量叠加，每次叠加都让"以后再抽象"的成本翻倍，形成沉没成本循环。**这是所有硬编码问题的母题：Demo 起步，增量演进，缺一次结构重构的里程碑。**
- **业务暴露场景**：①装备第二把枪(手枪)——移动/跳跃/瞄准姿势全是步枪，角色"持手枪却跑出持步枪姿态"；②换角色骨架——整张 ABP 重链；③动画师想单独调整步枪动画包——要在主 ABP 里翻找，与结构节点纠缠。
- **如何优化**：ALI_WeaponPose 动画分层五步(14 号文档 4.2 节)：建接口资产 → 主 ABP 留空的 Linked Anim Layer 插槽(现有 Rifle 链作为默认实现整体搬入)→ `Definition.PoseLayer` 字段 → 装枪时 `Link Anim Class Layers` / 卸枪 Unlink → 每枪一个层实现 ABP。
- **优化思想**：**依赖倒置 + 开闭原则的动画版**。主 ABP(L3 骨架)对"武器种类"封闭修改、对"新姿势层"开放接入；姿势层的解析从编译期(烘焙)移到运行期(Link)——与 `BP_On*` 钩子、Definition 注入是同一个思想在动画维度的重演。
- **验证有效**：①打开 ABP_Player_Manny，AnimGraph 内搜索不到任何 "Rifle" 字样的资产节点；②**换枪测试**：新建 DA_Pistol 填 PoseLayer → 游戏内换枪，姿势层自动切换，全程未打开过角色 ABP；③未链接任何层时，默认实现行为与改造前逐帧一致(回归)。

### P6 武器 ABP 每枪复制 + 遗留命名

- **问题**：武器动画蓝图实际资产名为 `ABP_VIRTUS`(上一代武器遗留名)承担 Rifle 职责；且其结构只有 `DefaultSlot → Result`，与武器种类无关，却被设计为每枪复制一份。
- **为什么会出现**：武器 ABP 诞生于 VIRTUS 时代；迁移到 SK_Rifle 后只换了用途没换名。而"每枪一个 ABP"是把角色 ABP 的复杂度误推广到了武器侧——武器网格的动画需求(蒙太奇宿主)天然全枪通用。
- **业务暴露场景**：新枪开发时复制 ABP_VIRTUS → 改名 → 网格/骨架逐一对，纯仪式性工作且改名容易漏(引用按路径)。
- **如何优化**：重命名为 `ABP_Weapon_Slot`，所有武器 Definition.AnimClass 共同指向它；仅当某把枪需要程序化特殊结构(如开膛待击、双持)时才派生子类。
- **优化思想**：**共性与个性分离**。先问"这个资产里有哪部分随枪变"——答案是"没有"，那就合并。
- **验证有效**：全局仅存在一个武器 ABP 资产；新增一把枪全流程零 ABP 操作。

### P7 ABP/蓝图魔数散落

- **问题**：FInterpTo 速度 10(AimWeight)、过渡混合时间 0.1/0.15、(若采用)俯仰系数 0.6、相机位(Z70/X8)、View Bob 振幅——散落各 BP 图内，无集中管理。
- **为什么会出现**：调参时"就地改数字"最快，没有人会为一个大临时改一个常量建资产。
- **业务暴露场景**：①手感统一调优(如全线放宽过渡时间)要翻多个资产；②两处用了同名概念不同数值(如两处"插值速度")排查困难。
- **如何优化**：建 `DA_GameFeel` 调优资产(相机/插值/混合时间/震屏参数分组)；ABP 侧至少把数值提升为命名变量并分类注释。
- **优化思想**：**调优参数与逻辑分离**(同 P4)。
- **验证有效**：手感类调整全部在单一 DA 内完成，全程零打开 BP 图。

### P8 插槽名字符串耦合 ✅ 已解决(契约表成文)

- **问题**：蒙太奇资产的插槽轨道名与 ABP 插槽节点名靠字符串约定耦合(FullBodyAdditivePreAim/UpperBody/DefaultSlot)，无文档。曾实际踩坑：换弹蒙太奇轨道在 UpperBody，开火在 FullBodyAdditivePreAim，不一致时"播了看不见"。
- **为什么会出现**：插槽机制本质是引擎级字符串协议，GAS 素材按自己的约定命名，迁移时约定未被显式记录。
- **业务暴露场景**：新蒙太奇落错轨道 → 播放无任何表现、无报错。
- **如何优化**：插槽名契约表写入 14 号文档(已完成)；新增蒙太奇必须落表内轨道。
- **优化思想**：**隐式契约显式化**。字符串协议无法靠编译器约束，就只能靠文档契约 + 人工核对清单。
- **验证有效**：新增蒙太奇时对照契约表操作，一次接通率 100%。

### P9 ABP 单资产三层职责

- **问题**：ABP_Player_Manny 同时承担：①数据喂值(事件图表 7+ 变量、双 Cast 分支)；②图形结构(状态机/层/插槽链)；③调试(Print/临时节点)。一个资产三层职责。
- **为什么会出现**：单骨架单角色的规模下，拆分收益不明显，合并维护成本最低——**当前规模这是合理选择**。
- **业务暴露场景**：变量持续增长(每加一个同步量图更挤)、新人读图成本上升、动画师与程序在同一张图冲突。
- **如何优化**：暂不动；触发条件=变量超过 12 个或出现第二套角色骨架时，拆分喂值(接口函数化)与结构(Anim Layers)。**记录在案，防止"忘了它已经超载"。**
- **优化思想**：**重构触发条件显式化**——不为未来过度设计，但为未来埋好"该动手了"的信号。
- **验证有效**：达到触发条件时本条目能被检索到(文档存在即有效)。

## 四、特效/贴图侧问题

### P10 ImpactFXConfig 双源

- **问题**：命中特效配置(SurfaceType→贴画/音效/粒子/尺寸)的引用挂在 `ASightlineWeapon` 类属性(SightlineWeapon.h:158)而非 Definition——武器 BP 层配置。
- **为什么会出现**：ImpactFXConfig 体系(09 号)晚于武器框架出现，挂在当时最顺手的"武器自己身上"；Definition 收口意识是后来才建立的。
- **业务暴露场景**：**已实际发生过**——子类 BP 显式 None 覆盖导致命中特效配置丢失，"结果为无"报错刷屏；换新枪时漏配即复现。
- **如何优化**：`Definition.ImpactFXConfig` 字段收口，武器 BeginPlay 按既有回填模式读取；武器类属性退役。
- **优化思想**：**每枪配置的唯一入口是 DA**(与 P3 同源思想)。
- **验证有效**：新建一把枪只填 DA，命中表现四件套(贴画/音效/粒子/尺寸)全部生效；全局搜索确认无第二处配置入口。

### P11 弹壳/贴画两套池模式重复

- **问题**：弹壳 Actor 池与贴画组件池各自手写，生命周期/回收/预热逻辑模式相同但实现独立。
- **为什么会出现**：两个功能在不同期由不同需求驱动，各自为战。
- **业务暴露场景**：新增第三类 pooled 特效(弹道拖尾/碎片)时第三次重写同构逻辑。
- **如何优化**：抽 `TQueuePool<T>` 式通用池基类(或组件池模板)，弹壳/贴画改为特化；新特效零成本入池。
- **优化思想**：**模式抽象**——第三次重复之前完成抽象(规则 of three)。
- **验证有效**：新特效接入池 ≤ 10 行代码；现有两池回归无异常。

### P12 特效分级缺失(多人规模项)

- **问题**：所有粒子全量播放，无 Significance/距离分级。
- **业务暴露场景**：多人同屏开火时粒子预算爆炸(当前 2 人无感)。
- **如何优化**：接入 Significance Manager 或简单的距离裁剪；触发条件=支持 4 人以上同房间时。
- **优化思想**：**按需表现**——看不见的特效不值得算。
- **验证有效**：多人压测下帧率平稳，近处特效观感无差异。

### P13 音频无总线体系(全项目最大缺口)

- **问题**:`PlaySoundAtLocation` 裸播，无 SoundClass 混音分组(武器/环境/UI)、无衰减资产体系。
- **为什么会出现**：音频一直是"功能存在即可"的配角。
- **业务暴露场景**：全局调音量要逐资产改；枪声与 UI 音无法分组平衡；距离衰减全靠默认。
- **如何优化**：建 SoundClass 总线树(Weapon/Ambient/UI)→ Mix in Sound Cue 或 MetaSound → 音频资产挂组；C++ 播放路径不变(资产自带分组)。
- **优化思想**：**表现的横切维度用体系管，不用资产逐个管**。
- **验证有效**：运行时改 Weapon 组音量，所有枪声同步变化，其它音不受影响。

- **验证**：手感调优零打开 BP/ABP。

## 六、流程问题

### P15 设计-实现漂移 + 回写纪律

- **问题**：flags 位分配文档与代码漂移(已发生已修)；计划外功能(跳跃/2D 混合空间/瞄准层)完成后未即时回写文档(11 号本次补齐)。
- **为什么会出现**：文档是"写在大地上的事后总结"而非"随代码演进的活物"；没有"完成后 30 分钟内回写"的纪律。
- **业务暴露场景**：新人/未来的自己按旧文档读代码读出错误语义(位分配那次就是典型)。
- **如何优化**：①协议位代码化为枚举(见 P2)——代码成为唯一真源，文档引用之；②"功能验收通过 → 当次会话内回写文档"作为完成定义(DoD)的一部分。
- **优化思想**：**文档是接口的一部分**——它和代码一样需要"编译检查"(回写纪律就是它的编译)。
- **验证有效**：任意文档描述的机制，代码中可按文档直接定位；下次审查时漂移项为零。

## 七、UI/材质/道具/命名层问题

### P16 HUD 武器信息硬编码 + Definition 展示元数据缺失

- **问题**：WBP_HUD 中武器名称("MCX-VIRTUS.300BLK")与图标为写死的文本/图片；Definition 无 DisplayName/Icon 字段。另：HP/弹药采用每帧轮询+Cast 模式（案例 12 已分析）——**登记为显式接受的决策**，防止重复审查。
- **为什么会出现**：HUD 先于武器数据体系做完，当时只有一把枪，"先写死"顺理成章。
- **业务暴露场景**：装备第二把枪 → HUD 仍显示旧名/旧图标；玩家误以为换枪失败。
- **如何优化**：Definition 增加 `DisplayName`(FText) / `Icon`(Texture2D) 两个展示字段；HUD 在 `BP_OnWeaponEquipped` 时读取刷新。
- **优化思想**：与 P3/P10 同源——"一切每枪可变物进 DA"，HUD 是武器数据的**消费者**而非定义者。
- **验证有效**：换枪测试中 HUD 名称/图标随 Definition 变化；HUD 图内搜索零武器相关常量。

### P17 材质/贴图规范缺失

- **问题**：`MI_Weapon_Rifle` 参数化(✓)但未成文为约定；无 MPC(材质参数集)统一控制；特效材质混合模式/渲染优先级无规范；贴图分组/流送策略未约定。
- **为什么会出现**：材质单件使用时参数化收益不可见——规范总是"第二个材质出现时"才被需要。
- **业务暴露场景**：受击闪白要同时作用于角色+武器+道具三种材质，无 MPC 就要三种实现；将来红蓝团队配色同理。
- **如何优化**：建工程级 MPC(受击强度/团队色/高亮)；约定"可变参数一律走 MI 实例"；明确特效材质的 Deferred Decal/Translucent 使用边界。
- **优化思想**：**横切维度用 MPC，个体差异用 MI**——企业惯例分工。
- **验证有效**：受击闪白=改一个 MPC 参数全材质生效；新增材质按清单即合规。

### P18 道具类型枚举硬编码（范围声明：本期仅登记）

- **问题**：`ESightlineItemType`（客户端）与服务器 ItemTypeId 数值耦合（HealthPack=1/AmmoBox=2）；新增道具 = 协议 + 服务端 + 客户端枚举 + DA 四处同改。
- **为什么会出现**：P2 道具系统只有两类，枚举直传是最短路径——**当前合理**。
- **业务暴露场景**：新增第三种道具（护甲/高爆弹箱）时的四处联动与漏改风险。
- **如何优化**：新增道具立项时同步设计"道具注册表"（类型 id → DA 映射，服务器下发 id，客户端查表）。
- **优化思想**：同 P2——数值协议 + 查表解耦。
- **验证有效**：新增道具类型时客户端侧只新增 DA 资产 + 查表一行。

### P19 跨类同名事件（BP_OnReloadStarted ×2）

- **问题**：`ASightlineWeapon` 与 `ASightlineCharacter` **各有一个同名 `BP_OnReloadStarted`**（前者武器钩子，后者经 `OnWeaponReloadStarted` 转发）。两个类都是蓝图父类，添加事件节点时极易加错目标。
- **为什么会出现**：两期功能独立命名，"ReloadStarted" 是最自然的名字，撞了。
- **业务暴露场景**：接换弹手臂蒙太奇时事件加在错误类上 → 静默不触发（BP 事件无编译错误）。
- **如何优化**：武器侧改名（如 `BP_OnGunReloadVisual`）或至少在本契约表登记区分；长期约定：**跨类事件不允许同名**。
- **优化思想**：同 P8——隐式契约显式化。
- **验证有效**：在任意武器/角色 BP 中搜索事件名，唯一命中。
