# Sightline 演进路线图（归档版）

> **定位**：项目全生命周期的演进规划归档——每个阶段回答四个问题：**什么业务触发它、服务端改什么、客户端改什么、怎么算完成**。
> **性质**：本文是计划基线，不是承诺清单。每个阶段有明确的**触发条件**——条件不到不做（YAGNI），条件到了按本文执行（不临时拍脑袋）。任何偏离本文的演进决策，需先在本文登记修订。
> **配套**：架构依据见《架构设计文档》，协议契约见《字节协议与传输详解》第十一节契约面清单，客户端架构见《03-客户端架构与C++基类设计》。

## 一、演进总则（所有阶段共同遵守）

### 1.1 触发框架（反 YAGNI 纪律）

| 问题 | 答案 |
|---|---|
| 这个抽象的第二实现什么时候出现？ | 排期里有明确阶段才做；"以后可能要"不做 |
| 需要代码评审/单元测试吗？ | 是 → C++；纯表现/配置 → 蓝图或数据资产 |
| 改动会动契约面吗？ | 会 → 两端同步 + 契约面清单登记 + 各自提交注明 |
| 影响服务器权威吗？ | 会 → 规则落 domain，客户端只服从 |

### 1.2 每阶段通用完成定义（DoD）

- [ ] `build_and_test.sh` 全绿（编译 + 单测）
- [ ] `check_dependencies.sh` 三红线干净
- [ ] 冒烟 `run_smoke.sh` 通过
- [ ] 契约面如有变更：两端文档同步 + 提交注明
- [ ] 压测基线不回退（30000 连接 0 失败 / p50 ≤ 0.4ms）

### 1.3 反目标（明确不做，防止范围蔓延）

| 反目标 | 理由 |
|---|---|
| 分布式多进程房间 | 单进程 3 万连接已超 demo 需求；分布式是运维课题非架构课题 |
| 账号鉴权体系 | 无第三方账号依赖；Login 简化是已知限制非缺陷 |
| 配置热更新 | 毕设 800 行热更新烂尾的直接教训——配置收敛为启动时一次性注入 |
| UE 复制系统混用 | 自研网络是项目核心叙事，NetMode 锁死 Standalone |
| 微服务拆分 | 服务不是架构——单体内部分层完整即达标 |

## 四、各阶段详细规划

### P1：蓝图从零搭建 + 回归（当前主线）

| 项 | 内容 |
|---|---|
| **业务** | 客户端从"无 UI 骨架"变为可玩可演示 |
| **服务端** | **零改动**（协议契约已冻结） |
| **客户端** | 按《05-蓝图从零搭建手册》执行：BP_RemotePawn → ABP_Manny → BP_Player → ABP_Arms → BP_Weapon → 六步回归 |
| **契约面** | 无变更 |
| **验收** | M1（登录+RTT）/ M2（双开互见）/ M3（对射重生胜负）全绿；拔服务器不崩溃 |
| **产出** | 迁移/搭建对照表（面试讲"逻辑下沉"的素材） |

---

### P2：道具系统（弹药箱/血包）

| 项 | 内容 |
|---|---|
| **业务** | FPS 基础玩法闭环；展示"网络对象动态生成与销毁 + NetID/TypeID 映射" |
| **设计原则** | 服务端定规矩（位置/刷新/拾取判定），客户端演皮影戏（模型/特效）；枚举是唯一通用货币 |

**服务端**：
- `domain/`：`item.h`（TypeId 枚举 + Item 结构体）；`Room` 增加 items 容器 + **在 applyMove 内懒检查拾取**（走过自动拾取：距离<拾取半径 + 冷却 → 效果结算 → 标记 + 延迟重生）
- `application/`：编排并入 `RoomService`（广播 Spawn/Taken 事件）
- `adapters/`：codec 新增 **2** 条 S2C 消息——`S2C_ItemSpawn`(15)、`S2C_ItemTaken`(16)（省掉 C2S_Pickup，拾取判定在 applyMove 内——走过自动拾取，契约面更小）
- **顺带修复**：`spawnPoint` radius 18→1800（18米），修 P3 联调发现的出生点单位遗留
- **契约面**：登记消息表 + NetID 分配规则（Room 内自增）+ TypeID 枚举（HealthPack=1/AmmoBox=2）

**客户端**：
- `SightlineProto`：EMsg 追加 `S2C_ItemSpawn(15)` / `S2C_ItemTaken(16)` + 语义节点（含坐标换轴）
- `ASightlineCharacter`：`HandleItemSpawn/HandleItemTaken` + `Items` TMap + 钩子 `BP_OnItemSpawned/BP_OnItemTaken`
- 表现：`AItemActor`(DataAsset 驱动：TypeId/模型/旋转速度，道具不走蓝图子类) — **数据驱动练兵**为 P8 铺路

**验收**：双开——地图刷新道具双方可见 → A 拾取 → B 侧消失+音效 → 血包回血数值正确（服务器权威）。

### P3：HUD/表现打磨

| 项 | 内容 |
|---|---|
| **业务** | 交付标准中的"HUD 显示：playerId、HP、RTT、击杀播报"；演示观感 |
| **服务端** | 零改动（现有事件已携带全部所需数据） |
| **客户端** | Print 全部替换为 UMG：血条（绑 `GetHP`）、弹药（绑武器 `AmmoInMag`）、RTT、击杀播报（`BP_OnKillConfirmed`）、受击红闪（`BP_OnHitReceived`）、死亡/重生遮罩、Tab 网络面板（RTT/字节率，字节率读 Subsystem 统计） |
| **契约面** | 无变更 |
| **验收** | 交付标准 DoD（交接文档 Step 9）：双开完整对局 + HUD 全项 + 拔线不崩 |

### P4：夺旗战（"数据节点"模式）

| 项 | 内容 |
|---|---|
| **业务** | 第二玩法证明多模式架构能力；炫技变体（动态带宽/服务端时钟进度条/对象生命周期） |

**服务端**：
- `domain/`：**IRoomMode 接口抽取**——`onPlayerJoin/Leave、validateFire、checkWinCondition、onTick`；现有 FPS 规则迁入 `modes/fps_mode.h`（第一实现，行为零变化，单测护航）；新增 `modes/capture_mode.h`（数据节点规则：球生成/携带/上传进度/得分/服务端时钟驱动）
- `application/`：`RoomService` 按模式实例化 Room（构造注入 IRoomMode）
- `adapters/`：新消息（C2S_EnterMode/球位置流/进度同步/得分事件）
- **契约面**：登记新消息组

**客户端**：
- 基类加对应 `Handle*` + `BP_On*`；球的表现（BP_Ball）+ 进度条 UI
- 抱球者同步频率调整 = 服务端广播节流（客户端无感，插值兜底）

**验收**：双开完整夺旗对局；FPS 模式回归不变（IRoomMode 抽取零行为变化的证明）。

---

### P5：断线重连

| 项 | 内容 |
|---|---|
| **业务** | 网络抖动不应判负——"连接断开 ≠ 玩家退场"语义 |

**服务端**（架构文档第五节已有落点推演，按此执行）：
- `domain/`：`Player.disconnected_at` 字段；`Room::detachPlayer(pid)`（保留数据标记离线，区别于 `removePlayer`）+ `reattachPlayer`
- `application/`：`SessionService` —— onDisconnected 改调 detach + 宽限定时器（ITimerScheduler）；`reconnect(token)` 校验票据 → 恢复 connIdOf 映射 → cancel 定时器 → reattach → 广播
- `adapters/`：`C2S_Reconnect(token)` / `S2C_ReconnectAck(state)`（消息号顺延）
- **契约面**：token 生成规则、宽限时长（建议 30s）、恢复范围（身份/房间/血量/位置）

**客户端**：
- `ASightlineCharacter`：OnDisconnected 不再清空状态，改"尝试自动重连 N 次"（token 本地存）
- 蓝图：重连 UI（转圈/重连按钮）

**验收**：双开对局中 kill 服务端进程重启（或断网 10s）→ 重连后身份/房间/血量恢复；超宽限期才判负。

### P6：客户端预测与服务器校正

| 项 | 内容 |
|---|---|
| **业务** | 移动手感：200ms RTT 下"按了才动"不可接受；同时是反外挂校验的进化位（架构文档已知限制 #1） |

**服务端**：
- `domain/`：`applyMove` 增加**校验式**规则——速度上限/单帧最大位移/回拉判定（采纳式 → 校验式的既定演进）
- `adapters/`：**契约面变更**——C2S_Move 追加字段：输入序列号（uint32）+ 客户端时间戳；S2C_Move 追加：最后处理序列号
- 契约面登记 + 两端同步

**客户端**：
- `ASightlineCharacter`：移动改为"立即本地应用 + 队列缓存输入"→ 收到服务器广播携带"已处理序列号"→ **回滚重放**（reconciliation）：未确认输入在服务器状态上重放
- 归 C++（算法逻辑），蓝图无感
- 调试：Tab 面板加"客户端/服务器坐标差值"（直观展示校正）

**验收**：模拟 200ms 延迟（工具注入）下移动无回拉感；stat 面板坐标差值 < 阈值；超速移动被服务器拉回。

### P7：KCP 传输层

| 项 | 内容 |
|---|---|
| **业务** | 公网 FPS 的丢包/队头阻塞；证明"传输层可替换"的架构承诺 |

**服务端**：
- `adapters/`：新增 KCP 版 TcpConnection 等价物（传输接口抽象下）；**协议帧格式不变**
- 可靠性分级设计（契约面）：可靠有序（Login/JoinRoom/Fire/Hit/Respawn/GameOver）vs 可丢（Move 快照——旧包不如新包）
- `application/`/`domain/`：零改动

**客户端**：
- `USightlineNetSubsystem`：TCP Socket 换 KCP 端点（UE 侧 KCP 库集成）；拆包逻辑复用
- 蓝图：零改动

**验收**：同机 RTT 不劣化；10% 丢包模拟下射击命中可靠、移动平滑；30 连接冒烟通过。

---

### P8：protobuf 序列化 + 数据驱动武器（Level 3 落地）

| 项 | 内容 |
|---|---|
| **业务** | 协议 schema 单一事实源（两端手写 codec 的漂移风险清零）；武器数量增长后加枪成本归零 |

**服务端**：
- `.proto` 文件定义全部消息 → protoc 生成编解码 → `protocol_codec` 改为薄适配
- `RoomRules` 支持按武器查伤害（**契约面**：武器伤害表进契约——数据驱动后各枪伤害不同）
- 构建脚本接入 protoc 生成步骤

**客户端**：
- protoc 生成 UE 侧代码替换手写 `SightlineProto`（保留语义节点外壳，内部换生成代码）
- 蓝图零改动

**数据驱动武器（Level 3 落地，见演进讨论归档）**：
- `FWeaponDefinition` 结构体收拢现有全部配置槽/资产槽
- `UWeaponDefinitionAsset : UPrimaryDataAsset`——一把枪一个 .uasset
- `ASightlineWeapon::ApplyDefinition(def)` + `ASightlineCharacter::WeaponLoadout[] + EquipByIndex()`
- 蓝图子类退役——加一把枪 = 建一个 DataAsset 填 12 个属性

**验收**：加一把新枪 = 新 DataAsset 资产（零 C++ 零蓝图）；伤害按武器正确结算（服务器判定）。

---

### P9：武器配件系统

| 项 | 内容 |
|---|---|
| **业务** | 武器改装玩法（枪管/弹匣/瞄准镜/枪托） |

**三级递进**（见武器配件讨论归档）：
- Level 0（默认）：配件集成进武器模型——零系统
- Level 1（视觉）：`FWeaponAttachment{SlotName, Mesh}` + 武器骨架插槽 + 挂载逻辑（~10 行 C++）；定义进 `FWeaponDefinition.Attachments[]`
- Level 2（玩法）：配件库 DataAsset + 装配 UI + **服务端数值修正**（`C2S_EquipAttachment` 契约面变更 + Room 规则按配件计算生效值）+ 客户端装配界面

**验收**：Level 2——装配瞄准镜后服务器判定精度规则生效（不可客户端伪造）。

---

### P10：Soak 长跑压测

| 项 | 内容 |
|---|---|
| **业务** | 稳定性硬数据（面试素材）：内存泄漏/句柄泄漏/定时器漂移 |
| **服务端** | 3000 连接 × 1 小时长跑；监控 RSS/fd/ msgs-in-out 曲线；日志轮转验证 |
| **客户端** | 双开挂机 30 分钟无崩溃无内存增长 |
| **验收** | RSS 曲线平稳（无阶梯上涨）；fd 无泄漏；p50 无劣化 |

## 五、阶段间的依赖与并行性

```
P1（蓝图搭建）──┬──► P2（道具）──► P8（数据驱动，道具练兵先行）
                ├──► P3（HUD）
                ├──► P4（夺旗，需 IRoomMode 抽取）
                ├──► P5（断线重连）
                ├──► P6（预测校正）──► P7（KCP，预测后收益最大化）
                └──► P10（soak，任意时点插入）
P8（数据驱动）──► P9（配件，依赖 FWeaponDefinition）
```

- P2/P4 可并行（不同 domain 子模块）；P5/P6 可并行（Session 与 Move 互不干扰）
- P7 必须在 P6 后（预测校正的序列号机制在 KCP 下才有完整意义）
- P8 必须在 P2/P4 后（消息集合稳定后一次切 protobuf，避免反复）
