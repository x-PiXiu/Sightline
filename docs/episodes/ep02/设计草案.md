## 2. 整洁架构映射（依赖规则落地）

### 2.1 服务器四层（同心圆，依赖只向内）

```
┌─ 框架与驱动（不动）──────────────────────────────┐
│ net/*: EventLoop · Acceptor · ClientConnection   │
│   · 帧队列 · 33ms 帧驱动                          │
│  ┌─ 接口适配器（新增/改造）───────────────────┐  │
│  │ MessageDispatcher：msgid→Handler 分发表      │  │
│  │ FrameWriter：领域事件 → 帧 → conn->send      │  │
│  │  ┌─ 用例（新增，纯逻辑）─────────────────┐  │  │
│  │  │ LobbyService：login/create/join/      │  │  │
│  │  │   leave/list —— 不 include 任何 net   │  │  │
│  │  │  ┌─ 实体（新增，纯结构）──────────┐  │  │  │
│  │  │  │ Player{id,name}               │  │  │  │
│  │  │  │ Room{id,name,members,max}     │  │  │  │
│  │  │  └───────────────────────────────┘  │  │  │
│  │  └─────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────┘
```

**核心设计决策（CA 的灵魂一步）：LobbyService 不知道 socket 的存在。**

它的每个方法形如：
```cpp
LoginResult Login(int connFd, const std::string& name);          // 返回结果
std::vector<DomainEvent> Join(int connFd, uint32_t roomId);      // 返回"待通知事件"列表
// DomainEvent = LoginOk{fd,pid} | RoomListChanged{} | MemberJoined{roomId,name} | ...
```

房间变了之后"该通知谁、发什么帧"由**外层的 FrameWriter** 翻译执行。理由与取舍：
- ✓ **内层可脱离网络纯单测**（整洁架构体检第 3 条）：给 LobbyService 喂一串请求，断言一串领域事件，不用起服务器、不碰 socket——测试是架构健康度体检报告
- ✓ 服务器的"业务在尖叫"：打开代码先看到 Room/LobbyService，不是 EventLoop
- ✗ 代价：多一层"领域事件→帧"的转译代码（约几十行，可接受）
- ✗ 代价：DomainEvent 结构体数量随消息增长（用变体/简单 struct 列表可控）

### 2.2 客户端四层

```
┌─ 框架与驱动 ────────────────────────────────┐
│ UMG 三界面（登录/大厅/房间 WBP）· Socket     │
│  ┌─ 接口适配器 ─────────────────────────┐  │
│  │ WBP：BindUObject 到 Session 委托刷 UI； │  │
│  │   按钮 onClick → 调 Session 意图接口    │  │
│  │ FSightlineConnection（现有，原样）      │  │
│  │  ┌─ 用例（新增 UObject）─────────────┐  │  │
│  │  │ ULobbySession：                   │  │  │
│  │  │  意图接口 Login/CreateRoom/       │  │  │
│  │  │    JoinRoom/LeaveRoom（只发包）    │  │  │
│  │  │  收帧解析 → 更新 Model → 广播委托   │  │  │
│  │  │  ┌─ 实体（纯数据）─────────────┐  │  │  │
│  │  │  │ FLobbyModel：bLoggedIn/     │  │  │  │
│  │  │  │  PlayerId/房间列表/当前房间   │  │  │  │
│  │  │  └────────────────────────────┘  │  │  │
│  │  └──────────────────────────────────┘  │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

- **意图接口只发包，不碰 UI**（"客户端只发意图"军令状的代码化）：`Login(name)` 内部就是打包 `MSG_C2S_LOGIN` 调 `Connection->Send`，无任何界面逻辑
- **状态更新走委托**：Session 收到 S2C 帧 → 更新 FLobbyModel → `OnRoomListChanged.Broadcast()`；WBP 用 `BindUObject` 订阅——**UMG 与 Connection 互相不知道对方存在**（依赖都指向 Session）
- GameInstance 职责不变（连接生死/心跳/LAG），仅加一行"OnFrame 转发给 LobbySession"——不把大厅逻辑塞进 GI 防上帝类
- 取舍：比"WBP 直连 GameInstance"多一层中转，换来 UI 可整体替换（第 14 期界面动画化时逻辑零改动）+ 会话层可 mock 单测

### 2.3 依赖规则自检（整洁架构体检四问）

1. 换序列化格式（二进制→JSON），LobbyService/FLobbyModel 要改吗？——**不改**（编解码在适配器/协议层）
2. 换 UI（UMG→整套重做），Session 逻辑要改吗？——**不改**（WBP 只是订阅者）
3. 能否脱离网络测房间规则（重名拒绝/满员拒绝/列表快照）？——**能**（LobbyService 纯单测，tests/ 新增）
4. 加新消息（第 3 期同步消息），要动分发表以外的旧代码吗？——**不用**（map<msgid,handler> 注册制，开闭）

## 3. 契约 v2（先改文档，再动代码——第 1 期规矩的第一次真实执行）

MSG_IDS.md v1→v2：**1~3 不动，只增不改**（向后兼容铁律：老客户端面对新服务器照常心跳）。全部小端。

| msgid | 名称 | 方向 | 字节布局 | 触发/推送时机 |
|-------|------|------|----------|---------------|
| 4 | `MSG_C2S_LOGIN` | C→S | `[1B 名长 n][nB UTF-8 名字]` | 连接建立后第一个业务帧 |
| 5 | `MSG_S2C_LOGIN_RESULT` | S→C | `[1B 结果码][4B PlayerId]` | 0=成功 / 1=重名拒绝 / 2=名字非法（空/超长） |
| 6 | `MSG_C2S_CREATE_ROOM` | C→S | `[1B 名长 m][mB UTF-8 房间名]` | 需已登录、不在房中 |
| 7 | `MSG_S2C_CREATE_RESULT` | S→C | `[1B 结果码][4B RoomId]` | 0=成功 / 1=未登录 / 2=已在房间 |
| 8 | `MSG_C2S_JOIN_ROOM` | C→S | `[4B RoomId]` | 需已登录、不在房中 |
| 9 | `MSG_S2C_JOIN_RESULT` | S→C | `[1B 结果码][4B RoomId][1B 人数]` | 0=成功 / 1=未登录 / 2=房间不存在 / 3=已满 / 4=已在房间 |
| 10 | `MSG_C2S_LEAVE_ROOM` | C→S | 空 payload | 需在房中 |
| 11 | `MSG_S2C_ROOM_LIST` | S→C | `[2B 房间数 N]{[4B RoomId][1B 人数][1B 房间名长][房间名][1B 房主名长][房主名]}×N` | **推送**：登录成功后先发一次全量；此后每次房间增减/人数变化向所有"已登录未进房"连接推全量快照 |
| 12 | `MSG_S2C_ROOM_STATE` | S→C | `[4B RoomId][1B 房主名长 h][hB 房主名][1B 人数 n]{[1B 名长][名字]}×n` | **推送**：房间成员变化时发给房内所有人；房主显式字段，房主离开自动转移给最早加入者 |
| 13 | `MSG_S2C_KICKED` | S→C | `[1B 原因码]` | 1=顶号（同名新登录挤掉旧连接）/ 2=登录超时 / 3=服务器关闭。**随后服务器主动断开** |

**会话规则**（已登记进 MSG_IDS.md v2 契约正文）：
- 登录前宽限期：连接建立 10s 内未发合法 LOGIN → `KICKED(2)` 断开（防裸连接堆积）
- 顶号：同名字第二次登录成功 → 旧连接收 `KICKED(1)` 断开（"一个账号一处在线"）
- 心跳契约不动：LAG/重连照旧；**重连后必须重新 LOGIN**（会话不跨连接保活——取舍见 7.6）
- 房主规则：建房者首任房主；房主离开/断线 → 转移给剩余成员中**最早加入者**；本期房主无特殊权限（第 3 期"开始对局"预留）
- 优雅关闭：服务器收关闭信号 → 向所有在线连接广播 `KICKED(3 服务器关闭)` 后退出

## 4. 状态机（drawio 定稿后入库）

- **服务器侧连接会话**：`Connected（未登录，10s 宽限）→ LoggedIn → InRoom{Waiting<4 | Full=4}`；断开/KICKED → 回收
- **房间**：`Waiting(<4 人) ⇄ Full(=4 人)`；解散条件 = 人数归 0。**房主 = 剩余成员中最早加入者**（建房者首任；房主离开/断线自动转移；本期无特殊权限，第 3 期"开始对局"预留）
- **客户端 UI**：`登录界面 → 大厅 ⇄ 房间界面`；任意状态断线/KICKED → 回登录界面并弹原因

## 5. 权威规则表（"服务器说了算"逐字段落地）

| 数据/事件 | 权威方 | 客户端行为 | 同步方式 |
|-----------|--------|------------|----------|
| 房间列表与人数 | 服务器 | 只展示，不发"刷新请求" | 变更时全量快照推送（11） |
| 房间成员名单 | 服务器 | 只展示 | 变更时推送（12） |
| 进房成功与否 | 服务器（满员/不存在校验） | 发意图后**等回执**再切界面，绝不本地乐观切 | 请求-回执（9） |
| PlayerId | 服务器分配（自增） | 保存并随帧回传场景预留 | 登录回执（5） |
| 名字唯一性 | 服务器查重 | 重名被拒则提示改名 | 登录回执（5） |
| 房主归属 | 服务器按加入顺序指定 | 本地仅标记展示 | 变更随 ROOM_STATE 推送（12） |

**"实时刷新"的实现选型：推送而非轮询**——服务器在房间数据变化的同一帧驱动 tick 内组装快照、遍历订阅者发送。代价：服务器维护"已登录未进房"订阅者集合（单线程下就是一个遍历，零成本）；收益：客户端零轮询、列表即时（B 建房 A 的列表同帧更新）。

## 6. 关键时序：A 建房、B 进房（验收脚本原型）

```
A: connect → WELCOME ← ────────────────┐
A: LOGIN("alpha") → LOGIN_RESULT(0, pid=1)
A: 收 ROOM_LIST(空)                     │ 两连接互不相干，各自心跳照旧（契约 2/3 不变）
B: connect → WELCOME ← ────────────────┘
B: LOGIN("beta")  → LOGIN_RESULT(0, pid=2)
A: CREATE_ROOM("第一房") → CREATE_RESULT(0, roomId=1)
A: ← ROOM_STATE(1, 房主=alpha, [alpha])              （A 在房内：收状态）
B: ← ROOM_LIST[{1,"第一房",1人,alpha}]               （B 在大厅：列表实时刷新）
B: JOIN_ROOM(1) → JOIN_RESULT(0, 1, 2人)
A: ← ROOM_STATE(1, 房主=alpha, 2人, [alpha,beta])   （房内推送：A 看到 B 进来了）
B: ← ROOM_STATE(1, 房主=alpha, 2人, [alpha,beta])
A: LEAVE_ROOM → 房主转移给最早加入的 beta
B: ← ROOM_STATE(1, 房主=beta, 1人, [beta])          （B 看到"我成了房主"）
A: ← ROOM_LIST[{1,1人,beta}]                        （A 回大厅，列表房主已更新）
B: LEAVE_ROOM → 房间人数归 0 → 解散 → B 收 ROOM_LIST(空)
```
