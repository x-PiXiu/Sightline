## 四、Pinned Worker 分桶设计 vs 整洁架构（复检）

### 4.1 判定符合的（设计里已做对的）

| 设计决策 | 整洁架构依据 |
|---|---|
| 跨线程只传 `MatchInput`/`MatchEvent` **纯数据**（零指针零引用） | §7.6-A 判定树第 4 条：跨边界传输 DTO——线程边界与源码边界同理，**数据过界必须值语义** |
| `MatchSession` 对"被哪个线程 Tick"无感（依赖注入 Deps，成员全私有） | 依赖倒置：Session 只依赖注入端口；worker 池是外层细节，**实体/用例层零感知并发** |
| `ITickDispatcher` 接口（Serial/Worker 可插拔） | §7.6-C 推迟决策：dispatcher 是机制不是策略，接口归用例层所有 |
| LuaRuntime per-worker、persistence 双队列复用、网络线程零改动 | 变化速率隔离：并发化只动装配层与 wiring 最后一跳 |
| 主线程保留 Lobby/Config/命令口 | §五"边界有成本"：不为并发而并发——单线程语义足够的地方不画新边界 |

### 4.2 架构评审四问（§7.6-D）

| 问 | 评 |
|---|---|
| 开发：可并行开发吗 | ✅ Session/Registry/worker 池/账号域四条线可并行（接口先立） |
| 部署：能简单部署吗 | ✅ 单二进制，worker 数是配置项；Serial 模式=同二进制退化运行 |
| 运行：性能是硬约束绑架架构吗 | ⚠️ **部分是**——"错相 8ms""Mailbox 4096"是拍脑袋数字，必须由压测定档（→ G7/G11 附带）；但架构未因性能提前焊死选型（dispatcher 可插拔），判定通过 |
| 维护：改动局部吗 | ✅ 逐文件改动清单已列（前文 §五），改动集中在 wiring/装配层 |

**四问通过，但并发给整洁架构带来一类全新问题——§7.6 判定树是按"import 方向"设计的，线程安全是它没覆盖的维度。以下缺口全部源于此：**

## 五、设计缺口清单（★核心章节·11 项）

> 每项：现象 → 风险 → 处置。P0=必须在设计草案定稿前解决，P1=实现期解决，P2=记录为已知边界。

### G1 幽灵输入：换房/退房窗口期的在途消息（P0·并发新增）

**现象**：玩家 A 的 19 号上报在 worker#0 的 inbox 排队；此刻他在大厅退出/换房（主线程改 Lobby）。worker 下拍执行这条输入时，**校验依据已经过期**——roomId 是旧的，pid 可能已复用。

**风险**：把输入应用到错误/已销毁的 session；pid 复用时**替别人移动**——竞态正确性事故。

**处置**：① `MatchInput` 增加 `epoch` 字段（玩家加入房间时分配的单调序号，Lobby 维护）；worker 执行前 `session` 内校验 `pid+epoch` 匹配，不匹配静默丢+计数。② 退房消息 `RemovePlayer` 与数据消息**同 FIFO 保序**（控制面插队头仅限 OpenRoom/Patch——RemovePlayer 不插队，否则退房后仍会执行一条在途开火）。二选一不够就都做（成本低）。

### G2 pendingClose 与 OpenRoom 的幂等竞态（P0）

**现象**：A 房 Ended → 2s 结算背景期（session 还在，标记 pendingClose_）；玩家此刻重开同 roomId → OpenRoom 投递到 shard → 现设计"已存在=幂等返回" → **新开局拿到的是旧局尸体**。

**处置**：OpenRoom 的幂等判定必须含状态机：`不存在 → 新建；存在且活跃 → 幂等返回；存在且 pendingClose → 视作不存在，创建新 session（旧的下拍收割时跳过——用 unique_ptr 替换而非复用）`。worker 单线程内处理这两条消息天然串行，无需加锁——**写在 Shard 的状态注释里当契约**。

### G3 LobbyService 并发读热点（P0）

**现象**：多 worker 后，`lobby.RoomIdByPid(pid)` 被所有 worker 的输入路由调用（估算 32 人 × 30Hz × 2 条 ≈ 2000 q/s），而 Lobby 留在主线程——**两个选择都不对**：worker 跨线程调 Lobby（锁/竞争）或把 Lobby 拆进每 worker（三份真相漂移）。

**处置**：**immutable snapshot + atomic 指针**——复用 ConfigService 的成熟手法（ep08 已实证）：房间成员表变更（进房/退房/开局）频率极低（<1/s），每次变更主线程构建新不可变快照原子换指针；worker 读快照零锁。**这是 G1 epoch 字段的数据源**（epoch 在快照里）。

### G4 错相 Tick 的配置版本撕裂（P1）

**现象**：worker#0 在 8ms 偏移处 Tick 用 v1，worker#1 在 16ms 处用 v2（reload 恰在中间落地）——**同一"帧"内不同房按不同配置判定**。单线程时代一帧内全服同版本，这个毛刺是新引入的。

**风险**：低（毫秒级窗口）；但审计对账会出现"30 号已广播 v2、某房最后两发按 v1 判"的记录间隙——对账叙事被自己打脸。

**处置**：①接受毛刺，但**判定日志与审计行必须带实际使用的 config version**（MatchEvent 加 version 字段——顺手把 ep08"判定回包带版本"的审计链补全）；②reload 命令口回执文案注明"各房最迟 N ms 内全部生效"（N=错相总偏移+1 拍）。不做同步屏障（为毛刺上屏障=过度设计）。

### G5 patch 的跨线程回执聚合（P0）

**现象**：patch 广播到 N 份 VM，每份回投 `PatchResult` 事件——nc 同窗回执等谁？等不全怎么办？N 份里一份成功一份失败呢？

**处置**：主线程聚合器（用例层小对象）：收到 patch 请求 → 记 `pending[nid]=N`；每份 PatchResult 递减；**归零或超时（500ms）时收口**：全成功 → 成功回执+审计；任一失败 → **整体失败回执**（已成功的 worker 执行回退 patch——**回退消息同样广播 N 份**，全部回退后收口）。聚合器状态只有主线程碰，无并发。这是 ep08"命令口同窗回执"在并发下的完整化。

### G6 worker 线程崩溃的爆炸半径（P1）

**现象**：C++ 线程未捕获异常 = `std::terminate` = **全进程死**——一局的 bug 杀死全服所有房。单线程时代"一局崩=全服崩"至少语义一致；分桶后用户预期是"隔离"，实际不是。

**处置**：worker loop 顶层 `try/catch(...)`：捕获后①将异常房标记 pendingClose（关房+Ended(fault) 事件+审计）②其余房继续跑③横幅可见"房间 fault 关闭"。**不承诺捕获段错误（SIGSEGV 仍进程死）**——那是 ep12+ 哨兵进程/多进程隔离的事，设计草案写明边界。

### G7 outbox 合流背压（P1）

**现象**：合流区设计里未定义上界——worker 产事件速率 > 主线程 drain 速率（Fanout 堵）时无界堆积 → 内存爬升+事件延迟无限涨。

**处置**：合流区有界（建议 8192 事件，压测定档）：满时**丢游戏表现类事件**（快照可丢——下一拍就是新的；**不可丢**：Ended/MatchStart/Kill 审计类——这类改走 persistence 直投队列绕过合流区）。丢弃计数+横幅。**快照与审计事件分两条通道**是这个缺口的真正答案——ep08 的 durability_policy（Must/BestEffort 分级）本来就是为此设计的，**复用而非新造**。

### G8 persistence 并发入队的丢弃计数（P2·小）

**现象**：多 worker 并发入队，统计队列（有界 1024）"满→丢"的判定与计数在 mutex 内——行为正确，但丢弃计数要原子聚合，横幅读数才不错。

**处置**：`std::atomic<uint64_t>` 计数器，一行实现，写进 durability_policy 的测试断言。

### G9 战绩查询（34 号）的阻塞 IO——账号域自身的缺口（P0·ep09 新功能）

**现象**：ep09 账号域设计中 34/35 号（战绩查询/回执）若在主线程 handler 直查 MySQL——**同步阻塞 IO 进主循环**，卡全局（违反 A1 纪律的翻版：网络线程零阻塞 IO 的教训在"查询线程"重演）。

**处置**：查询请求投递 persistence worker（既有双队列加一条"查询队列"或复用审计队列旁路）→ worker 查库 → 结果作为事件回流 → 主线程 Fanout 35 号回执。**注册/登录同理**（PBKDF2 计算虽然 CPU 级 ms，也一并投 worker——主线程零重活）。写进契约 v4.9：**34/35 的时序是异步的**（客户端要按"请求-稍后回执"建模，不能同步等）。

### G10 GI 消息路由注册表化（P1·客户端）

**现象**：见 §三 C1——switch 白名单在 31~35 号引入时的漏路由风险复现率高（已有一次实锤）。

**处置**：`TMap<int32, FHandlerDelegate>` 注册表 + 启动自检（注册表键集 vs 契约常量表比对，缺=启动即 Fail 带日志）。这是**把 ep08 的血泪教训制度化**，成本半天。

### G11 停机序的可验证性（P1）

**现象**：停机顺序（running=false → 停收 → drain inbox → 末拍 → join → 冲尾包 → persistence flush）写对了没有测试保护——顺序反了丢事件，而停机 bug 只在真实部署暴露。

**处置**：停机做成 **DeterministicTestable**——Shard/worker 的 drain/join 拆成可单独调用的阶段函数；单测按"注入 N 条输入→只跑 drain→断言 inbox 空→跑末拍→断言 outbox 空→才允许 join"逐步断言。**停机序从注释升级为被测试锁定的契约**。

## 六、修订后的设计决策（缺口 → ADR）

| ADR | 决策 | 对应缺口 |
|---|---|---|
| ADR-9 | 跨线程通信仅传值语义 DTO（MatchInput/MatchEvent），禁止指针/引用过界 | §四复检 |
| ADR-10 | 房间成员表读路径 = immutable snapshot + atomic 换指针（复用 ConfigService 手法）；epoch 字段随快照分发 | G1/G3 |
| ADR-11 | Session 生命周期消息（Open/Close）只在归属 worker 执行；OpenRoom 幂等含 pendingClose 分支 | G2 |
| ADR-12 | 配置判定审计带实际版本号；reload 回执声明最终一致窗口 | G4 |
| ADR-13 | patch/回退 = 主线程聚合器两阶段收口（500ms 超时） | G5 |
| ADR-14 | worker catch-all → fault 关房，进程不连坐；SIGSEGV 级隔离留给多进程期（ep12+） | G6 |
| ADR-15 | 事件双通道：合流区（可丢·表现类，有界）+ persistence 直投（Must·审计类）——复用 durability 分级 | G7/G8 |
| ADR-16 | 账号域全异步：注册/登录/查询投 persistence worker，回执事件回流；34/35 时序=请求-稍后回执 | G9 |
| ADR-17 | 客户端 GI 路由注册表化+启动自检；服务端 match_wiring 同款检查 | G10 |
| ADR-18 | 停机序阶段函数化+单测锁定 | G11 |

**对工期的影响**：缺口处置 ≈ +1 天（epoch+快照 0.5 / patch 聚合 0.25 / 注册表化 0.5 中客户端半天单列 / 其余并入既有件）→ **ep09 总预算 7~7.5 天**。

## 八、结论

1. **现状**：服务端四层依赖方向干净、体检四问全过——八期分层纪律是这次并发化的本金；客户端唯一结构性风险是 GI 白名单（已有实锤史）。
2. **分桶设计**：方向符合整洁架构（跨线程传值语义/Session 无感/dispatcher 可插拔），四问通过。
