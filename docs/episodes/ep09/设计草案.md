**依赖规则不变**：worker 池/Mailbox 是适配器细节，用例层只见 `ITickDispatcher` 端口；实体层对并发**零感知**（它的线程安全由调用纪律保证——每 session 同一时刻至多一个线程触碰，ADR-9）。

**域事件地图（E14·防"单总线"误读）**：系统内有**三条域事件流，每域内部各自漏斗**（单一汇流+单一分拣），域与域不交叉：

| 域 | 生产者 | 汇流点 | 消费者 |
|---|---|---|---|
| 对局域 MatchEvent | worker 各 session+bot | 合流区→主线程 | Fanout（按房）/persistence 直投 |
| 配置域 ConfigChanged | ConfigService（主线程） | OnConfigChanged | 审计+30 号广播（ep08 G4 纪律：不混进对局域） |
| 账号域 AccountResult | persistence worker（ep09 新增） | **直投队列→主线程（不经合流区·Must 保序）** | Fanout（按发起 fd，§5.4） |

域分流的依据=**变化速率与消费方不同**（§五"边界有成本"）——三域各自可对拍、可审计、可演进，互不绑架。

## 4. 多房分桶架构章

### 4.1 线程拓扑与职责重划

| 现在跑在主线程的活 | 终态归属 | 依据 |
|---|---|---|
| 19/20/28/29 号消费→直调 MatchService | 主线程**只路由**（fd→pid→roomId→投 inbox），执行在 worker | 主线程绝不碰 session 指针 |
| MatchService::Tick | **worker**（本桶房） | 对局热路径 |
| BotDriver 决策 | **worker**（本桶 bot，本地闭环进 inbox） | bot 归属房→归属 worker |
| LobbyService Tick / ConfigService reload / 命令口 Dispatch / 事件合流+Fanout | **主线程保留** | 低频/全局单例/原子换表已就绪（§五"边界有成本"：不为其并发而并发） |
| persistence 入队 | **worker 直接入队**（队列 mutex 化） | 同房事件在 worker 内保序=审计序 ✓ |

### 4.2 MatchSession（一局=一个对象·ADR 同 §4.2 校验报告）

`MatchService` → `MatchSession`：**成员零改**（roomId_/entities_/weaponTable_/bActive_/bEnded_/快照停摆/重生环——本就是单局粒度），两件手术：

struct MatchSession::Deps {            // 共享依赖打包（构造注入）

    const MapGeometry*  geometry;         // 只读共享
    const IConfigView*  config;           // 配置视图（atomic 快照，跨线程读已就绪）

**接口规范（ADR-24）**：MatchSession 公开面 = 「输入方法返回事件流 + Tick 产出周期事件 + 纯查询（IsEnded/bPendingClose）」三类——**禁止 bool 返回的输入方法**（调用方丢事件=静默吞业务时序）。

- Session **不知道** Registry/worker 的存在（依赖向内，无环）。

### 4.3 MatchShards（桶容器+绑定·ADR-11）

```cpp
class MatchShards {
public:
    void OpenRoom(std::uint32_t roomId, std::vector<RosterEntry> roster) {
        shardOf(roomId).pushCommand({ShardCommand::OpenRoom, roomId, serialize(roster)}); // 控制面队列
    }
    void CloseRoom(std::uint32_t roomId);          // 投递，worker 自己删（所有权不跨线程）
    Shard& shardOf(std::uint32_t roomId) const { return *shards_[roomId % workers_]; }
private:
    std::vector<std::unique_ptr<Shard>> shards_;   // N=4（配置项 kWorkerCount，压测定档）
};
struct Shard {
    std::unordered_map<std::uint32_t, std::unique_ptr<MatchSession>> rooms;
    std::deque<MatchInput>   dataQ;                // 数据面（§4.4）
    std::deque<ShardCommand> cmdQ;                 // 控制面（先于数据面 drain）
    std::mutex               qMutex;               // dataQ/cmdQ 共用一把（同临界区，无嵌套锁）
    std::vector<MatchEvent>  outbox;               // outbox_mutex 保护（临界区纳秒级）
    std::unique_ptr<LuaRuntime> lua;               // per-worker VM（§4.7）
    std::atomic<std::uint64_t> dropCount{0};       // G8：入队丢弃原子计数
};
```

**绑定规则**：`roomId % N` 开房时定死、生命周期内不迁移 ⇒ 房内单线程语义 + 无迁移协议。**worker 数运行时不变**（改配置需重启——写明为已知边界）。

### 4.4 跨线程 DTO（E4：按语义拆两类）与 Mailbox（E5：epoch 过滤在适配器层）

```cpp
// ① MatchInput —— 对局输入（数据面·走 FIFO 保序）
struct MatchInput {
    enum class Kind : std::uint8_t { Move, Fire, Reload, SwitchWeapon, RemovePlayer };
    Kind kind;  std::uint32_t roomId, pid;
    std::uint32_t epoch;                  // ★G1：Lobby 进房时分配；过滤在 worker drain 层（下述）
    std::uint64_t atMs;                   // judgeAt 语义保留
    float x, y, z, yaw, pitch;  std::uint8_t wid;
};
// ② ShardCommand —— 生命周期控制（控制面·走独立命令队列，天然先于数据面）
struct ShardCommand {
    enum class Kind : std::uint8_t { OpenRoom, CloseRoom, Patch };
    Kind kind;  std::uint32_t roomId;
    std::string source;                   // Patch 的 lua 源码 / OpenRoom 的 roster 序列化——move 传递
};
```

**拆分依据（E4）**：两类消息的背压策略、保序要求、处理时机完全不同——混装一个 DTO 会让字段语义含糊（x/y/z 对 OpenRoom 无意义）且背压规则复杂化。`RemovePlayer` 留在 MatchInput（数据面 FIFO——G1 配套：与数据同序，防"退房后仍执行在途开火"）。**实现期批注（二轮校验 R2-A）**：`ShardCommand` 的 roster 直携 `std::vector<RosterEntry>`（值语义 move），不序列化成 string——序列化是 wire 层的活，跨线程 DTO 传结构化值。

**Mailbox（per Shard）**：`std::deque<MatchInput> dataQ`（有界 4096）+ `std::deque<ShardCommand> cmdQ`（有界 128，独立队列=控制面优先的干净实现）+ `outbox_mutex`：

| 队列 | 背压策略 |
|---|---|
| `dataQ` | `Move` **newest-wins**（同 (pid,roomId) 新覆盖旧）；`Fire/Reload/SwitchWeapon/RemovePlayer` 不丢——满则丢计数+横幅 |
| `cmdQ` | 不丢；满=系统异常（控制面频率 <1/s），横幅+审计 |

**epoch 过滤在适配器层（E5·修正 v1.0）**：worker drain 时对照最新 Lobby 快照（§4.8）做纯函数过滤——`快照里 (pid→roomId,epoch) 与输入不符 → 丢+dropCount`。**session 完全无感 epoch**（用例层保持"只认本房 roster"的干净语义）——若校验放 session 内，Lobby 概念会渗入用例层（依赖方向违规）。

### 4.5 Worker event loop（ITickDispatcher 的 Worker 实现·v1.1 修正 E2/E3/E10）

```cpp
void WorkerLoop(Shard& me, std::atomic<bool>& running, std::uint32_t idx) {
    const auto phase = std::chrono::milliseconds(idx * 8);   // ★错相 8ms（压测定档）
    auto nextTickMs = clock::now_ms();
    while (running) {
        try {
            // ① 控制面优先：drain cmdQ（OpenRoom 先于一切数据——含 pendingClose 幂等判定 §4.9）
            drainCommands(me);
            // ② 数据面：drain dataQ（epoch 过滤在此层做——E5，对照最新快照；session 无感）
            drainInputs(me);
            // ③ Tick 本桶（玩家输入已生效）——纯遍历，禁止循环内 erase（E2）
            for (auto& [rid, session] : me.rooms)
                appendOutbox(me, session->Tick(nextTickMs));      // ADR-1：钟由 loop 给
            // ④ bot 本桶直调（E3：与 session 同线程不绕 Mailbox——看到 Tick 后最新世界，
            //    决策直调 session.UpdateEntity，零一拍假延迟；bot 是服务器权威实体，免 epoch）
            appendOutbox(me, botDriver.LocalTick(me, nextTickMs));
            // ⑤ 收割与遍历分离（E2）：Tick 轮结束后统一 erase——range-for 中删除=UB
            reapPendingRooms(me);
            // ⑥ 出向：outbox 冲刷合流 + Must 类直投 persistence（§4.6）
            flushOutboxToMerge(me);
            persistDirect(me);
        } catch (...) { faultClose(me, idx); }                    // G6：关房不连坐（SIGSEGV 除外）
        sleep_until_30Hz(nextTickMs += 33, phase);
    }
}
```

**faultClose 规范（v1.2 裁决·核对项 2）**——`noexcept`，四条纪律：

1. **不碰 session**：异常后 session 状态不可信——fault Ended 事件由 **worker 侧构造**（roomId/fault 原因/时戳），不从 session 取任何数据
2. 动作集：房标记 pendingClose(fault) + outbox 追加 fault Ended + 横幅计数——全部不抛操作；审计等次要动作内层 `try/catch(...) swallow`（失败不 terminate）
3. **半轮事件合法**：Tick 中途抛异常时，outbox 里已 push 的事件是完整构造的（每条 push 前完成构造）——客户端收"部分快照 → Ended(fault)"=掉线语义，可接受；**对拍对 fault 房豁免**（异常路径不保证确定性，§6.1 分片规则附注）
4. 审计走 persistence 直投（Must）——fault 也是审计事件，一条不丢

- **错相**：4 worker 峰谷错开，CPU 平滑；各房仍 30Hz，客户端无感。
- **快照节拍**：所有 worker 的 tickPhase 推自同一 steady_clock——快照时间戳语义一致（ADR-1 延伸）。
- **主循环节拍与合流时机（E10·v1.2 裁决·核对项 3）**：主循环由 epoll 唤醒驱动（非 30Hz 对齐轮询），`epoll_wait timeout = kMainLoopMaxLatency = 5ms`（**配置常量**，压测可在 1~5ms 调档）——空闲圈=超时唤醒零自旋；**合流延迟上限 5ms+ε**（错相 8ms 的事件下一圈必被合流），p99 归因表"合流等待"分量 ≤5ms。依据：33ms 帧间隔的 15%，客户端无感；空转成本与延迟的折中由压测定档。

### 4.6 事件双通道与合流（G7/G8·ADR-15——复用 durability 分级，不新造）

| 通道 | 内容 | 上界 | 满时 |
|---|---|---|---|
| **合流区**（worker outbox → 主线程 DrainAllOutboxes → Fanout） | 表现类：17 快照/开火/掉血/换枪 | 有界 8192（压测定档） | 丢**快照**（下一拍即新）+计数横幅；其余堵入队 |
| **persistence 直投**（worker → 双队列，绕过合流区） | Must 类：Ended/Kill 审计/ConfigChanged | 既有双队列纪律 | 审计落 WAL（ep08 已实证） |

- `persistence` 双队列入队端 mutex 化；丢弃计数 `std::atomic` 聚合（G8）。
- **消费调度优先级（E6·ep09 新增）**：账号队列是**交互式请求**（用户在等 33/35 回执），审计/统计是批量——worker 消费循环改为**交互优先+批量限流**：每轮先清空账号队列（非阻塞），再消费审计 ≤K 条（防账号洪流饿死 WAL 回放），最后统计。K=64（压测定档）。ep08 双队列无此问题（皆非交互），ep09 必须定，否则登录体验随审计积压崩。
- 合流后 Fanout **零改动**：`e.roomId → lobby_wiring.RoomMemberFds → 逐 fd 投发送队列`（per-fd 队列天然隔离）。

### 4.7 LuaRuntime per-worker（最大深水区）

- **现状雷点**：`lua_State` 非线程安全，多 worker 并发调公式/决策=崩。
- **方案**：`LuaVmFactory` 每 worker 建一份 VM（lua_newstate+计数分配器 32MB+沙箱摘 os/io+加载 damage.lua/bot_ai.lua+ref 注册+bot_brain 五件常量桥注入）→ `Shard.lua` 独占。内存 ≈4×几 MB，可忽略。
- **patch 闭环（G5·ADR-13）**：主线程收 patch → N 份 `{Patch, source}` 投各 inbox 队头 → worker 下一拍"编译+出口校验+换 ref" → 各回投 `PatchResult{ok}` → **主线程聚合器**：`pending=N` 递减，**归零或 500ms 超时收口**——全成功=成功回执+审计；任一失败=**整体失败**：广播回退 patch（N 份），全部回退后失败回执。聚合器仅主线程碰，无并发。
- `fire_judge`/`bot_brain` 接口签名零改——拿到的 VM 引用从"全局那份"变"本 worker 那份"。

### 4.8 Lobby 快照 + epoch（G1/G3·ADR-10）

- **读热点**：`RoomIdByPid` ≈2000 q/s 全 worker 共享——worker **不跨线程调 Lobby**，也不各自持副本（三份真相漂移）。
- **方案**：**immutable snapshot + atomic 换指针**（复用 ConfigService 成熟手法）：

```cpp
struct LobbySnapshot {                      // 不可变·主线程构建
    std::unordered_map<std::uint32_t, std::pair<std::uint32_t, std::uint32_t>> pidRoomEpoch;
    // pid → (roomId, epoch)
    std::vector<std::uint32_t> activeRooms;
};
std::shared_ptr<const LobbySnapshot> snap_;  // std::atomic<std::shared_ptr> 换指针
```

- 变更（进房/退房/开局/关房）频率 <1/s：主线程构建新快照原子换指针；worker 路由时 `atomic_load` 取快照零锁读。
- **epoch 规则**：玩家每次进房 `epoch++`；`MatchInput.epoch` 与快照不符=在途过期消息，丢。
- **一致性回写**：`RoomClosed` 事件回流驱动 `lobby.SetRoomInMatch(false)`（D3 通道）——**主线程禁止直查 shard 内部**（Lobby 与 shard 的一致性只靠事件流，防"Lobby 说在局、session 已亡"的永久卡死）。

### 4.9 生命周期

| 场景 | 流程 |
|---|---|
| **开房** | 大厅 START_MATCH（主线程）→ `shards.OpenRoom(roomId, roster)` 投递 → worker 建 session（幂等：见下）→ 回投 `MatchStart` → 合流 → 主线程 OnWiringEvents：15 号先出→30 号随后（D4 时序纪律在合流后保持） |
| **幂等（G2·ADR-11）** | OpenRoom 执行时：不存在→新建；活跃→幂等返回现有；**pendingClose→视作不存在，新建 session 替换**（旧的下一拍收割跳过——unique_ptr 替换不复用）。此三分支写进 Shard 状态注释当契约 |
| **结算** | Ended 事件 → 25 号广播+落库（直投通道）→ session 置 pendingClose（2s 背景期供客户端收尾画面）→ worker 收割 → `RoomClosed` 回流 → Lobby 回写 |
| **结算背景期行为契约（E8）** | pendingClose 的 session：①快照**继续发**（客户端收尾画面）②**输入全丢**（drain 层按 pendingClose 拒——开火/移动不生效）③结算类事件静默（比分冻结）④重生环停转⑤34/35 账号域查询**不受影响**（与房无关）。不定义此契约，单房时代靠"房要没了没人管"蒙混，多房下它是 pendingClose 语义的核心 |
| **断线** | 不清房（实体保留、对局继续）——ep12 会话票据地基 |
| **停机（G11·ADR-18）** | 阶段函数化：`StopIngest() → DrainAllInboxes() → FinalTick() → JoinWorkers() → FlushMerge() → persist.Shutdown()`——每阶段可独立调用+单测逐步断言（§6.4），顺序反了丢事件从注释升级为被测试锁定的契约 |

### 4.10 同步语义（客户端零改动的合同）

- **17 号 payload 语义不变**："你这局所有人的状态"。A 房客户端收到的数组=它的全世界，**客户端不需要知道"房"概念**——协议层保证：17/19/20/21/25 等房级消息 payload 不加任何字段（契约 v4.9 只增 31~35，见 §5）。
- **事件分类**：房级事件（17/19/20/15/18/21/25——仅本房成员）vs 服务器级事件（30 配置版本/26 房间列表——全体连接）。30 号跨房是既有实现，多房后语义不变（全体共享同一张表）。
- **节律**：v1 全量轮转同帧同拍（所有 worker 30Hz）；客户端插值（ep04 25ms 滑窗）零改动。
- **配置版本审计（G4·E12 边界注记）**：`MatchEvent` **内存结构**加 `configVersion` 字段（判定日志/审计行带实际使用版本，对账撕裂窗口 ≤错相+1 拍可量化）——**wire payload 零改动**（17 号合同不破）。reload 命令回执注明"各房最迟 N ms 内全部生效"。

### 4.11 ITickDispatcher（可插拔·推迟决策）

```cpp
struct ITickDispatcher {                                   // 用例层端口
    virtual ~ITickDispatcher() = default;
    virtual void Start(ShardView) = 0;  virtual void Stop() = 0;
    virtual bool Running() const = 0;
};
// SerialDispatcher：主线程顺序消费全部 shard（v0 兼容/测试/降级开关——编译期选择）
// PinnedWorkerDispatcher：本草案主体
```

- **可退开关是生产纪律不是偷懒**：worker 版异常可切 Serial 保发布节奏；**双模式事件流对拍**（§6.2）正是两版共存的价值。
- Serial 模式下 Mailbox/双通道照跑（数据通路同一套，只是消费线程=1）——**保证对拍输入同构**。

## 5. 契约 v4.9 账号域章

### 5.1 五消息 wire 定义（MSG_IDS v4.8 → v4.9 增补 31~35）

| 号 | 方向 | payload | 说明 |
|---|---|---|---|
| **31 CRegister** | C→S | `accountLen(1) account(≤24B utf8) passLen(1) pass(≤64B)` | 传输侧明文——**TLS 缺口标注 ep12 收口**（服务端即哈希，不留存明文） |
| **32 CLogin** | C→S | `accountLen(1) account(≤24B) passLen(1) pass(≤64B)` | 同上 |
| **33 SAuthResult** | S→C | `ok(1) reason(1) accountId(4) mode(1) nameLen(1) name(nb)` | reason：0 ok/1 已存在/2 不存在/3 密码错/4 参数非法/5 服务不可用；mode：0 guest/1 account；**accountId 非 pid（E7）**——pid 仍由进大厅/建房路径分配（既有 4 号机制零改），身份层与在线层解耦："账号≠在线" |
| **34 CQueryStats** | C→S | `limit(1≤20)` | 身份从**连接上下文取**（fd→pid→登录态 accountId——服务端绑定，客户端不传身份防伪造）；登录态绑定：查**自己**（防枚举；放开留 ep16 防作弊期裁决） |
| **35 SStatsResult** | S→C | `count(1) × count{ matchId(4) kills(1) deaths(1) endedAt(8) }` | 按 ended_at 倒序 |

- **17/19/20/21/25 房级消息零改动**（§4.10 合同）；26/30 服务器级零改动。
- MSG_IDS.md 变更历史同步：v4.9（2026-11-11）+31~35；规则注记"31~35 为账号域·全异步·回执只走 33/35"。

### 5.2 密码方案（PBKDF2·ADR-16 的安全面 + 终审 F1 端口化）

- **层归属裁决（ADR-22）**："密码必须哈希存储+恒时比较"是**安全业务规则**→ 用例层端口 `IPasswordHasher { hash(plain) → stored; verify(plain, stored) → bool }`；"PBKDF2-SHA256 实现"是**机制** → 适配器（OpenSSL EVP）。收益与 IDamagePolicy 同构：注册/登录流程单测可注入 fake hasher，换算法（argon2 等）不动用例层。
- `PKCS5_PBKDF2_HMAC`（OpenSSL EVP，零新增重依赖）·SHA-256·**iter=12000**（注释注明 OWASP 生产建议 600k，教学口径标注升级路径）·盐 16B `RAND_bytes`。
- 存储格式：`pbkdf2-sha256$12000$<salt_b64>$<hash_b64>`（t_account.pass_hash VARCHAR(128)）。
- 校验用 `CRYPTO_memcmp` 恒时比较。
- 合法性：account `^[A-Za-z0-9_]{2,24}$`；pass 长度 6~64。非法=33 号 reason=4（不进库不进日志——**密码绝不进日志**）。

### 5.3 表结构（init.sql 幂等追加）

```sql
CREATE TABLE IF NOT EXISTS t_account (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  name       VARCHAR(24) NOT NULL UNIQUE,
  pass_hash  VARCHAR(128) NOT NULL,
  created_at BIGINT NOT NULL
);
ALTER TABLE t_match_result ADD COLUMN IF NOT EXISTS account_id INT NULL;
```

- 游客战绩 account_id=NULL；注册回溯绑定不做（历史局归属游客——写明边界）。
- **Redis 会话**（三库第二次被消费）：登录成功 → `SET sess:<pid> <account_id> EX 86400`（BestEffort：Redis 挂→跳过+降级计数，**不阻塞登录**——ep08 降级门纪律复用）。

### 5.4 全异步化（G9·ADR-16——账号域自身的血液纪律）

```
31/32/34 到达（主线程解析+合法性预检，微秒级）
  → 投 persistence worker 新增"账号查询队列"（有界 256）
  → worker: PBKDF2 计算 / SELECT / INSERT / Redis SET（阻塞 IO 在 worker——主线程零阻塞）
  → 结果作 AccountResult 事件回流（合流）→ 主线程 Fanout 33/35
```

- **时序契约**：31/32/34 的回执是**异步的**（请求-稍后回执模型）——客户端 UI 按"提交→loading→回执"建模，禁止同步等。
- **回执寻址（E9）**：31/32/34 入队时**封装发起时的 fd 快照**（persistence worker 不认识 fd）；AccountResult 事件携带该 fd 回流 → Fanout 按 fd 投递。fd 失效（断线）=丢+计数——查询无状态幂等，重连后重查即可。**跨域顺序契约**：33/35 与房级消息（15/17/25）之间**无顺序保证**（两域各自漏斗），客户端状态机必须容忍（如 33 号先于 25 号到达=正常）。**注册即登录（二轮校验 R2-F）**：31 号成功=自动登录态（33 号 reason=0 直接带 accountId+mode=1，省一次 32 号）；登录态绑定 pid 于进大厅时建立。
- **账号队列满（二轮校验 R2-E）**：有界 256 满 → 请求丢弃但**必回 reason=5（服务不可用）**——客户端永远不挂等；丢弃计数横幅。
- 账号域事件走 persistence 直投通道（Must 类保序），不经合流区（可丢）。

### 5.5 游客模式兼容（红线）

- 4 号游客登录**一行不改**（演示/测试零门槛）；33 号 mode 位区分；游客可打可结算（account_id NULL），**查战绩需登录**（34 号 reason 路径：未登录=reason 4 + 客户端提示"登录后可查"）。

## 附录 B · 终审：业务逻辑 × 架构设计逐链走查（v1.2·architect-handbook 第三轮）

> 方法：五条业务链逐层走查（开火判定链/账号链/同步链/生命周期链/持久化链）× 双向检查（业务规则是否漏到外层 + 架构约束是否绑架业务）。

| 链 | 走查结论 |
|---|---|
| **开火判定链**（19 号→路由→session.Fire→fire_judge→21/18 号→快照） | ✅ 判定规则全在实体层（射速/弹匣/无敌门+几何）、参数快照在用例、配置经端口注入；21 号即时事件先于 17 号新血量=既有客户端语义，无新问题 |
| **账号链**（31→预检→队列→worker→PBKDF2→回执） | ⚠️→✅ **F1**：哈希规则=实体层/实现=适配器——端口化 ADR-22；34 号"只查自己"强制点=AccountService 组装查询（用例层）✓ |
| **同步链**（17 号组装→Fanout→客户端插值） | ✅ flags 位语义归实体 invariants、组装翻译在用例（ep07 类图已报备）、客户端零改动承诺成立 |
| **生命周期链**（十杀/重生/无敌/结算） | ✅ 常量+不变式在实体；⚠️→✅ **F2**：重生选点**均匀随机**（e9790a8）是随机源——不端口化则双模式对拍的随机序列发散、子流永不相等——**ADR-23（对拍 P0 前置）**：IRandom 端口+per-session 独立 rng（seed=roomId 派生） |
| **持久化链**（事件→Durability→三库/WAL） | ✅ 分级是事件元数据不是分支逻辑，业务零感知 |

**反向检查（架构是否绑架业务）**：对拍确定性要求 ⇒ 唯一代价=随机源可注入（F2）——这是测试基建立法的常规成本，不构成绑架；worker 错相/双通道/优先级调度全部在适配层，用例层业务规则零迁就。

**终审结论**：五链走查后，业务逻辑与架构设计的映射**闭环**——每条业务规则有唯一层归属，每处架构约束有业务侧的等价兑现（确定性↔可对拍）。F1/F2 落 ADR-22/23 后，**无遗留设计问题，草案进入可批示状态**。

**ADR-22（哈希端口化）**：`IPasswordHasher` 端口归用例层，PBKDF2 实现归适配器——安全规则与机制分离。
**ADR-23（随机源端口化）**：全部业务随机源经 `IRandom` 端口注入，per-session 独立实例（seed=roomId 派生）——双模式对拍与单测确定性的**前置条件**；实现期核对现状 `rand()` 使用点并全部收编。
