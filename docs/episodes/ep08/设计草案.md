## 2. 架构总图：四层落位（v1.2 重画）

> 依据：architect-handbook §四「边界 = 接口 + 实现，**接口归高层**」+ §7.6-A 决策树。
> 旧图把 `BotDriver` 画进用例层、漏画 `net/*` 与 `protocol/*`，且与 §11.6-G2「BotDriver（适配器）」自相矛盾，本轮一并纠正。

```
框架与驱动   │ sol2 + Lua5.4 VM · hiredis · mariadb · mongocxx · 文件 IO
             │ net/(epoll · event_loop) · protocol/(帧字节 · 30 号 wire)
  └ 接口适配器│ scripting_lua.cpp  → IDamagePolicy / IBotPolicy
             │ config_service.cpp → IConfigSource（.lua 表 · 双缓冲 · 只读视图）
             │ persistence.cpp    → IMatchArchive / IAuditSink / ILeaderboard
             │   ├ mysql_store / mongo_store / redis_store（谦卑对象）
             │ match_wiring · bot_driver · map_geometry（既有，均属本层）
    └ 用例层  │ MatchService → IDamagePolicy / ICombatParams
             │ ApplicationOrchestrator（帧节律 · 事件订阅 · 生命周期）
             │ DurabilityPolicy（纯策略 · 零 IO）
      └ 实体层│ GameConfig + Validate() · WeaponParams
             │ DamageInvariants · BotIntentSanitizer
             │ fire_judge.h 几何/四道门 · bot_brain.h Decide（fallback）
组合根       │ main.cpp：只做 new + 注入（在四层之外，零业务节律）
```

**依赖方向**：箭头一律向内；`main.cpp` 是唯一知道全部具体类的地方。**所有端口定义在 `include/application/`（用例层），适配器实现之**（清单见 §2.1）；实体层不知道「策略」「存储」「配置源」这些用例概念。新增 `include/application/` 为纯头文件目录，不改 CMake 源组，步骤 1/2 登记即可。

**统一裁决（修正旧稿）**：§4.1 原把 `IDamagePolicy / IBotPolicy` 标为「实体层」，G3 却把 `IBanStore` 标为「用例层」——同类端口两种归属。本轮**全部归用例层**；实体层只放纯规则与值对象（`GameConfig` / `WeaponParams` / `DamageInvariants` / `fire_judge` / `bot_brain`），不出现「策略」「存储」「配置源」等用例概念。内建实现 `Builtin*` 是用例层的默认策略与测试桩，不是实体。

**跨层共享数据的处理**：`GameConfig` 是实体层值对象，但旧稿被 6 个消费者直接读（§3.2 读取点表）。按 ISP 切三张只读视图，由 `config_service`（适配器）投影，用例层只依赖视图接口；`std::atomic<std::shared_ptr<const GameConfig>>` 的**并发 / 生命周期机制归适配器**，实体层 `GameConfig` 只含数据与 `Validate()`（G1 裁决）。

**谦卑对象约束**：`persistence.cpp` / `config_service.cpp` / 三 `*_store.cpp` 只允许做「格式转换 + 搬运 + I/O 错误上报」，**不得含业务判定分支**；所有策略由用例层纯对象决定后以值传入。`DurabilityPolicy` 是纯函数集合（`Classify` / `Degrade`），返回 `QueueAction` / `DegradeDecision` 等结果 POD（输入 = 事件类型、队列水位、库健康位；输出 = 丢 / 留 / 告警），**零 I/O、零时钟、零全局状态**，可脱离 DB/Lua 单测（§9 策略单测行）。这把手册 E 第 3 问从「238 条存量断言继续绿」提升为「新增业务规则同样可纯单测」。

## 3. 配置体系：.lua 数据表 + 双缓冲 + 热重载

### 3.1 格式决策：服务端 .lua，客户端 DataAsset，同步走 30 号

> **判据：格式跟着生产者/消费者的生态走。**

| 层 | 格式 | 谁改 | 热更机制 |
|---|---|---|---|
| **数值**（枪参数/bot 旋钮/公式参数） | `game_config.lua`（纯数据表） | 运营/策划 | `reload` 整表换 |
| **公式**（伤害计算） | `damage.lua`（纯函数） | 开发 | `patch` 函数级换 |
| **决策**（人机 AI） | `bot_ai.lua`（纯函数） | 开发 | `patch` 函数级换 |

| **双端同步** | 30 号 wire | —— | 自动 |

**"两条热更通道"故事**：同一个 .lua 格式，两种换法——数据表整体换（reload）vs 函数级换（patch）。观众看到的是机制差异，不是格式差异。

### 3.4 双缓冲 + 版本 + 回滚

- **双缓冲**：`std::atomic<std::shared_ptr<const GameConfig>>`——加载→校验→原子替换→旧表 shared_ptr 延迟回收。消费方防半途换表撕裂——v1.8 实现定案：`MatchService::SetConfig(const GameConfig&)` **值拷贝推送**（主循环单线程，无并发读写，值拷贝即无撕裂；比 shared_ptr 局部快照更简），编排器在构造与 OnConfigChanged 时经五视图组装推入。**归属（§2.1）**：atomic / shared_ptr 是并发与生命周期机制，**只住 `config_service.cpp`（适配器）**；实体层 `GameConfig` 是纯值对象 + `Validate()`，不含任何并发原语。
- **版本号**：`v{会话序号}-{FNV1a_hash8}`（如 `v7-a3f2c1d8`）+ `version_note`（操作人动机一行话）。
- **快照环**：内存保留最近 4 版——`rollback` = 换回上一版（**内存 revert，不重读磁盘**——坏文件可能还在）；审计行标注"与磁盘分叉"警告。
- **校验**：全字段范围检查（`0 < weapons[type].reload_ms < 10000` / `mag ∈ [1,100]` / **`damage ∈ [1,255]`**（30 号 1B 上限）…）+ **跨字段关系**（`err_end_deg ≤ err_start_deg` / **`bot.fire_interval_ms ≥ max(weapons[*].fire_ms)`**（人机不得快于任何枪的射速门；原 `fire_min_interval_ms` 随 `combat` 组删除，不再有第二射速来源）/ `invuln_ms < respawn_ms` / `weapons[*].fire_ms > 0`）——任一不过=**整表拒收**保留旧表+红字告警。
- **审计时钟**：UTC 墙钟（与游戏内 ADR-1 steady 单钟分立各司其职）。

### 3.5 热重载语义（三条·测试钉住）

| 类型 | 语义 | 例子 |
|---|---|---|
| **数值类** | 下一发/帧即时生效 | 改 `weapons.rifle.damage` 25→50，下一枪就变（演示第一拍） |

### 3.6 reload 通道

- stdin 命令线程是 `ApplicationOrchestrator` 的**输入适配器**：`reload [note]` / `rollback` / `version` / `help`——命令表结构预埋 level 字段（ep08 只有 console=最高级，GM 权限分级雏形）。**`note` 是可选的一行操作动机**（含空格需引号，如 `reload "手枪过强 25→50"`），写入 `t_config_version.note`；未填记 `console@reload` 缺省值——这样 §3.4 的 `version_note` 才有来源，§1「审计链完整」KPI 才闭合。**组合根在 `main.cpp` 只把这个端口注入编排器，不解析命令、不持有主循环**（§2.1 归属表）。
- **线程安全（A1 修复）**：stdin 线程只入轻量命令队列，**编排器每帧开头消费**（33ms 延迟无感）——Lua 永远只被主循环碰，单线程语义保住。帧节律归用例层 `ApplicationOrchestrator`。
- 路径解析：env > CWD > exe 同级 > exe 上级（ep05 烘焙链同款）。

## 4. Lua 脚本层：策略接口 + 沙箱 + 热修

### 4.1 依赖倒置：接口归用例层，实现归适配器

> v1.2 修正：旧稿把 `IDamagePolicy / IBotPolicy` 标为「实体层」，与 §11.6-G3 把 `IBanStore` 标为「用例层」冲突。按手册 §四「接口归高层（用例）所有」，**全部端口统一归 `include/application/`**（完整清单见 §2.1）；实体层不出现「策略」概念。

```cpp
// ── 用例层（include/application/policies.h·端口归用例所有·零 sol2 痕迹）──
struct HitContext { float dist = 0.f; bool headshot = false; };

struct IDamagePolicy {
    virtual float Apply(float hp, float base, const HitContext& ctx) = 0;
    virtual ~IDamagePolicy() = default;
};
struct BuiltinDamagePolicy final : IDamagePolicy { /* 现行 DamageApply 搬入 */ };

struct IBotPolicy {
    virtual BotIntent Decide(const BotWorldView&, BotState&, BotMemory&,
                             std::uint64_t nowMs, const BotTuning&) = 0;
    virtual ~IBotPolicy() = default;
};
struct BuiltinBotPolicy final : IBotPolicy { /* 转调现行 Decide */ };

// ── 适配器（adapters/scripting_lua.cpp·唯一 include sol2）──
class LuaDamagePolicy : public IDamagePolicy { /* sol2 pcall damage() */ };
class LuaBotPolicy    : public IBotPolicy    { /* sol2 pcall bot_decide() */ };
```

`Builtin*` 是**用例层的默认策略与测试桩**（不是实体）；`Lua*` 是适配器实现。两者出适配器前都过实体层不变式（§4.3），保证换实现不改行为边界。此处为依赖倒置示意，`Lua*` 的**完整签名、沙箱与热修通道见 §10.2**。

### 4.2 Lua 三个面 + 两种热修

| 面 | 载体 | 热更机制 | 审计 |
|---|---|---|---|
| **参数面** | `game_config.lua`（纯数据表） | C++ 双缓冲 reload（整表换） | t_config_version |
| **公式面** | `damage.lua`（纯函数） | **同 lua_State 函数引用原子替换**（`luaL_loadbuffer`→沙箱自测→`std::swap` registry 引用→`luaL_unref` 旧闭包） | 同上+diff |
| **决策面** | `bot_ai.lua`（同签名换实现） | 同上 | 版本行 |

> **v1.3 语义精确化**：旧稿写「`dofile`→函数表原子替换」有两处不实——① `dofile` 属 base 库，会绕过沙箱读磁盘（§4.3 已修）；② Lua 没有 C++ 意义上的「函数表原子替换」，可换的是 **C++ 侧持有的闭包引用**（registry `int`）。实现签名见 §10.2.3；§4.5 的 upvalue 彩蛋正是「没换引用」的后果。

### 4.3 沙箱红线

- **库装载**：只 `luaL_requiref` 打开 `base / string / math / table`——**`os` / `io` / `package` 不装**（不用 `luaL_openlibs`）。
- **⚠ base 库陷阱（v1.3 修正）**：`dofile` / `loadfile` / `load` 属于 **base 库**，只开 base 它们仍可用，`dofile` 会绕过「不装 io」直接读磁盘任意文件。因此：① 脚本加载一律由 **C++ 侧按白名单路径读进内存**，用 `luaL_loadbuffer` + `lua_pcall`，**绝不调用 `dofile`**；② 沙箱初始化后把 `_G.dofile` / `_G.loadfile` / `_G.load` / `_G.require` / `_G.collectgarbage` 显式置 `nil`；③ `package` 不装使 `require` 本就不可用，置 nil 是双保险。§4.2 原写的「dofile→沙箱自测→swap」据此改为「loadbuffer→自测→函数引用 swap」（签名见 §10.2.2）。
- `nowMs` 一律 C++ 传参（ADR-1 延伸：**Lua 不持钟**）。
- **内存 cap**（B4 修复）：`lua_Alloc` 包计数分配器，超 32MB→分配失败→Lua 抛错→pcall 兜底接住→告警。
- **出口校验（A3 修复 · v1.2 归属修正）**：不变式是**企业级规则**，归实体层 `DamageInvariants` / `BotIntentSanitizer`（§2.1），由 **C++ 内建与 Lua 两条路径共用**，不再只保护 Lua 一条：
  - `DamageInvariants::Clamp(hp, result)`：有限值 + `[0, hp]` + 对 hp 单调不增，越界回退内建并计数告警；
  - `BotIntentSanitizer::Sanitize(...)`：坐标 clamp 到活动区 / `aimYawDeg` NaN 兜底 / 枚举越界 switch 兜底；
  - 适配器只负责**调用**这两个纯函数，不自己重写规则；`pcall` 失败回退内建后同样再过一遍（§4.4）。这也让 §4.7 第二层「热修不变式」有了唯一实现，不必在测试里另写一份断言逻辑。

### 4.4 pcall 兜底：脚本崩不塌服务器

```
Lua 调用 ──pcall 成功──► 用返回值
           ──pcall 失败──► 回退 BuiltinDamagePolicy / BuiltinBotPolicy
                         + 告警计数 + 日志（"降级可以但必须喊一声"）
```

两条分支的返回值**都过实体层 `DamageInvariants` / `BotIntentSanitizer`（§4.3）**——域不变式不因走了 fallback 而缺席。

### 4.5 upvalue 陷阱彩蛋（大纲钦定演示）

```lua
-- v1：local base = 25        ← upvalue
-- function damage(hp) return math.max(0, hp - base) end
-- 热修 v2 改 base = 50：函数表 swap 后，若 C++ 持有的是 v1 闭包引用 → 照跑 25
-- 演示：改了不生效 → 逐帧抓真凶（闭包捕获）→ 修法 = swap 引用而非改值
```

> 生产实现按 §10.2.3 的 `PatchFunction()` 换 registry 引用（`std::swap` + `luaL_unref` 旧引用），**不重赋值全局、不改 upvalue 的值**；彩蛋演示的 bug 恰是「只改值不换引用」。

### 4.6 调参纪律（C1）

`bot_ai.lua` / `damage.lua` **可调值一律从注入参数表读**，不许写 local 常量——防双源漂移。脚本只写逻辑（怎么用这些值），不写值本身。

### 4.7 对拍测试（两层门禁 · 2026-11-06 修订）

> 原稿只写「C++ 基准 vs Lua 逐字段一致，对拍不过 = patch 被拒」——但本期演示②就是「Lua patch 热修公式 bug」，修 bug 的定义恰恰是让输出与基准不同。**逐字段一致与热修生效互斥**，故拆成两层，各管一件事。

**第一层 · 上线等价性对拍（切默认前的一次性门禁）**
- 目的：证明 `damage.lua` / `bot_ai.lua` 的**初始实现**与 `BuiltinDamagePolicy` / `BuiltinBotPolicy` 行为等价，替换内建实现不会偷偷改变线上行为。
- 方法：同输入序列 C++ 基准 vs Lua 逐字段比对（**epsilon 浮点比较**——Lua double vs C++ float，中间结果可能差末位）。
- 失败含义：**不切换默认 Lua**（继续用 C++ fallback + 告警），而不是拒绝热修。
- 落点：步骤 8「bot_ai.lua 切默认」；与 §9「238 断言不链接 Lua 继续绿」互补。

**第二层 · 热修不变式校验（每次 patch / reload 的门禁）**
- 目的：允许热修**改变行为**，只保证改完仍在合法域内、不把服务器带塌。
- 方法：patch 后不再与 C++ 基准逐字段相等，改验：
  - `damage`：返回有限值、∈ `[0, hp]`、对 `hp` 单调不增、`HitContext` 全组合不抛错；
  - `bot_ai`：坐标 clamp 到活动区、`aimYawDeg` NaN 兜底、枚举越界 switch 兜底（§4.3 A3 出口 sanitize）；
  - 确定性：同一 patch 版本对同一输入序列重复执行，输出逐字段一致（防脚本藏随机数 / 全局状态漂移）；
  - 沙箱自测在 swap 前跑，pcall 失败即拒收并回退内建（§4.4）。
- 失败含义：**patch 被拒**，保留上一版函数表 + 告警计数 + 审计行记录拒收原因。
- 回归基线另存：热修前的 `Builtin*` 基准仍作为「未修改版本」的长期对拍基线，供 §3.4 快照环 `rollback` 后复验等价性。

## 5. 三库数据层：按形态与热度选库

### 5.1 选型判据（面试论点）

> **按数据的形态（行/文档）与热度（快/慢）选库。**

| 库 | 一句话 | 管什么 | 形态/热度 |
|---|---|---|---|
| **Redis** | 按**热度**选 | 击杀榜 ZSET / 封禁热名单 TTL | 热·快·可过期 |
| **MySQL** | 按**形态：结构化行** | 战绩聚合行 / 配置审计行 | 冷·稳·要查询 |
| **MongoDB** | 按**形态：文档** | 战报明细（嵌套时间线）/ 未来玩家档案 | 半冷·灵活 schema |

**其他库的排期位**：MongoDB 玩家档案=ep10+；ClickHouse/ES=离线分析侧；Kafka=ep12+ 跨服；分库分表=单服 QPS 到了才做。

### 5.2 事件订阅：编排归用例层（v1.2 修正）

> 旧稿把「三点扇出」放在 `main.cpp`，组合根因此承担业务编排，且只有裸 `std::function`、没有命名端口。按 §2.1 归属表，事件订阅归用例层 `ApplicationOrchestrator`；组合根只做注入。

```
三个事件源（B1 修复，事实不变）
  match.Tick()（main.cpp:239）/ botDriver.Tick()（main.cpp:238）/ match.Fire()（match_wiring 内）
        │ 通过端口注入（组合根接线，MatchWiring 不依赖任何具体 sink）
        ▼
  ApplicationOrchestrator（用例层 · 唯一的订阅点）
        ├─► IWireSink      → writer.deliverMatch()（现有 wire 分发）
        ├─► IMatchArchive  → persistence.ingest(events)
        └─► IAuditSink     → 配置变更审计（G4 · 独立通道）
                 ├─ MatchStart：开档（match_id = UTC 墙钟戳 + 会话内序号）
                 ├─ Kill：战报缓冲 append + 榜单增量
                 ├─ Ended：flush 战报文档 + 战绩行（分级由 DurabilityPolicy 决定）
                 └─ AbortMatch：落空档（end_reason=2 战报也是战报）
```

**归属要点**：「哪些事件要落库、什么时机开档 / flush」是应用级编排，写在编排器里；`persistence.cpp` 与三 `*_store.cpp` 是**谦卑对象**，只按 `DurabilityPolicy` 给出的决策值搬运字节，不含业务判定。`main.cpp` 不出现 `ingest` / `Tick` / `drain` 字样（§11.6 自检命令钉住）。原始三个事件源仍是 `match.Tick()` / `botDriver.Tick()` / `match.Fire()` 三处，B1 修复结论不变。

### 5.3 双队列分级（C 修复）

| 队列 | 策略 | 丢了怎样 |
|---|---|---|
| **审计队列** | `DurabilityPolicy::Classify` 判 `Must`；库可用→直写 MySQL，库不可用 / 队列将满→**`SpillToWal`** 落本地 `AuditWal`（append-only 文件 IO，最外层适配器）。**有界、不丢** | 法律级——丢了就追责 |
| **统计/战报队列** | 1024 有界，满=丢+计数告警 | 可丢——对局优先于落库 |

**doctrine：丢得起 / 丢不起分级。**

> **归属（§2.1）**：这两条是**业务规则**，不是队列实现细节。策略归用例层纯对象 `DurabilityPolicy::Classify(...) -> QueueAction{Enqueue, DropAndCount, SpillToWal, Defer}`（零 I/O、零时钟、可纯单测）；`persistence.cpp` 只执行返回的决策值。
> **v1.4 定案（消除「审计不丢 × DB 挂零中断」互斥）**：`Must` 事件在 sink 不可用时**不无限积压内存**，落 `AuditWal` 即视为「不丢」，**落库允许延迟**；`AuditWal` 是纯搬运的谦卑对象（只 append + fsync），`ReplayWal` 在库恢复或 `full` 启动时补写 MySQL。这样 §5.5「三库全挂 = 对局照打」与「审计不可丢」同时成立，队列可设上限、无 OOM 风险。**步骤 5 验收门**：`full` 下杀 MySQL → 审计行进 WAL → 恢复后回放补写，条数一一对应、无重复无遗漏（回放幂等靠 `version + FNV1a` 去重）。

### 5.4 三水槽设计

| Sink | 落什么 | DDL | 真相/投影 |
|---|---|---|---|
| **MySQLSink** | `t_config_version(version,source,diff_digest,note,created_at)` + `t_match_result(match_id,player_name,kills,deaths,ended_at,**config_version**)`（B3 修复：战绩行也带配置版本） | `init.sql` | **真相（must）** |
| **MongoSink** | 战报文档（roster/scores/kill_timeline/config_version/extra 空位）；索引 `_id` 唯一+`started_at` 倒序 | `init.js` | **尽力而为（best-effort）**+丢弃计数 |
| **RedisSink** | 击杀榜 `ZINCRBY leaderboard`；封禁通道 API（`ban(name,ttl)`/`is_banned`——ep08 只建通，ep09 消费） | —— | **投影**（MySQL 是真相；`REBUILD` 命令从 t_match_result 重建） |

**双写不一致（I 修复）**：MySQL 成功+Mongo 失败=聚合在、明细丢——doctrine：MySQL 行=must，战报明细=best-effort+丢弃计数。企业真解 outbox/事件溯源=口播对照不实现。

> **谦卑对象约束（§2.1）**：`MySQLSink / MongoSink / RedisSink` 只做「格式转换 + 写入 + 失败上报」，must / best-effort 的分级由 `DurabilityPolicy` 决定后以值传入，sink 内不得出现 `if (must)` 之类的业务判断。G4 的审计通道改由 `config_service` 发 `ConfigChanged` 域事件 → `ApplicationOrchestrator` 订阅 → 经 `IAuditSink` 端口入队，**不再 adapter 直调 adapter**（与 G7 同律，详见 §11.6）。

### 5.5 降级与生命周期

- **降级**：任一库挂=该 sink 丢弃计数+告警，**游戏零中断**（企业爆点镜头）；三库全挂=对局照打。**决策归用例层 `DurabilityPolicy::Degrade()`**（§2.1；结果 POD 为 `DegradeDecision`），`persistence.cpp` 只执行。
- **优雅停机**（B6 修复）：shutdown 三步——停 ingest→等队列清空（超时 2s）→join worker→三库正常断开。**这三步是应用级生命周期编排，归 `ApplicationOrchestrator`**，`main.cpp` 只转发信号；同时定义连接超时 / 重试退避，否则 2s 超时在 MySQL 网络超时面前不够。
- **生命周期 / 双模式开关**（J 修复 + v1.3）：`scripts/db_up.sh` 一键起三库 + 健康检查，服务器**启动横幅**打印三库连接状态（✓/✗）。**默认 `lite`：零前置启动、降级常驻；`full`：先 `db_up.sh --wait` 再启服务器、横幅三绿**。完整行为矩阵与时序见 **§5.7**；三库是可选的可观测性增强，**不再是启动前置**。
- 连接串走环境变量（`SIGHTLINE_MYSQL_DSN`/`MONGO_URI`/`REDIS_URI`）。

### 5.7 启动双模式（v1.3 · 部署可独立的落地）

> 起因：§2 评审四问「部署 ❌」——三库成了启动前置，但 §5.5「三库全挂=对局照打」证明库非业务必需。
> 方案：**默认 `lite`（零前置），`full` 为显式可选**。模式只改变**组合根对最外层持久化适配器的装配**，用例层 / 实体层 / wire 契约零感知——这本身就是整洁架构「框架与驱动可替换」的一次可演示证明。

#### 5.7.1 开关形式与优先级

| 项 | 取值 |
|---|---|
| 命令行 | `--db-profile=lite` 或 `--db-profile=full`（脚本层另提供 `--with-db` 简写） |
| 环境变量 | `SIGHTLINE_DB_PROFILE`（与 `SIGHTLINE_MYSQL_DSN` / `MONGO_URI` / `REDIS_URI` 同族） |
| 优先级 | **命令行 > 环境变量 > 默认 `lite`**（显式覆盖隐式；配置路径解析仍沿用 §3.6 的 env > CWD > exe 同级 > 上级） |
| 默认值 | `lite`——`./sightline_server` 裸跑即可开局 |
| 装配决策位置 | **只在 `main.cpp` 组合根**：`full` → `RealPersistenceAdapter{...}`，`lite` → `NullPersistenceAdapter{}`；两者实现同一组 `IMatchArchive / IAuditSink / ILeaderboard` 端口（§10.1.2） |
| 红线 | 用例层 / 实体层 / 任一 sink 内部**不得读 profile、不得 include 开关配置**；§11.6 自检命令第 6 条钉住 |

#### 5.7.2 行为矩阵（两模式唯一差异 = 持久化）

| 维度 | `lite`（默认） | `full`（演示 / 落库） |
|---|---|---|
| 启动前置 | 无 | `./scripts/db_up.sh --wait` 三库健康检查通过 |
| 装配 | `NullPersistenceAdapter`（三端口空实现，零 I/O） | `persistence.cpp` + `mysql_store` / `mongo_store` / `redis_store` |
| 启动横幅 | `[DB] profile=lite · 持久化未启用（对局照常）` | `[DB] profile=full · MySQL ✓ Mongo ✓ Redis ✓` |
| 事件落库 | **不落库**；`Must` 审计一律写 `AuditWal`（本地 WAL，文件 IO），`full` 启动后 `ReplayWal` 补写 MySQL（§5.3 定案） | 审计 / 战绩 / 战报 / 榜单正常落 |
| 降级 | 常驻（本就无库） | 任一库挂 → 该 sink 丢弃计数 + 告警、游戏零中断；**三库全挂时自动退化为 `lite` 语义** |
| 对局 / 17 号 / 21 号 / 30 号 / reload | **与 `full` 逐字节一致** | 同左 |
| 可测 KPI | reload 延迟、断线 0、双层对拍 | 全部（含审计链三连、DB 故障降级） |

> **关键约束**：模式**不得**影响玩法与 wire。两模式下同一输入序列产生的 17 / 21 / 30 号字节流必须相同（§9 新增双模式对拍），否则说明持久化渗进了业务路径——这比架构图更能证明边界画对了。

#### 5.7.3 启动时序

```
lite（默认 · 零前置）
  ./sightline_server
    → main 解析 profile=lite → 装配 NullPersistenceAdapter
    → 横幅 [DB] profile=lite → 正常开局（33ms 帧、30 号广播照发）

full（演示 / 落库）
  ./scripts/db_up.sh --wait               三进程健康通过后返回
  SIGHTLINE_DB_PROFILE=full ./sightline_server    （或 --db-profile=full）
    → main 解析 profile=full → 装配 RealPersistenceAdapter，连接串走环境变量
    → 横幅 [DB] profile=full · MySQL ✓ Mongo ✓ Redis ✓
    → 正常运行；运行中库挂走 §5.5 降级，不重启
```

#### 5.7.4 演示镜头（双模式不是妥协，是两个论点都能上镜）

| 镜头 | 模式 | 拍什么 |
|---|---|---|
| 正片开场 | `full` | 三绿 ✓✓✓ 横幅 + 一局落库可查（企业级观感保留） |
| 企业爆点 | `full` | `kill -9 mongod` → 丢弃计数 + 对局零中断（§1 KPI） |
| 架构反证 | `lite` | **不启任何库直接开局**，血条 / 换枪 / reload 全正常 →「库不是业务必需」从口播变成画面 |
| 边界证明 | 两模式对照 | 同输入序列 17 / 21 / 30 号逐字节一致，录屏并排 |

> 原顾虑「横幅不再是三绿」由 `full` 模式解决；`lite` 反而新增一个更有说服力的镜头。

#### 5.7.5 验收门（挂 §9 / §10 步骤 5）

1. `lite` 裸跑：一局完整对局、断线 0、`reload` 生效延迟达标；
2. `full` 三绿：一局落库 + 重启可查 + 审计链三连一致；
3. `full` 杀 `mongod`：对局零中断 + 丢弃计数 + 告警；三库全挂自动退化 `lite` 语义；
4. **双模式 wire 对拍**：同输入序列 17 / 21 / 30 号逐字节一致（排除 `match_id` 等仅持久化字段）；
5. 两模式 `reload` 延迟 KPI 一致 → 证明持久化不在热路径。

## 13. KPI 口径

| KPI | 口径 | 来源 |
|---|---|---|
| reload 生效延迟 | **命令被主循环消费时的 steady 时刻 → 首个采用新配置的伤害判定 steady 时刻**之差（同一 ADR-1 单钟，可相减）；审计行的 UTC 墙钟只用于展示，**不参与计算**（§3.4 双钟分立，混用会算出小时级误差）。口径不含「编辑文件→敲 reload」的人工耗时——服务器不可观测 | 命令消费时间戳 + 判定行时间戳 |
