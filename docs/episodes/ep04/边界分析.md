# 双端业务边界分析（ep04）

> 范围：`client/Sightline/Source/` 与 `server/` 全量业务代码通读。
> 结论先行：代码里的"边界"实为六类——**职责边界、输入合法性边界、数值/容量边界、状态边界、并发边界、失败边界**。

---

## 一、链路与传输

### 1.1 字节流 → 帧（粘包 / 半包 / 坏帧）

**服务端** `adapters/frame_codec.h:27-44`：

| 边界情形 | 处理 |
|---|---|
| 不足 4B 帧头 | `return false`，缓冲不动，等下次 read |
| `len < 2`（坏帧，无法定位 msgid） | **`buffer.clear()` 全量丢弃** + `return false` |
| 不足 `len + 2` 字节 | `return false`，半包留存 |
| 合法 | 切帧 + `consume` 对应字节 |

**客户端** `SightlineProtocol.h::TryDecode` 与之镜像，但多一处关键修复：

```cpp
Out.Payload.Reset();   // FFrame 跨迭代复用时必须先清
Out.Payload.Append(...);
```

这是 M6 联调实锤的坑——多帧粘包时前帧字节滚进后帧，产生 5/4 幻影人数。
**边界病灶不是校验缺失，是复用对象未清场。**

两边坏帧策略一致：**宁可丢弃整段缓冲，不可卡死切帧**。这是死循环防御，不是数据完整性防御。

### 1.2 连接生命周期

**服务端** `net/client_connection.h` 的边界处理最密集：

| 边界 | 处理 | 出处 |
|---|---|---|
| 重复 close（fd 复用） | `bClosed_.exchange(true)` 双关守卫 | `handleClose` |
| close/write 竞态 | `::close` 与 `send` 同 `outMutex_` 互斥 | TSAN 实锤 |
| 自我释放 UAF | `handleClose` 经 `queueInLoop` 延迟到 epoll 批次外 | `handleClose` 注释 |
| 发送积压 | 快路径直写 → `outBuf_` 兜底 → `EPOLLOUT` 动态挂摘 | `send` / `handleWrite` |
| 写已死连接 | `bClosed_` 快路径 + 锁内终检（TOCTOU 残窗） | 档二压测 6204 行 EBADF |
| SIGPIPE 杀进程 | `std::signal(SIGPIPE, SIG_IGN)` | `main.cpp` |

`send()` 的双重 `bClosed_` 检查是典型边界设计——**锁外快路径省开销，锁内终检封竞态**。

**客户端** `SightlineConnection.h` 边界更简单，但有一处服务端没有的：**入站损伤注入**。

- `InboundDelayMs` 是 `std::atomic<int32>`（游戏线程写 / 接收线程读）
- `DelayQueue` 仅接收线程触达，故零锁
- 抖动漂移有界随机游走，钳在 `[-Delay/2, +Delay/2]`

### 1.3 跨线程边界

两端都是**单一跨线程门**：

| 端 | 门 | 承载 |
|---|---|---|
| 服务端 | `frame_queue`（MPSC） | `Frame` / `Closed` 两种控制帧，worker 生产、main tick 消费 |
| 客户端 | `AsyncTask(GameThread, ...)` | 值拷贝投递 |

**服务端多一道陈旧事件防护**（`main.cpp` tickBody）：

```cpp
auto itc = connections.find(fd);
if (itc == connections.end() || itc->second != ev.conn) continue;  // 指针身份校验
```

fd 号会被内核复用——队列里排队的事件可能属于已死旧连接。
**校验的是指针身份而非 fd 值**，这是 fd 复用场景下唯一可靠的边界判定。

accept 回调里还做了对称的"旧账结清"，两侧闭环保证新主人不被误踢。

## 二、协议与输入合法性

### 2.1 长度校验的归属

服务端 `protocol/messages.h` 的纪律写得很死：

> ② 全工程唯一 switch = `DecodeC2S` 的 msgid→Parse 选择；**长度校验全部进 Parse**

```cpp
static std::optional<PlayerInputMsg> Parse(std::span<const uint8_t> b) {
    if (b.size() != kSize) return std::nullopt;   // 25→21 类欠账永绝
}
```

`StartMatchMsg` 更严：`if (!b.empty()) return std::nullopt;`（契约空 payload，非空即拒）。

**对比客户端**：长度校验散落在 `HandleFrame` 各分支的 `if (Payload.Num() < N) return;`，且解析越界时**整包放弃**（`Parse` 返回 false → `return`）。两种风格，效果等价但服务端更集中。

### 2.2 一处符号边界隐患

客户端 `SightlineMatchSession.cpp` 解析 15 号：

```cpp
const int16 SignedCount = static_cast<int16>(Payload[0] | (Payload[1] << 8));
const int32 Count = SignedCount;
```

服务端写的是 `u16(n)`，客户端读成**有符号 16 位**。当前房间上限 4 人，永不触发；但这是个潜伏的符号边界——若未来人数超 32767 会变负数导致循环不执行。同理 17 号 `Count` 也是 `u16` 写 / `int16` 读。

### 2.3 未知消息与降级

`MessageDispatcher::dispatch`：未注册 msgid → `LOG_WARNING` + 忽略。**不回错误码、不断连**——宽松收口，防协议演进期误杀。

高频帧（心跳）挂 `trace=true` 降级到 TRACE 级，不刷屏。这是**日志边界**，防止 30Hz×N 客户端把异步日志队列压垮（M6 实锤过终端冻结 → 双端 LAG 级联）。

## 三、账号与房间

### 3.1 容量与格式边界（`lobby/lobby.h`）

```cpp
constexpr size_t   kMaxRoomMembers   = 4;
constexpr int64_t  kLoginGraceMs     = 60000;   // 60s
constexpr size_t   kMaxNameBytes     = 16;      // UTF-8 字节
constexpr size_t   kMaxRoomNameBytes = 24;
```

`ValidName` = 非空 && 字节数 ≤ 上限。注意是**字节数不是字符数**——UTF-8 中文名 3 字节/字，实际可写约 5 个汉字。

### 3.2 状态边界与错误码

| 操作 | 边界检查 | 错误码 |
|---|---|---|
| Login | 名字非法 | 2（**宽限照旧，可重试**） |
| Login | 同名顶号 | 老连接 `Kicked(1)` → 离房 → 注销 |
| Login | 同 fd 重登录 | 先按断线自清（离房 + 注销旧名） |
| CreateRoom | 未登录 / 已在房 / 名字非法 | 1 / 2 / 3 |
| Join | 未登录 / 房不存在 / 已在房 / 已满 | 1 / 2 / 4 / 3 |
| Leave | 不在房中 | **静默无事发生**，不回错误 |
| Disconnect | — | 与 Leave 同路径，另注销玩家 |

两个值得注意的边界设计：

**① 房主转移无显式逻辑**
`Room::memberFds` 按加入顺序，**首位即房主**——删除元素后新首位自动成为房主。注释明确写"房主转移由删除自动成立"。用数据结构消解了状态边界。

**② 空房自动解散**
`LeaveInternal` 里 `if (room.empty()) rooms_.erase(roomId);`，同时触发 `RoomListPush` 全量快照。

### 3.3 时间边界

`SweepLoginTimeouts(nowMs)` 每 tick 调用，超 60s → `Kicked(2)`。
**时间由外层注入**，用例层零 `now()` 调用——这是可测性边界，不是功能边界。

> 注释漂移：`main.cpp` 写"登录宽限期起点（10s）"，与 `lobby.h` 的 `kLoginGraceMs = 60000` 不符。实际以常量为准。

## 四、对局与移动同步（服务端权威）

### 4.1 最小合法性钳制（R12）

`match_service.cpp` 的核心边界：

```cpp
constexpr float kMaxSpeedUuPerSec = 1000.f;   // 行走 450 / 冲刺 ~700，留裕量
constexpr float kMaxInputGapSec   = 0.1f;     // 100ms：10fps 单帧位移也放行
```

钳制公式：

```cpp
const uint32_t gap = (seq > E.ackedSeq) ? (seq - E.ackedSeq) : 1u;
const float gapScale = std::min((float)gap, 3.0f);      // cap 3x 防刷
const float bound = kMaxSpeedUuPerSec * kMaxInputGapSec * gapScale;  // 100~300 uu
if (len2 > bound * bound) { /* 保方向弃模长 */ }
```

**三道边界设计**：

1. **gapScale 感知丢帧**——丢帧时 `dx` 含多帧位移，bound 按实际间隔倍数放大，避免误伤诚实移动
2. **cap 3x 防刷**——恶意客户端不能靠刷大 seq 拿无限 bound
3. **保方向弃模长**——传送黑客打不动权威位

关键取舍写在注释里：**故意不用服务器测得的到达间隔**。
因为延迟滑块会让输入突发到达（间隔 1~5ms 但各含 ~16ms 位移），按到达间隔钳制会误伤诚实移动、刷爆客户端和解。
这是"防御边界不能建立在被污染的观测量上"的典型案例。

### 4.2 权威位推算

```cpp
if (!E.bHasReport) { E.x = x; ...; E.bHasReport = true; }   // 首报 = 上报位
else { E.x += dx; ... }                                      // 权威 = 上次权威 + 钳制增量
E.lx = x; E.ly = y; E.lz = z;                                // 增量基准永远 = 客户端声明轨迹
```

**两个基准分离**：权威位（`x/y/z`）走钳制增量累积，声明基准（`lx/ly/lz`）永远记原始上报值。
诚实路径两者恒等，作弊路径分叉但权威位不失控。

### 4.3 其他状态边界

| 边界 | 处理 |
|---|---|
| 未知 pid 上报 | **静默忽略**（注释："信任但只转发 ≠ 来者不拒"） |
| 未上报者 | `bHasReport=false` 不入快照——避免 `(0,0,0)` 幻影出生 |
| `ackedSeq` | `std::max(E.ackedSeq, seq)` **只进不退**，乱序防御 |
| yaw / pitch | 无动力学模型，末次上报即权威（**零校验**） |
| flags | 原样透传，**零校验** |
| 对局期 16 号 | `match_wiring.h` 直接拒收（v4 R10），不进用例 |
| 重复 START | **无服务端幂等**，靠客户端切图状态兜底（`IsActive` 仅日志用） |

朝向与 flags 的零校验是**已知缺口**，注释明确"完整反作弊 ep08"。当前信任模型是"钳位移，放朝向"。

### 4.4 快照边界

`deliverMatch` 的 Snapshot 分支有一条硬约束：

```cpp
// ⚠ 计数必须 = 实际写入条数（数清再写头）——声明的 n 与实体不一致会导致客户端幻影解析
std::string p = u16(static_cast<uint16_t>(n));  // n 在写 body 时数出来
```

**先写 body 数条数，再写头**。这是"帧自洽"边界——头载荷不一致会让客户端解析错位。

v4.1 起快照**含接收者自己**（v3 的滤自己废止），因为自实体权威位 + ackedSeq 就是和解对账基准。

## 五、客户端预测与和解

### 5.1 输入史容量边界

```cpp
constexpr int32 kInputHistoryTarget = 30;   // 1s @30Hz
constexpr int32 kInputHistoryCap    = 64;   // 硬顶
```

淘汰是**双条件**：

```cpp
while (Num - EvictCount > kInputHistoryCap ||
       (Num - EvictCount > kInputHistoryTarget &&
        Seq - InputHistory[EvictCount].Seq > kInputHistoryTarget))
    ++EvictCount;
```

- 条件 A：硬顶兜底（防帧率暴涨撑爆）
- 条件 B：目标条数 **且** seq 跨度超 30（保证历史覆盖 1 秒）

批量 `RemoveAt(0, EvictCount)` 而非逐条 `RemoveAt(0)`——30Hz×64 的高频路径，O(n²) → O(n)。

### 5.2 和解三分支边界（`SightlineReconcile.h`）

```
输入: 权威位 + 输入历史 + ackedSeq + ε

边界 1  线性查找 seq == ackedSeq
        └ 找不到 → FullSnap（断档全量兜底）
边界 2  errCm < kReconcileEpsilonCm (5cm)
        └ 是   → None（无感通过）
边界 3  否     → ErrorTranslate（误差向量平移）
```

`replayFrames = historyCount - 1 - idx`——只在 `ErrorTranslate` 有语义；`None` 分支强制归零（修过 HUD 恒显 1-2 帧的误标，那是管线深度不是重放量）。

**未处理的边界**：`Evaluate` 里 `historyCount == 0` 时 `errCm = 0`（FullSnap 分支），实际会走 FullSnap 因为找不到 seq。空历史是合法态（刚开局），兜底正确。

### 5.3 上报窗口边界

```cpp
if (!Conn || !bInMatch || SelfPlayerId == 0) return;
```

三重守卫。`bInMatch` 的置位 / 清位：

- 置位：收到 15（`MATCH_START`）
- 清位：自己 18 离场 / `NotifyLinkLost`

`InputHistory` 在三处清零：`NotifyLinkLost`、`MATCH_START`、（隐式）新对局。
**重连后从零起账**，不带旧预测史。

### 5.4 坏帧边界

`HandleFrame` 每个分支都有 `if (Payload.Num() < N) return;`，`Parse` 失败则 `return`——**整包放弃**，不做部分解析。宁可丢整帧快照，不让解析器错位。

## 六、远端插值与动画（客户端）

### 6.1 时间边界

```cpp
constexpr float kInterpDelaySec  = 0.025f;   // 25ms
constexpr float kRotInterpSpeed  = 10.f;
const float MaxExtrapolation     = 0.2f;     // 200ms
```

**核心约束**：`kInterpDelaySec(25ms) < 快照间隔(33ms)`。
若延迟 ≥ 间隔，`Alpha` 恒 0 = 30Hz 跳格。注释记录了 300ms 时代遗留的教训。

```cpp
const double Span = FMath::Max(1e-6, SnapB.TimeSec - SnapA.TimeSec);  // 除零防护
const float MaxAlpha = 1.0f + (float)(MaxExtrapolation / Span);
const float Alpha = Clamp(RawAlpha, 0.0, MaxAlpha);
```

`Span` 有 `1e-6` 下界（除零），`Alpha` 上界随 Span 动态缩放（快照迟到时允许外推，但最多 200ms 当量）。

### 6.2 快照窗口边界

```cpp
if (SnapCount == 0)      { /* 直摆 + 清零速度 + bRemoteActive = true */ }
else if (SnapCount == 1) { SnapB = ...; SnapCount = 2; }
else                     { SnapA = SnapB; SnapB = ...; }   // 滑动
```

`TickRemoteInterpolation` 开头 `if (SnapCount < 2) return;`——**凑不齐两帧不动**。
首帧直摆是必要的"入场边界"，避免角色从原点飘过来。

### 6.3 速度估计边界

```cpp
const int32 DAck = SnapB.Ack - SnapA.Ack;
if (DAck > 0) { /* 计算 */ }   // DAck <= 0：保持上一拍速度
```

四道滤波边界：

| 道 | 边界 | 目的 |
|---|---|---|
| `DAck > 0` 门 | ack 重复时不算 | 防除零，防速度闪回 Idle |
| 非对称低通 | 升 α0.1 / 降 α0.25 | 滤抖动 vs 停步拖尾 |
| 底部斩断 | `Size2D() < 15` → 归零 | 低速尾巴无物理意义 |
| 顶部钳制 | `GetClampedToMaxSize(420)` | 对齐 MaxWalkSpeed=400，防 BS 误触顶格 |

`kSpeedDeadZone = 5` 另有一处：`DirectionAngle` 在死区内强制归零，避免静止时方向角乱跳。

### 6.4 远端无物理边界

`BeginPlay` 非本地分支：`DisableMovement()` + `GravityScale = 0`。
**远端傀儡位置 100% 由快照决定**，移动组件是死壳。
这消解了"网络位姿 vs 物理模拟"的冲突边界——不给它们打架的机会。

### 6.5 GetVelocity 覆写

```cpp
return bRemoteActive ? RemoteVelocity : Super::GetVelocity();
```

`bRemoteActive` 只在首个快照后置 true——**未收快照前远端动画静止**，不返回垃圾值。

## 七、双端不对称与已知缺口

### 7.1 边界重复校验（纵深防御）

| 校验点 | 服务端 | 客户端 |
|---|---|---|
| 帧长度 | `Parse` 集中 | `HandleFrame` 分散 |
| 实体位移 | 钳制 100~300uu | 不校验（信服务器） |
| ε 阈值 | 不知（纯转发权威位） | 5cm |
| 快照计数 | 数清写头 | `int16` 读（**符号隐患**） |

### 7.2 明确的缺口（代码注释已认账）

1. **yaw / pitch / flags 零校验**——完整反作弊 ep08
2. **无 C2S 速率限制**——30Hz 之上不限流，恶意可刷爆 tick
3. **重复 `START_MATCH` 无幂等**——靠客户端兜底
4. **客户端 15/17 号 Count 用 `int16` 读 `u16`**——人数上限内安全
5. **`main.cpp` 注释"10s" 与 `kLoginGraceMs = 60000` 不符**——注释漂移
6. **远端插值无 jitter buffer**——靠 25ms 延迟 + 200ms 外推硬扛
7. **`kMaxInputGapSec` 是固定值**——不随实际 tick 率自适应

### 7.3 边界设计的共同范式

双端反复出现三个手法：

1. **静默忽略优于报错**——未知 pid、不在房、未知 msgid 一律不回错误码。协议演进期的宽容收口。
2. **整包放弃优于部分解析**——坏帧不尝试挽救，防解析器错位。
3. **单调只进不退**——`ackedSeq = max(...)`、`LastAckedSeq` 只更新不回退，乱序 / 重放天然免疫。

## 附：讲法建议

讲边界别按文件讲，按**「三种失败」**讲：

| 失败类型 | 典型边界 | 处理 |
|---|---|---|
| **坏输入** | 长度 / 格式非法 | `Parse` 拒绝 或 整包放弃 |
| **坏状态** | 不在房 / 不在局 / 未登录 | 静默忽略 |
| **坏时序** | 乱序 / 丢帧 / 迟到 | 单调 seq + gapScale + 外推限幅 |

服务端钳制公式那段最有说服力——它证明了**防御边界不能建立在被污染的观测量上**（不用到达间隔而用 seq gap）。
