# Sightline 架构设计文档

> 本文回答四个问题：**这个系统分几层、每层怎么设计的、为什么这样设计、消息在里面怎么流转**。
> 所有函数名、调用关系与代码一一对应（截至首次联调通过版本，commit `4270f29`）。
> 配套阅读：`README.md`（快速上手）、`docs/reference/game_plugin.h`（玩法插件参考设计）。

---

## 一、总览：一句话架构

**Sightline = 一颗零 IO 依赖的玩法内核（domain），被一层可整体替换的网络引擎（net）驱动，中间靠两个接口（ports）完成依赖倒置，字节与玩法对象之间的翻译全部收口在适配层（adapters）。**

```
                    main.cpp（组装工：创建一切、接线、上电、退场）
                        │
        ┌───────────────▼───────────────────────────────┐
        │  adapters/ 接口适配层 —— 翻译与分发             │
        │  GameServer（分发 + IGameChannel 实现）          │
        │  ProtocolCodec（字节 ↔ DTO）                    │
        │  Acceptor / TcpConnection / Buffer（连接与字节）│
        │  TimerWheelAdapter（ITimerScheduler 实现）      │
        └───────┬───────────────────────────▲───────────┘
                │ 调用 inward               │ 接口回调 inward
        ┌───────▼───────────────────────────┴───────────┐
        │  application/ 用例层 —— 编排"系统怎么被使用"    │
        │  SessionService（登录/心跳/踢人）               │
        │  RoomService（进房/移动/开火/胜负/重生）        │
        │  ports/: IGameChannel + ITimerScheduler ★     │
        └───────┬───────────────────────────────────────┘
                │
        ┌───────▼───────────────────────────────────────┐
        │  domain/ 实体层 —— 玩法规则，零外部依赖         │
        │  Room（状态机+权威判定） Player types           │
        │  combat/（hitscan 射线判定、伤害结算，纯函数）  │
        └───────────────────────────────────────────────┘

        ┌───────────────────────────────────────────────┐
        │  net/ + logger/ 框架与驱动层 —— 毕带网络库      │
        │  Epoll · Channel · EventLoop · Socket          │
        │  HierarchicalTimingWheel（分层时间轮）          │
        │  （不含任何 game 头，可整体替换为 asio 等）      │
        └───────────────────────────────────────────────┘

  铁律：依赖方向一律向内。domain 不知道任何人的存在；
       net 与 domain 互相不知道对方存在（它们处于不同的"世界"）。
```

**控制流 ≠ 依赖方向**：一条消息从 epoll 进来、穿过 domain、再回到 socket 发出去（控制流双向穿越各层），但源码的 `#include` 只允许指向内层。做到这一点的机关就是"接口归用例所有"——下文第四节详述。

## 二、分层设计详解

### 2.1 框架与驱动层：`include/net/` + `include/logger/`

**它是什么**：从毕设微服务库剥离出来的通用网络库（Reactor 模型），共 6 个组件。

| 组件 | 职责 | 关键设计 |
|------|------|----------|
| `Epoll` | IO 多路复用封装 | `kNew/kAdded/kDeleted` 三态状态机管理 Channel 生命周期；`fillActiveChannels` 里做 fd→Channel 指针一致性校验（防 epoll 返回悬空指针）|
| `Channel` | 一个 fd 的事件与回调 | 读事件 `EPOLLIN\|EPOLLPRI\|EPOLLET`（边缘触发）、写事件 `EPOLLOUT`（水平触发）；`tie()` 持有 owner 的 shared_ptr，事件处理期间防止 owner 被销毁 |
| `EventLoop` | 事件循环本体 | one loop per thread；`eventfd` 跨线程唤醒 + `pendingFunctors` 队列实现 `runInLoop/queueInLoop`；`runAfter/runEvery` 透传时间轮 |
| `Socket` | fd 的 RAII 封装 | `accept4(SOCK_NONBLOCK)` 产出非阻塞连接 fd；`setTcpNoDelay`（FPS 必关 Nagle）；析构设 `SO_LINGER(0)` 立即释放 |
| `InetAddress` | 地址封装 | 略 |
| `HierarchicalTimingWheel` | 分层时间轮定时器 | O(1) 插入/删除；最小堆追踪最近到期；跳 tick 补偿（卡顿时按 elapsed 补推） |

**设计立场**：这一层被当作"可替换的细节"对待——**它不知道任何 game 的存在**（守护脚本红线 3）。今天跑 FPS，明天把 `adapters/TcpConnection` 换成 asio 版本，`net/` 整个目录删掉，`domain/` 和 `application/` 一行不改。

**本项目的关键修订**（相对毕设原版）：
1. 删除了 800 行配置热更新（`networkConfig` 全家），`EventLoop` 从 2119 行瘦到 819 行；
2. `Channel` 补 `tie()`（防事件回调中对象销毁）；
3. `Socket::accept` 改 `accept4` 非阻塞产出 + 新增 `setNonBlocking()`——修复"阻塞 accept 卡死事件循环"的历史 bug（详见知识库重构笔记 9）。

### 2.2 实体层：`include/domain/` —— 玩法内核

**它是什么**：游戏的全部规则，**"去掉软件这些规则依然成立"的那部分**。

```
domain/
├── types.h               PlayerId/RoomId/Vec3 —— 全项目的基础词汇
├── player.h              Player：id、hp、kills、alive、position、yaw
├── room.h                Room：状态机 + 全部对战规则（本层的心脏）
└── combat/
    ├── hitscan.h         rayIntersectsAABB / pickNearestTarget —— 纯函数
    └── damage.h          applyDamage(hp, dmg) → {new_hp, dead} —— 纯函数
```

**Room 状态机**：`Waiting → Playing → Finished`。所有"什么时候允许做什么"都由状态机守门：

```
        addPlayer/canJoin        tryStart(人数>=min)        finish(三杀/仅剩一人)
 Waiting ────────► Waiting ────────► Playing ──────────────► Finished
    │                │                  │                        │
    └── Waiting 阶段：applyMove/applyFire 一律拒绝（返回 invalid）
                                       │
                                       ├─ applyFire：服务器权威命中判定
                                       └─ respawn：死亡 N 秒后满血回到出生点
```

**`Room::applyFire(shooter, origin, dir)` 是服务器权威的具象化**——它一次完成：
1. 校验射手合法（存在、Playing、存活）；
2. 把所有存活敌人抽象为 AABB 候选（`TargetBox{0.4, 0.9, 0.4}` 人形包围盒）；
3. `combat::pickNearestTarget` 做 slab 法射线求交，取最近者（子弹不穿人）；
4. `combat::applyDamage` 结算血量；
5. 若击杀：`kills+1`，达到 `kills_to_win` 则 `finish()` 并给出 winner；
6. 全部结果打包成值对象 `FireResult` 返回——**Room 不产生任何副作用（不发消息、不定时器、不打日志）**。

**为什么这样设计**：
- **可单测**：`tests/domain/` 里 15+ 个断言（正面命中/擦过/身后不中/取最近/三杀获胜/退房判胜/满员拒绝）不需要任何网络环境，`g++ tests/domain/test_room.cpp` 直接跑；
- **确定性**：同输入同输出，这是未来做录像回放、帧同步校验的地基；
- **红线**：`domain/` 只 include 标准库。`scripts/check_dependencies.sh` 用 grep 强制守护这条线——**架构规则不靠自觉，靠脚本**。

### 2.3 用例层：`include/application/` —— 编排

**它是什么**：描述"系统怎么被使用"的业务流程。它不发明规则（规则在 domain），它负责**取实体 → 调规则 → 把结果翻译成事件 → 选收件人**。

```
application/
├── dto.h                 命令(GameCommand)与事件(GameEvent)，全部是 variant 纯数据
├── ports/
│   ├── i_game_channel.h      ★Port#1：sendTo / sendToAll / close（网络的全部）
│   └── i_timer_scheduler.h   ★Port#2：runAfter / cancel（时间的全部）
├── session_service.h     登录身份分配、conn↔player 映射真源、心跳喂狗、超时踢人
└── room_service.h        房间池、进房匹配、移动转播、开火编排、重生调度、退房处理
```

**两个 Port 是全项目仅有的接口**（反过度设计红线：C++ 没有反射，接口只在需要第二实现/测试替身时才建）。它们解决两个"控制流向外、依赖向内"的经典问题：

1. **RoomService 算出命中事件后要发给别人**——直接调 TcpConnection 就形成了"用例依赖框架"。解法：`IGameChannel` 接口**声明在用例层**（归用例所有），实现在适配层（GameServer）。
2. **心跳超时踢人需要定时器**——直接调 EventLoop 就把 timerfd 拖进了用例。解法：`ITimerScheduler` 由 `TimerWheelAdapter` 实现（内部透传 `EventLoop::runAfter` → 时间轮）。

**单测收益的直接兑现**：`tests/application/test_room_service.cpp` 用 `FakeChannel`（记录所有发送）+ `FakeTimer`（手动推进时间）驱动"登录→进房→开战→移动→命中→踢人→判胜"全流程——**整套业务逻辑的测试不需要 socket、epoll、timerfd 中的任何一个**。

**身份映射的真源原则**：`connId ↔ playerId` 的映射只存在于 `SessionService`（`playerIdOf` / `connIdOf`）。适配层发送时反查，不维护第二份映射——单一真源消灭了"两份数据不同步"这一整类 bug（联调时真的抓到过：LoginAck 因映射注册晚于发送而被静默丢弃）。

### 2.4 接口适配层：`include/adapters/` —— 翻译

**它是什么**：外部世界（字节流、系统调用）与内部世界（DTO、实体）之间的海关。职责只有三类：**搬运、翻译、分发**，禁止出现业务判断。

```
adapters/
├── acceptor.h            监听 + accept4 排干循环（ET 要求排干到 EAGAIN）
├── tcp_connection.h      连接生命周期：ET 读排干 / 直写+输出缓冲+EPOLLOUT / tie 保活
├── buffer.h              读写缓冲（readv + 栈上 extra buffer，吸收粘包半包）
├── protocol_codec.h      [2B len][2B msgid][payload]（小端）↔ DTO 的唯一翻译点
├── game_server.h         连接表 + switch(msgid) 分发 + IGameChannel 实现
└── timer_wheel_adapter.h ITimerScheduler → EventLoop::runAfter 透传
```

三个值得展开的设计：

**① TcpConnection 的写路径**（`sendInLoop`）：先尝试直写内核缓冲；写不完的进 `output_buffer_` 并 `enableWriting()`，等 `EPOLLOUT` 事件再排干，排干后立即 `disableWriting()`——"有积压才关注可写"是 LT 写事件的正确姿势（否则可写状态会持续触发空转）。

**② ProtocolCodec 的谦卑对象属性**：它把 `[2,7]` 翻译成 `LoginCommand{"Alice"}`，除此之外一无所知。协议改版（比如换 protobuf）= 重写这一个文件 + UE 端对应改动，其他层不动。

**③ GameServer 是依赖倒置的"回程桥"**：它 include 了两个服务并直接调用（adapters→application，依赖向内 ✓）；同时它实现 `IGameChannel`（application 通过接口反向调用它，控制流向外、依赖向内 ✓）。

### 2.5 组装层：`main.cpp` —— 50 行的装配线

```cpp
EventLoop loop(cfg.loop);                  // 框架层
TimerWheelAdapter timers(loop);            // Port#2 实现
ChannelProxy proxy;                        // Port#1 占位（解决"服务要通道、通道要服务"的循环引用）
RoomService rooms(proxy, timers, cfg.room);            // 用例层
SessionService sessions(proxy, timers, onPlayerGone, cfg.session);
GameServer server(loop, sessions, rooms, cfg.port);   // 适配层 + Port#1 真身
proxy.bind(server);
server.start();
loop.loop();                               // 上电
```

`ChannelProxy` 是 main 私有的 20 行小类：先给服务一个空壳通道，`GameServer` 构造完成后再绑定真身。**循环引用在组装层解决，不污染任何一层的内部设计**——这是"main 当组装工"的典型收益。

## 三、消息流转全景：一条开火消息的完整旅程

以"玩家 A 开枪击中 B"为例，从网卡字节到 B 掉血的**每一步**（函数名全部真实）：

```
 [客户端] FireCommand{origin=(0,0,0), dir=(1,0,0)} 序列化为 28 字节帧
    │  [2B len=24][2B msgid=7][24B payload]  (小端)
    ▼
 ① 字节到达内核 receive queue ──► epoll_wait 返回 fd 可读(ET)
    │
 ② EventLoop::loop() → Epoll::poll() → fillActiveChannels() → Channel::handleEvent()
    │   └ tie() 守卫已锁住 TcpConnection 的 shared_ptr（本事件期间连接不会被销毁）
    ▼
 ③ TcpConnection::handleRead() —— ET 排干循环：
    │   while: Buffer::readFd(fd)  →  n>0 继续 / EAGAIN break / n==0 对端关闭
    ▼
 ④ GameServer::onMessage(conn, buf) —— 循环拆帧：
    │   ProtocolCodec::tryExtract(buf) → {msgid=7, payload=24B}
    │   ProtocolCodec::decode(7, ...) → std::variant<FireCommand>
    ▼
 ⑤ GameServer::dispatch() —— switch(msgid) 的 variant visit：
    │   a. SessionService::onActivity(pid)   ← 任何消息都喂心跳狗
    │   b. handle(FireCommand) → RoomService::handleFire(pid, cmd)
    ▼                                          [进入用例层，此后不再接触字节]
 ⑥ RoomService::handleFire：
    │   roomOf(pid) 找到玩家所在房间
    │   room->applyFire(pid, origin, dir)     ← [进入实体层]
    ▼
 ⑦ domain::Room::applyFire —— 权威判定（纯计算，无副作用）：
    │   combat::pickNearestTarget(origin, dir, 存活敌人的 AABB 列表)
    │   combat::applyDamage(75, 25) → {new_hp=50, dead=false}
    │   返回 FireResult{hit=true, victim=B, damage=25, victim_hp=50, ...}
    ▼                                            [回到用例层]
 ⑧ RoomService 构造事件并广播：
    │   channel_.sendToAll(room->playerIds(), HitEvent{A, B, 25, 50, false})
    │   （经 Port#1 接口 IGameChannel——控制流开始向外，依赖仍向内）
    ▼                                                [进入适配层]
 ⑨ GameServer::sendToAll → sendTo(pid, ev)：
    │   sessions_.connIdOf(pid) 反查连接 → connections_[connId]
    │   ProtocolCodec::encode(HitEvent) → "[len][msgid=8][shooter|victim|dmg|hp|dead]"
    ▼
 ⑩ TcpConnection::send → sendInLoop：直写内核缓冲（写不完 → output_buffer_ + EPOLLOUT）
    │
 ⑪ 字节出网卡 → 客户端 HUD 扣血、播受击特效
```

**十个步骤、四次穿越层边界**。注意两个方向的对称性：③-⑤ 在"字节世界"里收，⑦ 在"规则世界"里判，⑧-⑩ 回到"字节世界"里发——而 `#include` 方向自始至终只有 `adapters → application → domain`。

### 3.1 心跳超时踢人：定时器驱动的反向链路

另一类重要链路不是由客户端消息、而是由**时间**触发的：

```
 任意消息到达 ─► SessionService::onActivity(pid)
      └► cancel 旧定时器 + ITimerScheduler::runAfter(8000ms, 超时回调)   [经 Port#2]
                              │
              （8 秒内无任何消息）
                              ▼
 TimerWheelAdapter::runAfter → EventLoop::runAfter → 时间轮 addTimer
      └► timerfd 到期 → epoll_wait 返回 → 时间轮 tick() → 回调执行：
              ① IGameChannel::sendTo(pid, KickEvent{reason=心跳超时})   [经 Port#1]
              ② IGameChannel::close(pid) → GameServer::close
                    → TcpConnection::shutdown → queueInLoop(cleanup)
                    → Channel::disableAll + remove → close_cb_ → GameServer::onConnectionClosed
              ③ SessionService::onDisconnected(connId) → dropPlayer
                    → on_player_gone(pid) = RoomService::handlePlayerGone
                          ├► room->removePlayer(B)  [实体层：仅剩一人 → 判胜]
                          ├► 广播 PlayerLeftEvent
                          └► 广播 GameOverEvent（对局中才触发）
```

这条链路把三个 Port 调用（timer、send、close）和一次跨层联动（网络关闭 → 会话销毁 → 房间规则变更）串在了一起——**网络断开与玩家退房的一致性由事件级联保证，没有轮询、没有双向引用**。

### 3.2 击杀 → 重生 → 胜负：调度链路

`handleFire` 中若 `FireResult.victim_dead`：`ITimerScheduler::runAfter(3000ms)` 注册重生；到点回调 `room->respawn(victim)`（实体层守门：仅 Playing 状态生效，**若期间对局已结束，重生自动失效**——定时器回调与状态机的一致性不需要额外锁或取消逻辑）→ 广播 `RespawnEvent`。若 `game_over`：广播 `GameOverEvent`，房间进入 Finished，最后一个玩家离开时房间从 `rooms_` 表中回收。

## 四、为什么这样设计：四个可验证的收益

| 承诺 | 验证方式 | 依据 |
|------|----------|------|
| **可测试**：业务逻辑脱离网络可测 | `ctest` 三个测试二进制，编译时只依赖 domain/application 头文件，不链接 sightline_net | 谦卑对象模式：TcpConnection/Codec 被剥得只剩搬运字节，逻辑全在可单测的内层 |
| **可替换**：网络引擎整体可换 | 把 `adapters/` 里 TcpConnection 一族换成 asio 实现，domain/application 一行不改 | net 层不知道 game 存在（守护红线 3） |
| **可演进**：换玩法不伤框架 | 未来接第二种玩法 = 新增 domain 子模块 + 新 Service，ports 复用 | 变化速率隔离：玩法（周级变化）与引擎（年级变化）被边界切开 |
| **可守护**：架构不随时间腐化 | `scripts/check_dependencies.sh` 三条红线（domain 净空 / application 净空 / net 不含 game 头），可挂 CI | 毕设的教训：800 行配置热更新就是"没有守护的分层"烂掉的样子 |

一句话：**这套分层把"什么容易变"和"什么不能错"物理分开了**——容易变的（协议、玩法、引擎）都在外圈各自独立，不能错的（判定、血量、胜负）在最内圈被单测钉死。

## 五、未来场景推演：断线重连（W5 计划）如何落进这套架构

**场景**：FPS 对局中玩家 B 网络抖动掉线 10 秒后重连，期望恢复身份、房间与血量，而不是被系统踢出判负。

**现状缺口**：当前 `SessionService::onDisconnected` 会立即 `dropPlayer` → `handlePlayerGone` → 房间判负。重连需要"**连接断开 ≠ 玩家退场**"的语义。

**改动落点分析**（这正是架构的价值所在——每一处改动都有明确的归属层，且半径可控）：

```
domain/（改 Room，加规则）
  ├─ Player 增加 disconnected_at 字段；Room 增加 detachPlayer(pid)（保留数据、标记离线）
  │  与 removePlayer(pid)（真退场）两个语义不同的操作
  ├─ applyFire 候选过滤已天然兼容：!alive 的离线玩家不参与判定
  └─ 新规则：离线超过 N 秒才转 removePlayer（触发判负链）
     → 单测新增 6 个用例即可钉死

application/（改 SessionService，改语义）
  ├─ onDisconnected 不再直接 dropPlayer，改调 room->detachPlayer + 挂"宽限定时器"
  ├─ 新增 reconnect(token)：校验重连票据 → 恢复 connIdOf 映射 → cancel 宽限定时器
  │   → room->reattachPlayer → 广播 ReconnectEvent
  └─ 宽限定时器到点 → 才走原来的 handlePlayerGone 判负链
     → FakeTimer 单测全流程，依然不需要网络

adapters/（几乎不动）
  ├─ ProtocolCodec 增加 2 个消息号（C2S_Reconnect / S2C_ReconnectAck）
  └─ GameServer::dispatch 加一个 case，两行

net/、main.cpp：零改动
```

**改动半径对比**：如果连接管理、会话、房间规则焊在一起（毕设 HTTP 服务器的结构），这个需求要横穿 3000 行 HttpServer；现在它被拆成 domain 6 个用例 + SessionService 一个方法 + codec 两个消息号，**并且每一部分都能被已有的测试设施独立验证**。

第二个例子简说——**新增第二种玩法（如团队占点）**：`domain/` 新增 `mode/` 子模块实现规则；`application/` 的 `handleJoin` 按 RoomRules 选择玩法类型实例化 Room；adapters 的消息表扩展。`docs/reference/game_plugin.h` 里那套 `IGamePlugin` 抽象（validateAction/processAction/GameReplay）就是当时为多玩法预留的设计参考——当第二种玩法真的出现时再抽取，而不是现在（推迟决策）。

## 七、已知限制（诚实清单）与演进路线

1. **移动是"采纳式"而非"校验式"**：`Room::applyMove` 直接采纳客户端位置。反外挂的速度/碰撞校验是它自然的进化位（在 domain 内加规则，接口不变）。
2. **单进程单房间表**：跨服、分布式房间管理未做（也不该现在做——为猜测的未来预埋抽象是毕设烂掉的教训）。
3. **无鉴权**：Login 无 token 校验；接账号系统时在 SessionService 层加，不影响其他层。
4. **TCP 传输**：局域网演示无感；公网 FPS 应换 KCP（W6 计划，换传输层只动 adapters）。
5. **W4~W6 路线**：UE 客户端联调 → 断线重连 + AOI + 压测 → KCP + protobuf + 录像回放（GameReplay 思路已留在参考设计里）。
