# 求职方案评审与实施对照

> 本文回答三个问题：外部求职方案（"NetHero FPS"计划）**哪些可用、哪些与现状冲突、UE 客户端在已有蓝图用户系统上是改造还是重开**。
> 结论先行：方案与 Sightline 现状**高度互补**——方案里最难的部分（自研网络库、权威判定、协议、压测）已经完成并被验证；UE 客户端**在现有蓝图工程上改造，不重开**。
> 配套阅读：《项目交接与UE客户端实现指南》（实施步骤以它为准）、《架构设计文档》（分层依据）、《字节协议与传输详解》（协议契约）。

## 一、方案与现状逐项对照

方案设想的七周排期中，前三周的"地基"在 Sightline 已完成。逐项对账：

| 方案模块 | 方案要求 | Sightline 现状 | 差距与落点 |
|---|---|---|---|
| 自研通信层替代 NetDriver | Socket/ASIO 收发 | ✅ **手写 epoll Reactor**（毕设库剥离 3813 行，主从 Reactor） | 比方案假设的选型更强——面试叙事核心正是"手写"二字 |
| 二进制协议/序列化 | 自定义序列化 | ✅ `[2B len][2B msgid][payload]` 小端，14 条消息，两端契约文档齐全 | 道具系统只需追加消息号 |
| 服务器权威判定 | 伤害、校验 | ✅ `Room::applyFire`：hitscan 射线×AABB、取最近、血量结算、三杀判胜 | 已有 15+ 单测钉死 |
| 移动同步 | 客户端预测 + 服务器校正 | ⚠️ **半完成**：10Hz 上报 + 服务器采纳式转发 | 预测/校正未做（见第三节 W6） |
| 射击可靠传输 | Reliable + ACK | ✅ TCP 天然可靠；UDP+自研 ACK **不需要**（见第二节第 1 条） | W6 换 KCP 是既定路线 |
| 死亡布娃娃 + 3 秒重生 | 表现/数据解耦 | ✅ 服务器侧完成（RespawnEvent，3000ms，状态机守门：对局结束重生自动失效） | UE 侧表现待做（M3） |
| 断线判负/心跳踢人 | — | ✅ 惰性心跳扫描 + Kick + 退房判负 + 5s 自动重开 | — |
| 弹药箱/血包拾取 | NetID + 枚举映射、动态 Spawn/Destroy | ❌ 未做 | **新增功能**，落点明确（见第三节 W3） |
| 夺旗战（数据节点） | 带宽控制/服务端时钟进度条 | ❌ 未做 | 新 domain 子模块 + 编排，ports 复用 |
| 网络调试面板 | RTT/字节率/坐标差值 | ❌ 未做（服务器侧 stats 已有：`GameServer::logStats` 周期输出） | 客户端侧 UMG 实现 |
| UE 客户端 | 表现层 | ❌ 未联调，但 **M1~M4 路线与薄封装代码已备好**（交接文档 Step2 可直接抄） | 本文第四节回答改造/重开 |

**对账结论**：方案的总工作量约 60% 已完成，且完成部分恰是含金量最高的部分。方案真正的新增量是三块：**道具系统、夺旗模式、客户端预测**。

## 二、方案中需要修正的五个技术点

方案的架构方向（表现与通信解耦、服务器权威、枚举作通用货币）与 Sightline 完全一致，但以下五点按现状修正后执行：

1. **"UDP + 自研可靠性"对 Demo 是高风险项，砍掉。** ACK/重传/乱序重排是数周工作量，且正确性极难验证（方案自己也在第七周才敢录视频）。Sightline 已做过规模决策：8 人房 10Hz 下 TCP 队头阻塞不可见；传输层已被边界隔离（换传输只动 adapters），演进走 W6 的 **KCP（成熟可靠性实现）**，不手写。方案第 1 周"搭建 Socket 底层"是 Sightline 早已交卷的功课。
2. **道具"绝不传坐标"只在 C→S 方向成立。** 客户端上报不带权威坐标/身份——对，且 Sightline 已实现（C2S_Move 不含 playerId，身份由会话推导，协议层第一道防伪）。但服务器**下发生成事件必须带坐标**（NetID + TypeID + 出生位置），否则客户端不知道弹药箱在哪，无从表现。正确表述：*客户端不报坐标，服务器广播带坐标*。
3. **"共享枚举表"的真实形态是协议数值契约。** Sightline 服务器是纯 C++ 非 UE 工程，不存在"两边共享 UE 枚举"——实际做法与现有 MsgId 完全一样：两端各自定义同值枚举（服务器 `protocol_codec.h` 的 `MsgId` ↔ UE 的 `EMsg`），改动需两端同步、文档钉死。方案方向正确，表述需要落回这个现实。
4. **重命名"NetHero FPS"成本大于收益，不改。** 仓库、三份文档、协议契约、压测基线全部署名 Sightline，且"视线即弹道"本身就是 hitscan 玩法的命名叙事（面试官问起项目名即入题）。简历里保留 Sightline。
5. **血量增量压缩不进首版。** HP 是 1 字节字段，Delta 压缩收益趋近于零，反而引入"丢了增量怎么补"的状态歧义。作为面试话题可讲，实施优先级排在录像回放之后。

**方案中直接可用的部分**：第六节面试话术质量高，补三条 Sightline 已验证的硬数据即可上战场——
- 3 万 TCP 连接压测 0 失败，p50 0.4ms，≈8KB/连接；
- 异步日志单变量实验 p99 改善 258 倍，业务层一行未改（分层收益的实证）；
- 全项目只有 2 个接口（IGameChannel/ITimerScheduler）——"接口只在需要第二实现或测试替身时才建"的反过度设计立场。

## 四、UE 客户端：在现有蓝图工程上改造，不重开新项目

**结论：改造。** 三条依据：

1. **目标架构本来就规定"UI/动画归蓝图"。** 交接文档的总原则是"UE 只做表现层——Socket/拆包归 C++，HUD/动画归蓝图"。蓝图实现的用户系统（登录界面/菜单/HUD）站在它该站的层上，是**资产不是债务**；重开等于扔掉正确的部分、留下要写的部分。
2. **接缝很窄。** 改造的本质是把 UI 的**数据源**换掉：从"本地状态 / UE 复制系统"换成 C++ 子系统的两个委托（`OnNetMessage` / `OnDisconnected`）。交接文档 Step2 的 `USightlineNetSubsystem` 就是为此设计的——任何蓝图 UI 都能 `BindEvent` 到委托上，UMG 布局与控件逻辑一行不用动。
3. **服务器契约已就绪且可随时验证健康**（`demo_interact.py` 七步全绿），客户端任何时刻对着一个已知正确的对端联调，排错空间减半。

### 改造前的审计清单（把蓝图用户系统里的代码分成三类）

| 类别 | 内容 | 处置 |
|---|---|---|
| **保留** | UMG 布局、动画状态机、输入映射、纯本地表现状态 | 原样保留——这正是蓝图该干的 |
| **替换数据源** | 通过 UE NetDriver / 复制（PlayerState·GameState）/ 会话系统取数据的连线 | 断开旧连线，改绑 `OnNetMessage` 委托，按 msgid 解码后写入原 UI 槽位 |
| **移除** | Online 插件、Session/FindSessions 节点、复制相关设置 | 移除；Net Mode 确认 **Standalone** |

### 仅当出现以下情况才考虑新建工程

审计发现用户系统与 UE 在线子系统**大面积焊死**（如登录走 OnlineSubsystem 账号体系、深依赖 Session 界面）。即便如此也不是"重写"：新建 Blank C++ 工程（交接文档 Step1），旧工程的资产与 UMG 用 **Migrate** 迁入——损失仅是工程设置重配，半天量级。

### 改造步骤（并入交接文档 M1，30~60 分钟）

1. 现有工程加入 `USightlineNetSubsystem`（Step2 代码可整抄）→ 编译通过；
2. 登录按钮 `OnClicked`：断开原登录连线 → `Connect(127.0.0.1, 8888)` + `SendFrame(C2S_Login, EncLogin(输入框文本))`；
3. `OnNetMessage` msgid==2 → `DecodeU32` 取 playerId → 写入原 UI 的显示槽位——**UI 不改，只换数据源**；
4. 挂 2 秒 Ping 定时器 + RTT 显示（此后它就是常驻健康检查）；
5. 通过后按 M2（移动互见）→ M3（开火命中）正常推进，蓝图用户系统随后续里程碑逐步长出房间/对局界面。
